# React Native 実機テスト詰まりどころプレイブック

React Native / Expo アプリを実機(iOS実機・Androidエミュレータ含む)で動かし、
自動操作・E2E的な検証を行う際に繰り返し踏む詰まりどころと、その解消手順の一般論。
特定プロジェクトの固有値(UDID・APIエンドポイント・DBスキーマ・アカウント情報等)は
含まない。個別プロジェクトの詳細はプロジェクトローカルの手順書に別途まとめること。

## 大原則

### 1. 観測器具は「安さ」ではなく「真実への近さ」で選ぶ

詰まった時に試行錯誤を重ねる前に、観測手段を強い順に上げる。

1. 画面のピクセル(実機/エミュレータのスクリーンショット) — 最も真実に近い
2. 端末syslog / クラッシュログ
3. DB / API を直接叩いて実データ・実レスポンスを見る

要素ツリー(uiautomator dump 等)やコマンドの exit code は補助情報であって、
「見た目」や「実際に何が起きたか」の証拠にはならない。要素ツリーに要素があっても
画面上は別のカードやオーバーレイに覆われている、ということが普通に起きる
(メタデータ ≠ ピクセル)。

### 2. 同一ステージで2回失敗したら、再試行を禁止してギアを上げる

同じ手順・同じステージで2回続けて外したら、3回目をただ繰り返さない。
その場で「故障仮説を箇条書きにする → それぞれを判別できる最安の観測を1つ実行する →
結果に基づいて直す」の順に切り替える。指摘されてから切り替えるのではなく、
2回失敗した時点で自発的に切り替わるのが正常動作。

### 3. コードの存在は「適用済み」の証拠にならない

「このコードに値が書いてあるから直っているはず」という判定をしない。値がファイルに
存在することと、それが実機で正しくレンダリングされることは別。UI修正の検証は必ず
実機/エミュレータのスクリーンショットで行う。

## 環境が生きているかの事前確認(PHASE 0 的なラダー)

実機を触る前に、以下の順で「環境が壊れていない」ことを先に確認してから触る。
個別の詰まりを推測で潰しにいく前に、まずこのラダーを一通り通す。

1. **IP/ホスト名の自動同期**: Macのローカル開発サーバーのIPが変わると、ネイティブ
   バイナリに焼き込まれた古いIPのままでは端末から繋がらなくなる。IPは手動で
   `ipconfig`/`ifconfig`して自分で読み取るのではなく、プロジェクトの自動更新タスク・
   スクリプトがあればそれに出させる(複数ネットワークインターフェースがある環境では、
   人力での取り違えが実際の事故原因になる)。
2. **キーチェーン/認証ストアのロック解除**(macOS実機ビルド時): バックグラウンド
   セッションではログインキーチェーンがロックされていることがあり、これが
   `codesign` 系のエラーや謎の署名失敗、自動化ツールの原因不明のクラッシュの
   真因であることが多い。Face ID/生体認証の問題に見えても、実際はMac側の
   キーチェーンロックというケースがあるため、これを先に疑う。
3. **DBスキーマの適用漏れ確認**: マイグレーション未適用があると、特定のAPI/画面だけが
   静かに 500 エラーを返す。他は正常に動くため、一見無関係な画面の不具合に見える。
   実機を疑う前にマイグレーション状態を確認する。
4. **インフラの生存確認**: ローカルのコンテナ基盤(Docker/OrbStack等)はディスク逼迫時に
   無言で落ちることがある。ディスク残量 → コンテナ生存 → API疎通、の順に機械的に
   確認してから実機側の不具合を疑う。
5. **端末を使わずに認証/API疎通を先に確定させる**: 認証トークンの取得とAPIへの
   疎通を、実機やエミュレータを介さず直接のHTTPリクエストで確認できると、以降の
   不具合が「サーバー側」か「クライアント側」かを一発で切り分けられる。

## ビルド成功の判定を誤らない

「ビルドが成功した」ログだけでは、端末が開発サーバーに実際に接続できたことの証拠には
ならない。JSバンドルが実際に端末へ配信されたことを示すログ行(バンドラーの
"Bundled" 系メッセージ等)が出るまでを「成功」とする。補助的に、開発サーバーの
ポートに対する実際のTCP接続本数を確認すると良い(0本なら繋がっていない)。

## 「UIが空だがDBにはデータがある」時は配線を観測する

推測でシード(テストデータ)の形を変えたり、タップやリロードを繰り返したりする前に、
アプリとAPIの間にロギング用のプロキシを挟んで、アプリが実際に何を送信し、
何を受信しているかをそのまま読む。これにより「HTTP 200 だが GraphQL/APIレベルの
エラーが返っている」「バッジのカウントは別クエリで動いていて実際のリストは
失敗しているクエリを叩いている」といった、UIやDBの目視だけでは分からない不整合が
一発で判明することがある。

Expo/Metro のような環境では、環境変数はビルド時にJSバンドルへ埋め込まれる方式が
多く、稼働中の開発サーバーに対して単に `.env` を書き換えただけでは反映されない。
バンドルキャッシュをクリアして再起動する必要がある点に注意する。

## ディスク枯渇の連鎖に注意

ローカルのコンテナ基盤・DB・開発サーバーは、ディスク枯渇(ENOSPC)をきっかけに
連鎖的に落ちることがある。「何もしていないのに突然すべてが動かなくなった」時は
まずディスク残量を疑う。スクリーンショットを撮るたびに新しいファイル名で
溜め込むとディスクを圧迫しやすいため、検証用のスクリーンショットは同一パスへの
上書きで運用し、確認済みのものは消す。

## 認証エミュレータ/バックエンドの再起動に注意

認証エミュレータやバックエンドコンテナが(クラッシュ等で)再起動すると、それ以前に
発行されたトークンを持つセッションは無効化される。再起動前からログイン済みだった
端末はキャッシュされたセッションでそのまま動き続ける一方、再起動後に新規ログインする
端末は再シードされたユーザーが必要になるため、「片方の端末だけ症状が出る」という
非対称な現象が起きる。原因不明の認証エラーが特定の端末だけに出る場合、この非対称性を
疑う。

## ログイン/オンボーディング直後のモーダル地獄

クリーンな状態からログインすると、決まった順序でプッシュ通知説明・OS許可ダイアログ・
プロモーション/キャンペーンの全画面モーダルなどが連続して出ることが多い。1つでも
残っていると、以降の操作(タップ等)が無言で効かなくなる。すべて機械的に順番通り
消してから本題の操作に入る。

一部のモーダルは特定のユーザー属性(電話番号未登録など)が設定されるまで、
ホーム画面に戻るたびに再発することがある。この場合は「毎回ダイアログを閉じる」の
ではなく、根本の属性をバックエンド側で設定し、クライアントのキャッシュ済み状態
(後述)もクリアしてから再ログインする方が確実。

## クライアント側の永続化キャッシュ

Redux-persist / AsyncStorage 的なキャッシュ機構を使うアプリでは、アプリの
強制終了だけでは永続化されたキャッシュは消えない。「本当にまっさらな状態」を
作りたい場合は、アプリのストレージ自体をクリアしてから再ログインする必要がある。
古いキャッシュが残っていると、サーバー側でデータを直しても画面には反映されない
(いつまでも同じ古い状態が出続ける)ことがある。

## 座標タップは推測しない

自動操作でのタップは、スクリーンショットを見て座標を目分量で推測しない。
uiautomator dump(Android)や accessibility tree の取得(iOS/WDA)から要素の
bounds/rect を取得し、その中心座標を計算して使う。

カスタムのPressable/タブコンポーネントは、要素に対する「クリック」操作が
効かないことがある。その場合は取得した矩形の中心へ座標タップにフォールバックする。

## OTP・生年月日等の「1文字ずつ自動送り」入力欄

多くのモバイル自動化ツールの一括テキスト入力(プログラム的なテキスト注入)は、
ネイティブのIME/キーボードイベントを経由しないため、こうした制御入力欄(1文字ずつ
自動的に次のフィールドへ進むタイプの入力、OTP・日付入力等でよくある実装)では
無視されたり、連続する同一の数字が1つ脱落したりする。確実に効く方法は、
画面上のソフトウェアキーボードのキーを実際に1つずつ座標タップすることで、
実際の人間の操作と同じイベント経路を通す。

OTP/認証コードは推測せず、自分たちの管理下にあるデータストアやログから直接確認する。
多くの開発環境では、非本番環境向けに固定のOTP値を返す実装になっていることがあるため、
実際にSMS/メールを送受信する前提を疑い、まず該当のサーバー側実装を確認する。
また、OTP画面を離れて戻ると再送信がトリガーされ、以前取得したコードが無効化される
実装がよくある。コードは「送信をトリガーした直後」に取得し、すぐ使う。

## ディープリンクでオンボーディング途中の画面に飛ばない

オンボーディングのようなクライアント側の状態機械(Redux等)を持つフローは、
ディープリンクで途中の画面に直接遷移すると、状態がリセットされて画面が空になったり
必須の状態が undefined になったりする。自動化する場合も、必ずランディング/
入口から自然な操作で歩かせる。

## 非ASCII文字の入力

一部の自動化ツールのテキスト入力は非ASCII文字(日本語等)を受け付けない。
自動テストでの入力値はASCIIの仮値で代用する。

## サードパーティSDKのトースト/オーバーレイがタップを奪う

分析・クラッシュレポート・課金系のSDKがデバッグビルドで表示するトースト/バナーは、
下部のナビゲーションボタンやFABに重なって、意図しない要素がタップを奪うことがある。
覆っている要素を先に明示的に閉じてから本来のボタンを操作する。

## iOS 17+ 実機自動化の落とし穴

- iOS 17以降の実機自動化(WebDriverAgent経由)は root権限が必要なトンネル
  (RemoteXPCベースの接続)を要求する実装が増えている。トンネルを起動する
  プロセスとテストを実行するプロセスとで、設定ディレクトリ/ホームディレクトリの
  向き先が食い違うと、後者が前者の張ったトンネルを見つけられず、正しく動かない
  (見かけ上は接続拒否やリセットに見える)。両者で同じ設定ディレクトリを明示的に
  揃えることが解決策になることが多い。
- 自動化ツール自身の「アプリ起動」コマンドがOSバージョンで壊れていることがある。
  その場合はOS標準のプロセス起動/終了コマンドで代替する。
- セッション中に、別の遠隔操作系コマンド(OS標準のデバイス操作CLI等)を同時に
  混ぜて使わない。複数のトンネル/セッション機構が競合して接続が落ちる。
- アクセシビリティツリー取得APIが空を返すことがまれにある。空でなくなるまで
  数回リトライする。
- 自動化ツール自体の画面録画機能は、内部で使っているドライバと競合して壊れる
  ことがある。OSのスクリーンショット連写 + 動画合成ツールでの後合成の方が
  ドライバに依存せず確実。
- 自動化セッションは使い終わったら都度明示的に破棄する。放置するとタイムアウト
  清掃処理がフォアグラウンドのアプリを巻き込んで終了させ、次の実行を壊すことがある。

## 宣言的E2Eツール(Maestro等)の限界と落とし穴

- 対象デバイスを指定するフラグの位置がサブコマンドの前か後かで挙動が変わる
  実装があるため、公式のヘルプ/ドキュメントで正しい位置を確認してから使う。
- OS標準の「アプリ起動」相当のステップがOSバージョンで壊れていることがある。
  その場合はネイティブのプロセス起動/終了コマンドで代替する。
- 宣言的E2Eツールは、あらかじめ書かれた決まった手順しか実行できない。
  画面の状態を見ながらその場で判断して操作する必要がある場合は、
  対話的に操作できる自動化ツール(Appium系、あるいはMCP経由のモバイル操作ツール)を
  使う。

## 人にしか出来ない操作を依頼する時の手順

環境設定の変更や、実機を目で見て確認してもらうなど、人にしか出来ない操作を
依頼する時は、以下の順で回す。順番を崩すと、相手が見た瞬間には何も再現していない、
という空振りが起きる。

1. 依頼の目印を立てる(何を見てほしいかを明示する)。
2. 見える状態を先に作る(サーバー起動、データ準備、アプリ起動)。
3. 依頼する前に自分で先に測る(繰り返し測定して数値が安定/変動することを確認する)。
   自分で測れていないものを人に見せに行かない。
4. 1メッセージで、1項目だけを頼む。項目番号・見る場所・期待する結果を明示する。
5. 返事を待つ間は環境を落とさない(他の作業に移るのは良いが、開発サーバー停止・
   DB復元・コンテナ停止はしない)。
6. 返事を受け取ってから撤収する。

## 自動操作ツールの優先順位の考え方

- 対話的にタップ・入力・スクリーンショットができるMCP的なツールが使えるなら、
  それを直接使う。Pythonスクリプトを都度書く必要はない。
- MCP/対話的ツールが使えない/落ちる場合のフォールバックとして、自動化フレームワーク
  (Appium等)をCLIで直接使う。
- 決まりきった手順の反復(リグレッション用のログインフロー等)は宣言的E2Eツール
  (Maestro等)で良いが、状況判断が必要な操作には向かない。
- ユーザーに「ログインしておいて」等の操作を代わりに頼まない。自動操作ツールで
  自分で完結させる。

## 使ってはいけない操作の一般化

- 環境変数/ホスト名を人力で調べて使う(自動更新の仕組みがあるならそれに任せる)。
- 「ビルド成功」ログだけを見て「端末に反映された」と報告する。
- スクリーンショットを1枚ごとに新しいファイル名で溜め続ける。
- 画面が空の時に、シードデータの形を推測して試行錯誤を重ねる(先に実際のデータ・
  実際の通信を観測する)。
- 同一の詰まりに対して同じ操作を3回以上繰り返す(2回目で観測手段を上げる)。
- プロジェクトで明示的に「使用禁止」とされているデバイス/環境を使う。
