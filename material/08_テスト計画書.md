## 1. テスト方針

- ユニット: なし（学習者向け教材のため、テストコードの記述は第3弾で扱う）
- 結合: 04/06 で定義される画面 ↔ Supabase クライアントの動作確認を手順に含める
- E2E: Expo の web 出力に対する Playwright のみ。ネイティブ実機は手動確認

## 2. 機能要件ごとのテスト観点

| FR | 観点 |
|---|---|
| FR1 認証 | publishable key のみ使用。secret/service_role はアプリに含まないことを `strings` / 逆コンパイルで確認 |
| FR1 新規登録 | username 重複時のエラー、メール未確認状態でのログイン拒否、`auth.users` トリガー失敗時の挙動 |
| FR2 プロフィール | 他人のプロフィールは更新できない（RLS）。自分のプロフィールのみ更新可 |
| FR3 投稿 | 280 文字制限、画像 4 枚制限、他人の投稿を消せない（`deleted_at` 更新のみ自分のもの） |
| FR4 タイムライン | Realtime 配信の重複排除、オフライン復帰後の再取得、ページネーション |
| FR9 通知 | Realtime 配信の欠落を DB 再取得で埋める。`read_at` 列のみ UPDATE 可 |
| FR13/14 メール | 1 時間 2 通制限。development build カスタムスキームでリダイレクト確認 |

## 3. E2E シナリオ（Playwright / Web 出力）

1. 新規登録 → メール確認 → ログイン → 投稿 → タイムライン表示
2. 複数アカウントでフォロー・いいね・通知の動作確認
3. 他人の投稿を削除しようとした場合の RLS 拒否

## 4. 実機でしか確認できない手動確認手順

- カメラ権限ダイアログ
- ディープリンクからのアプリ起動（Expo Go と development build の両方）
- SDK 57 プロジェクトを物理端末の Expo Go で読み込む（失敗確認）
- development build の認証メールリダイレクト成功

## 5. RLS ポリシーの検証方法

1. ユーザー A とユーザー B の2アカウントを用意
2. ユーザー A の `supabaseClient` でユーザー B の投稿を UPDATE/DELETE しようとする
3. エラー `42501`（権限拒否）が返ることを確認
4. `notifications` の `actor_id` / `type` をユーザー B の自分の通知で UPDATE しようとして拒否される

## 6. G6 実走環境

- Supabase project URL / publishable key
- Node 22.x, npm 10.x
- iOS / Android 実機またはシミュレータ
- リセット手順: `supabase db reset` または `psql` で seed 再投入

## 7. モバイル試験基準

- 対応 OS 範囲: B15 参照
- 権限拒否: カメラ権限を拒否した場合の画面表示
- オフライン: Realtime 切断中の挙動、復帰後の再取得
- 再接続: Realtime チャンネルの `status` 遷移

## 8. アクセシビリティ受入基準

- コントラスト比 4.5:1 以上（主要テキスト）
- タッチターゲット 44×44pt 以上

## 9. タイムライン応答時間

- DB 側: `EXPLAIN ANALYZE` で主要クエリの実行計画を確認
- クライアント: 実機で 10 回計測し、中央値を記録
- 条件: 固定 Wi-Fi、固定 Supabase region、開発モードは除外して比較

## 10. メール系の検証

- FR13 メール確認: リンクの有効期限を確認
- FR14 パスワード再発行: トークン有効期限を確認
- 1 時間 2 通制限: 3 つ以上のアカウント作成を連続で試し、何通目で止まるか実測
