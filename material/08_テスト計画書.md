## 0. 本書の位置づけと読み方

### 0.1 着手条件は満たしている

スタブが定めた着手条件は「`04_詳細設計書.md`・`06_API設計書.md` が確定した時点」である。
両書は 2026-08-09 に本文へ書き下ろされた。ただし**どちらも凍結していない**
（04 は局長レビュー待ちのドラフト、06 は 03・05 の承認後に凍結）。
よって本書も次の扱いにする。

- 04・06 が承認時に変わったら、**同じPRで本書も直す**。
- 本書を「確定した試験仕様」として引用しない。
- 04・06・05 に無い事項を本書で新たに決めることはしない。決める必要が出た箇所は
  **§12 に未決定として期限つきで並べた**。`16_決定バックログ.md` が未決定の唯一の正本（16 A1）なので、
  台帳への起票は本書では行わない。

### 0.2 これは製品の試験計画書ではない

本書は **教材の章を書くための試験設計図**である。テストには2つの読み手がいて、
本書はその両方を扱う。**混ぜると必ず崩れるので、最初に分けておく。**

| 誰のためのテストか | 何を確かめるか | 本書のどこ |
|---|---|---|
| **学習者が自分で走らせるもの** | 自分が書いたコードとポリシーが意図どおり動くこと。**教材の本文に手順として載る** | §2 §4 §5 §10 |
| **制作側が受入として走らせるもの** | 教材のとおりに手を動かすと章の完成状態に到達すること | §6 §7 §9 |

**§5（RLS の検証）は前者である。**学習者自身に他人の行を触らせて DB に拒否されるところまで
やらせることが、`05_DB設計書.md`・`11_ターゲット・ペルソナ・UX定義.md`・`15_カリキュラム骨子案.md` の
3文書で決まっている。したがって §5 の手順は**学習者が読んでそのまま再現できる粒度**で書く。

章IDは凍結前（16 B1）なので、本書も **パート単位**（15 の A0 / A / B / C / D / E）でしか
割り付けを書かない。

### 0.3 画面とテーブルは名前で参照する

`03_基本設計書.md` §2 の画面一覧は連番 #1〜#15 に #13-2 を挟んだ16行で、
**飛び番を節番号や試験項目の番号に持ち込むと並べ替えのたびに壊れる**（04 §0.3 / 06 §1.1）。
本書は画面を名前で参照する。画面IDの体系そのものは未決である（04 §0.3 で起票を求めた項目）。

### 0.4 未決定の書き分け（04 と同じ要領）

| 印 | 意味 |
|---|---|
| （決定） | 既存文書から導出できる。本書で書き下ろす |
| **（初期案）** | 本書の案。凍結はしていない。台帳の該当項目が閉じるまで確定として扱わない |
| **【未決 Bxx】** | 台帳に番号がある未決。本書は待つ側 |
| **【未決・要起票】** | 台帳に番号が無い未決。本書の返答で起票を求めた |

**16 A3 に従い、未決には必ず決定タイミングを書く。**期限は工程上の時点で書き、日付では書かない。

### 0.5 本書が絶対にやらないこと

1. **性能の数値を置かない。**`01_要件定義書.md` §3 が「目安値は再定義中」と書き、
   16 B23 が「推測で置かない」と明記している。§9 は測り方だけを書く。
2. **測っていない挙動を断定しない。**「拒否される」「エラーが返る」と書く前に、
   それが実測済みかを §5.2 の一覧で確かめる。未実測のものは未実測と書く。
3. **05 §4 の課題2〜6 を決まっているものとして扱わない。**この5件には台帳の B番号が無い
   （06 §7.1）。試験観点も同じ穴を持ったまま書く。

## 1. テスト方針（ユニット / 結合 / E2E の範囲分担）

### 1.1 6つの層

本教材の構成では、**アプリと DB の間にサーバーが無い**。守りの実体が SQL 側にあるので、
層の切り方も前作 `task-app`（Web フルスタック）とは変える必要がある。

| 層 | 何を確かめるか | 走らせる場所 | Supabase が要るか |
|---|---|---|---|
| L0 型検査 | 型の食い違い | 手元・CI | 不要 |
| L1 ユニット | Supabase を叩かない純粋な処理 | 手元・CI | 不要 |
| L2 結合（データアクセス） | 06 §1 のデータアクセスが期待どおりの行を返すか | Supabase の実プロジェクト | **要る** |
| L3 **認可（RLS / Storage ポリシー / 列単位の権限）** | 他人の行を触ろうとして DB に拒否されるか | Supabase の実プロジェクト | **要る** |
| L4 E2E | 主要動線が通しで動くか | 未決（§3） | **要る** |
| L5 手動 | 自動化できない挙動（実機・メール・権限ダイアログ） | 実機 | **要る** |

**L3 を L2 から分けたのは意図的である。** 認可は `supabase/` 配下の SQL であり、
16 B2 が「実行されるサーバー側のコードであり、本構成の認可の境界そのもの」と明記している。
**画面のテストで代わりにはならない。**画面を通さない呼び出しが通ってしまうかどうかが論点なので、
画面を通して確かめても意味がない。

### 1.2 L1 に置けるもの / 置けないもの

L1（Supabase を叩かない）に置けるのは、**入力から出力が閉じている処理**である。
つまり、値を渡すと値が返るだけで、DB もネットワークも端末の機能も要らないものに限る。
**「06 §1 のデータアクセス一覧に現れない処理」と言い換えてもよい**が、逆は成り立たない。
一覧に載っている行でも、書き込みの**前**に画面側で回る判定は L1 に置ける。
具体的には次になる**（初期案）**。根拠はいずれも 04 である。

| L1 に置ける | 根拠 |
|---|---|
| 本文からのハッシュタグ抽出 | 04 §1.3 の書き込み順序4。本文という入力から、タグの配列という出力が決まる。**結んだ行を書くのは 06 §1 の別の処理で、そちらは L2** |
| 本文の文字数の数え方（280字） | 04 §1.2。絵文字・改行をどう数えるかで結果が変わる。06 §1 に行として存在しない |
| 画像の枚数の判定（0〜4枚） | 04 §1.2。送信ボタンを押す前の判定。**ただし DB 層での保証は 05 §4 課題2 で未決**（§5.9 の末尾） |
| 日時の表示形式 | 画面をまたいで揃える必要がある。06 §1 に行として存在しない |

**06 §1 の「対象」列だけを基準にすると、この4件は選び出せない。**
一覧で対象が Supabase でないのは「カメラで撮る（FR15）｜端末（`expo-camera`）」の1行だけで、
それは L5（実機）にしか置けない。**基準は「対象が何か」ではなく「入力から出力が閉じているか」である。**

**ハッシュタグ抽出は L1 の筆頭に置く**（初期案）。入力と出力が文字列だけで閉じており、
DB もネットワークも要らないのに、間違えると検索結果が黙って割れる。
**教材でユニットテストを最初に書かせる題材としてこれ以上の材料が本教材には無い。**
ただしタグ本体の正規化（大文字小文字・全角半角・前後の空白）を誰がやるかは未決（06 §7 U9）で、
**正規化の仕様が決まらないとこのテストの期待値が書けない**。期限は 06 U9 と同じ、
パートC の章分割が確定する前（B1）。

**L1 に置けないものを L1 に押し込まない。**Supabase クライアントを偽物に差し替えて
「呼ばれたこと」を確かめるテストは、**呼び方が正しいかを一切確かめない**。
RLS に弾かれるかどうかは偽物では再現できないので、認可は必ず L3 で見る。

### 1.3 教材での扱い（16 A9 に従う）

16 A9 が決めているのは次の3点である。本書はこれを超えない。

1. テストコードは**含める**。ただし「網羅的に書く」ではなく「**壊れたことに気づける最小のテスト**」。
2. **E2E は主要動線1本に絞る。道具は Playwright と名指しされている**（A9 の本文は
   「E2E（Playwright）は主要動線1本に絞る」）。**本数だけでなく道具も A9 の決定に含まれる。**
3. 章位置と分量は B1 で確定する。

**テストの章は「見える変化」を作りにくい。**画面は何も変わらず、ターミナルに緑が出るだけである。
`decisions/D5_章の骨格.md` D5-3 の章分割表では `tool` に寄る行になり、
**`tool` が並び順で3章連続すると G1 が FAIL する**（10 §4 G1 / 11 原則5）。
04 §1.4 が同じ理由でメール確認・パスワード再発行の連続を警告している。
**テストの章とメール系の章を隣接させると、この FAIL に当たる可能性が高い。**
B1 はこの2つを離すか、`tool` 以外の見える変化を各章に作るかを判断する必要がある。

### 1.4 CI で走らせる層と、走らせない層

CI は GitHub Actions（16 A10）。リポジトリは公開済みで、無料枠で走ることは実測済みである。

| 層 | CI で走らせるか |
|---|---|
| L0 L1 | 走らせる。Supabase が要らないので条件が無い |
| L2 L3 | **【未決・要起票】** |
| L4 | L2 L3 と同じ判断に従う |
| L5 | 走らせない（自動化の対象外。§4） |

**【未決・要起票】DB を要するテスト（L2 L3 L4）を CI でどう走らせるか。**
選択肢は3つある。(a) CI から Supabase のホスト型プロジェクトへ接続する
（**公開リポジトリなので、キーの置き方が secret 管理の話になる**）。
(b) Supabase CLI のローカルスタックを CI 上で起動する（Docker が要る。
学習者には Docker を要求しない方針〔04 §5〕とは別の話だが、教材で見せるなら衝突する）。
(c) CI では走らせず、L2 L3 は手元と G6 実走でのみ確かめる。
**この判断は §6（G6実走環境）と同じ材料を使う**ので、同時に決める。
期限は Phase 2 のゲート実装より前。

**論点はもう1つある。上の3案はどれもこれに触れていない。**
**L2 L3 のテストが A と B の2つの認証済みセッションをどう獲得するか。**
§5.3 は「アカウントが2つ要ることが、そのまま B14 に当たる」と書いたが、
これは**学習者が手で回す側**の文脈で書いたもので、**CI の文脈へは引き継がれていない。**
自動で走らせる側には、手で回す側には無い制約が3つ重なる。

1. **FR13 でメール確認を有効にする以上、未確認のアカウントではパスワードでのログインが通らない。**
   確認を自動で通す経路は Admin API（secret key / `service_role`）だが、
   **§6.4 はそれを「絶対に渡さない」と定めている。**
2. §10.1 の数え上げのとおり、**アカウントを2つ作るだけで1時間の送信上限に届く。**
   L2 L3 を CI で毎回回すと、毎回上限に当たる。
3. 上限に当たった失敗は「アプリが壊れた」ではなく「メールが送れなかった」で赤くなる（§3.3 の3）。

**§6.4 の禁止と衝突しない形で線を引き直す必要がある。**
secret key を**制作側の閉じた CI** で使うことと、**G6 の実行体や学習者へ渡す**ことは別の判断である。
前者を許すか、あるいはテスト用プロジェクトではメール確認を切るか。
どちらも決めていないので §12 に並べた。期限は上の3案と同時（Phase 2 のゲート実装より前）。

## 3. E2E のシナリオ一覧

### 3.1 まず、当てる先が無い

スタブは E2E に「Expo の web 出力に対する Playwright」を想定していた。
**この想定は、15 のパート順と噛み合っていない。**

- 15 のパート順では、web 出力は**パートD（終盤）**にしか登場しない。
- **パートB・パートC の段階では、Playwright を当てる対象が存在しない。**
- 16 A9 は「E2E は主要動線1本に絞る」と決めているが、**その1本をいつ書かせるか**が決まっていない。

**【未決・要起票】E2E をどの時点の成果物へ当てるか。**
04 §4.6 が「期限は 08 の着手前」として起票を求めた項目だが、**閉じないまま本書の着手時点を過ぎた**。
期限をそのままにすると 16 A3 の「タイミングの無い先送り」に落ちるので、
**期限を「章分割表の凍結前（B1）」へ置き直す**。理由は、この判断が「E2E の章をどこに置くか」
＝章分割そのものだからである。

### 3.2 選べる形は3つある。どれも決めていない

| 案 | 中身 | 代償 |
|---|---|---|
| (a) パートD で1本だけ書く | web 出力ができてから Playwright を当てる | E2E が最終盤にしか無い。パートB・C の間、通しの動線は誰も自動で確かめない |
| (b) パートB の段階で web 出力を先取りする | web 出力を早めに1回出して E2E を当てる | 15 の C → D の順序（「証明する対象が揃ってから」）を崩す。パートD のハイライトが先食いされる |
| (c) native 向けの別の道具で書く | 実機・シミュレータ上で動線を回す道具を使う | **その道具を教材で教える分量が丸ごと増える。**16 A9 の「最小限」と衝突する。**A9 は道具を Playwright と名指ししているので、この案を採ると A9 の改訂が要る**（代わりの道具そのものも未選定） |

**本書はどれも採らない。**選ぶのは B1 と、上の【未決・要起票】である。

### 3.3 1本に絞るなら何を選ぶか（初期案）

どの案を採っても、**動線1本の中身は先に決めておける**。
04 §4.5 の順序制約から、通しで意味を持つ最短の鎖は次になる**（初期案）**。

```
ログイン → 投稿（本文だけ）→ タイムラインに自分の投稿が出る
```

**⚠️ この鎖の最後の1手は、まだ成立するか決まっていない（B60。2026-08-09 追記）。**
01 FR4 と 03 §2 はタイムラインを「フォロー中ユーザーの投稿」としか定義しておらず、
**自分の投稿が自分のタイムラインに出るかを決めた行が、どの文書にも無い。**
本節は「出る」前提で書いているが、§2 の FR4 の観点は
「自分がフォローしていない人の投稿は出ない」＝**出ない前提**で書いてある。
出ない仕様に決着したら、この E2E は初手で成立しないので鎖を組み直す。

**メール確認を E2E の1本に含めない**（初期案）。理由は3つある。

1. メールの受信を自動化する手段が決まっていない（§10）。
2. **確認の着地点が2系統になる。**native ではディープリンクでアプリが開き、
   web ではブラウザの URL へのリダイレクトとして着地する（02 §4 は web 出力を
   「同一コードベースから Web を出す」と位置づけている）。
   Playwright は URL を直接開けるので **web 側の経路そのものは踏める**が、
   **踏めるのは web 側だけで、§4 の H6〜H8（native のディープリンク）の代替にはならない。**
   02 R1 が「モバイルでメール確認を成立させるにはディープリンクの実装が要る」と書いた難所は、
   web 側を1本通しても1つも確かめられない。
3. Supabase 標準の送信上限（1時間2通）を E2E が毎回消費する。**上限に当たった E2E は
   「アプリが壊れた」ではなく「メールが送れなかった」で赤くなる**ので、失敗の原因が読めない。

よってメール系は §4（手動）と §10（メール系の検証）へ寄せる。**これは自動化の敗北ではなく、
02 R5 が「自動テストでカバーできない」と正直に書いた範囲そのものである。**

## 5. RLS ポリシーの検証方法

**本節が本書で最も重い。**06 §2 で書き下ろした各ポリシーに対して、
「別の利用者で叩いて拒否されること」を確かめる手順を、**ポリシー単位**で並べる。

### 5.1 これは学習者がやる

`05_DB設計書.md`・`11_ターゲット・ペルソナ・UX定義.md`・`15_カリキュラム骨子案.md` の3文書が同じことを決めている。

> RLS の章は必ず「アプリを改造して他人の行を触ろうとすると DB に拒否される」実演で終える。

したがって本節の手順は、**制作側の受入項目ではなく、教材本文に載る手順**である。
書く粒度もそれに合わせる。「B のトークンで叩く」では学習者は再現できないので、
**誰のアカウントでログインした状態から、どの操作をして、何が返れば合格か**まで書く。

### 5.2 先に測っておくこと（測る前に手順を確定しない）

本節の期待値は、次の5点が実測されるまで**確定しない**。M1〜M3 は 06 が未実測として挙げたもの、
M4・M5 は本書が新たに立てたものである。

| M1 | **RLS で弾かれた update / delete が「エラー」ではなく「0行」で返るか**（06 U14） | §5.3 以降の「期待」列のほぼ全部。0行なのかエラーなのかで、学習者に見せるものが変わる。**06 U14 は「0行が何として観測できるか」（`select()` を繋いだとき／`count` を要求したときに何が返るか）も測る対象に含めている**ので、§5.3 の「判定の読み方」もここに従属する | 06 の凍結前 |

### 5.3 共通の準備

すべての手順が次を前提にする。**教材では、この準備そのものを1つの節として書く**（初期案）。

| 記号 | 中身 |
|---|---|
| **A** | 学習者自身のアカウント |
| **B** | もう1つのアカウント（他人役） |
| **P_A** | A が作った投稿1件 |
| **P_B** | B が作った投稿1件 |

**アカウントが2つ要ることが、そのまま B14（メール送信の1時間2通）に当たる。**
§10 を先に読むこと。またシードデータで用意するのか学習者が手で作るのかは **B10** で未決である。

**各行の手順は、削除していない P_A・P_B を前提とする。**論理削除を立てる手順（§5.6 の2行目）を
回したあとは、**P_A を作り直してから次の行へ進む**。理由は §5.6 の直後に書いた。
以下の表には「前提」を独立した列としては置かず、**前提が崩れる行にだけ注記を付けた**。

**判定の読み方**（M1 の実測で確定させる）:

| 表記 | 意味 |
|---|---|
| **0件** | 取得が成功して中身が空。**エラーは出ない** |
| **0行** | 更新・削除が成功扱いで返り、影響した行数が0。**エラーは出ない**（M1 で要確認） |
| **拒否** | エラーが返る。insert のポリシー違反はこの形になる |

**「エラーが出なかったから通った」と読ませない。**これが本節の教育上の核心で、
06 §6.3 が「update と delete は影響した行数を必ず確認する」を契約に入れた理由である。

**★ 「0行」を学習者がどう観測するかは、まだ書けない。**
supabase-js の `update()` / `delete()` は既定で行を返さないので、
**0行でも1行更新でも学習者の画面には同じものが出る。**観測の形は2つ考えられる。

| 形 | 何を見るか | 落とし穴 |
|---|---|---|
| 影響した行数を要求する | 返ってきた件数を読む | 要求の書き方が M1 の測定対象そのもの |
| 更新した行を返させる（`select` を繋ぐ） | 返った配列の長さを見る | **SELECT ポリシーが併走する。**`bookmarks`（本人のみ select）や `posts`（`deleted_at is null`）では、**更新が成功していても空の配列が返る**ので「0行＝拒否された」と読めない |

どちらを採るかは **M1（06 U14）に含まれている**。06 U14 の文面が
「0行が何として観測できるか（返り値の形。`select()` を繋いだとき／`count` を要求したときに
何が返るか）も含める」と書いているので、**本書はここで先に決めない。**
ただし**後者を採るなら上の落とし穴の注記が要る**ことは、測る前から確定している。
§5.1 が「何が返れば合格かまで書く」を本節の基準に掲げている以上、
**M1 が閉じるまで §5 の手順は教材本文へ出せない。**

### 5.4 どこから叩かせるか（未決）

**【未決・要起票】学習者に他人の行を触らせる経路。**選べる形が3つあり、
教材の分量と危険度がそれぞれ違う。

| 経路 | 中身 | 良い点 | 代償 |
|---|---|---|---|
| (a) アプリを改造する | 画面のコードを一時的に書き換え、他人の id を渡す | **3文書が決めた文面（「アプリを改造して」）に一致する** | 章ごとに改造して戻す手順が要る。戻し忘れると次章が壊れる |
| (b) Supabase の管理画面から叩く | 画面を通さずに問い合わせを投げる | 改造も戻しも要らない | **`auth.uid()` を持たない文脈で叩くと結果が変わる。**誰として叩いているかを学習者が見失う |
| (c) 素の HTTP で叩く | publishable key と B のセッションで直接呼ぶ | 「アプリを通さない呼び出し」という本質がそのまま見える | 道具（HTTP を投げる手段）の説明が要る。教材の分量が増える |

**RLS が守っている本当の理由**をより直接に見せる。どれを採るかで §5.5 以降の「操作」列の書き方が変わる。
期限は**パートB の RLS を扱う章の実装PR前**。

以下の表の「操作」列は、**経路を確定せずに書けるところまで**にしてある。
「B でログインした状態から〜を投げる」という形で、どの経路でも読み替えられるようにした。

| delete を書かないこと | 誰もプロフィール行を消せない | A でログインし、自分の行を delete する | **0行**（M1 待ち）。**ただし 05 と 06 が食い違っている（下記）** | 同上 |

**⚠️ 上の2行は、ポリシーが無くても「拒否」が返る。**（codex 指摘 2026-08-09。処置済み）

§5.3 の A/B の作り方では、**Auth のアカウントを作った時点で §3.1 のトリガーが `public.users` の行を自動で作る。**
`users.id` はそのテーブルの主キーであり、かつ `auth.users(id)` への外部キーでもある。したがって:

- **A の `id` を B の `id` へ更新する** → B の行はもう在るので**主キーの重複**で落ちる。`with check` を丸ごと消しても落ちる
- **A の `id` を持つ行を insert する** → 同じ理由で**主キーの重複**で落ちる。insert ポリシーを親切心で足しても落ちる

つまり**どちらも「期待どおり拒否された」という結果が、検査したい理由とは別の理由で出る。**
教材でこれをそのまま出すと、学習者は**ポリシーが効いた証拠を見ていないのに見たと思う**。
10 §1 の #10（AI の「100%合格」虚偽報告）と同じ形の、検査そのものが嘘をつく型である。

**主キーを避けた道具立ては作れない。**`id` の値として使えるのは `auth.users` に実在する id だけ
（外部キー）で、実在する id には必ずトリガーが作った行がある（主キー）。
`gen_random_uuid()` を入れれば外部キーで落ちるだけで、置き換えにならない。
**`users_update_own` の `with check` が制約しているのは `id` 列だけ**なので、
**この2つの境界は `users` では観測できない**というのが現時点の結論である。

対処の案は3つあり、どれを採るかは決めていない（§12 に期限つきで並べた）。

| 案 | 中身 | 代償 |
|---|---|---|
| (a) 観測できないことを教材で明示する | 「制約が先に効くのでポリシーの働きは見えない。だが書かないと別経路で破れる」と説明する | 学習者は証拠を見ないまま「書け」と言われる |
| (b) 同じ境界を `posts` で見せる | `posts_update_own` の `with check`（`author_id` の付け替え）は主キーに当たらないので**そのまま観測できる** | `users` の章では実演が1つ減る |
| (c) 返るエラーを実測して見分ける | 主キー重複（`23505`）とポリシー違反（`42501`）はエラーコードが違う。**どちらが先に返るかを実測**し、ポリシー違反が先なら手順は生きる | 実測が要る。順序が版に依存するなら教材に載せられない |

**(b) が素直だと考えているが、(c) の実測をしてからでないと (a) と (b) の必要性そのものが確定しない。**

**`users` の delete は、05 と 06 で書いてあることが違う。**
05 §5 のテーブル別方針は `users` の欄を「INSERT / UPDATE / DELETE」でまとめ、
「自分の行のみ（`id = auth.uid()`）。INSERT はトリガー経由なので直接は許可しない」と書いている。
**除外しているのは INSERT だけなので、DELETE は本人に許す読み方になる。**
一方 06 §2.3 は「delete のポリシーは書かない。アカウント削除は機能要件に無い」と方針を変え、
06 §2.9 の一覧も `users` の delete を「なし」にしている。
本書は 06 の方針（delete を書かない）を採って上の行を書いたが、**05 側が未修正である。**
**この差は 2026-08-09 に 06 §7.2 へ U18 として起票された**（期限は U3 と同じ「05 の局長承認前」）。
本書が当初書いていた「06 §7.2 の U 一覧にこの差を直す項目は無い」は、その起票前を見たもので、いまは誤り。
**この差が閉じるまで、上の行の期待値は M1 だけでは確定しない。**

**章末の実演としてはこの表の2行目を使う**（初期案）。プロフィール初期設定画面が
`users` の UPDATE ポリシーを学習者が最初に使う場所なので（04 §7.6）、
**その直後に「他人の行では0行になる」を見せる**のが順序として自然である。

**`notifications` の delete を誰かに許すかは未決である**（06 §7 U5）。
現在ポリシーを書かない扱いにした根拠は「通知の削除は機能要件に無い」だけで、
**要件に無いことは禁止の根拠として弱い**。期限はパートB の通知の章の実装PR前。

### 5.12 RLS を有効にし忘れたときの検証

**15 パートB の「セキュリティの扱い」が「ポリシーを書き忘れたテーブルは全公開になる、を
1分で体験→即修正、の粒度」と書いている**（粒度の根拠として 11 の原則6 を引いている。
11 の原則6 の本文は「重いトピックは必要になった瞬間に最小限」で、テーブルにもポリシーにも触れていない）。
これを確かめる手順は他のどれとも形が違うので、独立して置く。

| 手順 | 見るもの |
|---|---|
| `alter table public.<テーブル> disable row level security;` を実行する | — |
| B でログインし、そのテーブルの他人の行を更新する | **通ってしまう。**0行ではなく実際に書き換わる |
| `alter table public.<テーブル> enable row level security;` を実行する | — |
| 同じ操作をもう一度投げる | **0行になる** |

**手順1を「マイグレーションから `enable row level security` の行を消す」と書かない。**
既に適用済みのデータベースの状態は、ファイルから行を消しても変わらない。
必要なのは `disable row level security` を**新たに実行する**ことで、これは「外す」とは別の文である。
**どこでこの SQL を実行するか（管理画面の SQL エディタか、CLI か、マイグレーションを1本足すか）は
B2（`supabase/` の構造）に従属する**ので、そこは B2 待ちとする（§12）。

**⚠️ この手順は、途中で止まると RLS を落としたまま放置される（2026-08-09 追加。codex 指摘）。**
手順2 が想定外のエラーで落ちる、学習者が席を立つ、テスト処理が中断する — どれでも
**手順3 に到達しない。**そのテーブルは以後ポリシーの検査を受けないまま、
A と B のログイン済みセッションから誰の行でも書き換えられる状態で残る。
本節は「守りが外れるところを見せる」手順なので、**外したままにする経路を持ってはいけない。**
本書のどこにも後始末の記述が無かった。次の3つを手順の一部として必須にする。

### 5.13 未ログイン（`anon`）での検証

### 5.14 Realtime の購読に対する検証

**M3（06 U6）が済むまで、この節の手順は書けない。**

購読が RLS を通るなら、`notifications` は本人宛の行しか配信されず、フィルタは二重の守りになる。
**通らないなら、フィルタが唯一の守りになり、フィルタを書き忘れた時点で他人宛の通知が端末へ届く。**
どちらであるかで、この節が「念のための確認」になるか「最重要の検証」になるかが変わる。

測ったうえで、通らない場合に置く手順**（初期案）**: 通知画面の購読からフィルタを外した状態で、
B が第三者へいいねする。**A の端末に他人宛の通知が届いてしまうかを見る。**

**★ 陽性対照を先に置く。順序を逆にしない。**
上の手順は「何も届かなかった」を「RLS が購読を通っている＝安全」と読む形になっているが、
**購読は RLS 以前の理由でも1件も発火しない。**対象テーブルが `supabase_realtime`
パブリケーションに入っていなければ、購読のコードが正しくてもエラーも出ないまま何も届かない
（06 §4.1 の契約1項目目。「1項目目を落とすと §4.2 の行がすべて1件も発火しない」）。
**この状態でフィルタを外しても、最も危険な側の結論を何も検証せずに PASS させることになる。**

よって手順はこの順にする。

| # | 手順 | 見るもの |
|---|---|---|
| 1 | **フィルタを付けたまま**、自分宛の通知が届くことを確かめる | 届く。**届かないなら、この節の検証はここで止める**（パブリケーション登録を先に直す） |
| 2 | 1 が届いてから、フィルタを外す | — |
| 3 | B が第三者へいいねする | A の端末に他人宛の通知が届くか |

**1 を飛ばした 3 の「届かなかった」は何も証明しない。**

## 6. G6実走環境の定義

`10_教材制作フロー.md` §4 の G6 は「書き上がった章の手順・コード片**だけ**を、

本節はその**実行環境**を定義する。ゲートの設計そのものは 10 が正本で、本書は環境だけを書く。

### 6.1 実行主体の制約（16 A5 が決めている。本書は変えない）

- 実走は**執筆に関与していない文脈ゼロの実行体**が行う。同一セッション・同一会話文脈での実走は無効。
- 渡してよい入力は「**その章までの教材テキスト**」と「**章開始時点のスターター**」だけ。
  設計書・開発ログ・実装リポジトリを見せてはならない。
- 教材外の知識で補完して進んだ箇所は、進めたから PASS ではなく**欠落として記録する**。
- **実行体は偶数体（既定4体）、合否は過半数（D0-2）——ただしこれは G6 read の規則である。**
  10 §4 のこの記述は「面白さの判定は比較評価で行う」ブロックの中にあり、合否の設問は
  「どちらの教材を買うか」「本物を読んでいて退屈だった箇所」の2つである。
  `decisions/D0_台帳の記述ズレ修正.md` D0-2 も `g6-run.sh` の read の体数（`G6_READERS`）として書いている。
  **実走（`exec`）を何体で回すか、実走の合否をどう判定するかは、これとは別問題であり決まっていない**
  （§6.6 のとおり実走は未完走）。§12 に期限つきで並べた。

なお、この節の見出しが引く 16 A5 は5項目とも知識隔離の規則で、**体数と合否には触れていない。**
上の3つが A5、4つ目は D0-2 由来である。

### 6.3 起動とリセットの手順

旧構成にあった Docker Compose は消滅している（16 B3）。学習者に用意させるのは

1. **実行体ごとに別プロジェクトを作るか、1つを使い回すか。**4体が同じプロジェクトを共有すると、

本節が書けるのは**測り方**だけである。B23 が閉じたら、この測り方の上に数値が乗る。

### 9.2 2つの時間を分けて測る

2026-07-27 の別ファミリーレビューが指摘し、01 §3 と 16 B23 が採った線である。

| 何を測るか | 測る場所 | 何に効くか |
|---|---|---|
| **DB 側の実行時間** | Supabase 側でクエリの実行計画と実行時間を取る | 索引が効いているか。JOIN の形が悪くないか |
| **利用者の体感時間** | 端末で、操作してから画面に中身が出るまで | 読者が「遅い」と感じるかどうか |

**この2つは一致しない。**DB が速くても、端末・回線・リージョン・開発モードの分だけ体感は遅れる。
**片方だけ測って「速い」と書くと、教材が嘘になる。**

### 9.3 固定する条件

測るたびに変わる条件を先に固定しないと、**測り直すたびに違う数字が出て比較できない。**

| 条件 | 固定の仕方 | 状態 |
|---|---|---|
| Supabase のリージョン | 1つに固定して記録する | **【未決・要起票】どのリージョンか。§12** |
| 回線 | 有線・Wi-Fi・モバイル回線のどれか。速度も記録する | 同上 |
| 端末 | 機種と OS の版を記録する | **【未決 B15】** |
| 実行モード | 開発モードか本番相当か。**開発モードは遅い** | 記録する（決定） |
| データ量 | 投稿件数・フォロー数・1投稿あたりの画像枚数 | **【未決 B10】** |
| 試行回数とパーセンタイル | 何回測って、中央値か上位いくつかを採るか | **【未決・要起票】。§12** |

**データ量が B10 に従属することに注意する。**シードデータの方針が決まらないと、
「投稿10件のタイムライン」を測るのか「投稿1000件」を測るのかが決まらない。
**桁が違えば結論が変わる。**

### 9.4 測る対象のクエリは B4 で変わる

**【未決 B4】タイムライン生成をプッシュ型にするかプル型にするか。**

| 案 | 測る対象 |
|---|---|
| プル型（初期案） | 閲覧時に `follows` と `posts` を結合して取る1本のクエリ |
| プッシュ型 | 投稿時に各フォロワーの行を書く処理と、閲覧時に自分の行を取る処理の**2本** |

06 §7.1 も「プッシュ型ならテーブルが1つ増え、ポリシーが1組増える」と書いている。

### 9.5 教材での扱い

**性能の章を独立させない**（初期案）。11 の原則6 に従い、
タイムラインが遅いという文脈が生まれた章で、実行計画を1回だけ見せる。

章分割表の「見える変化」列では `tool` になる**（§1.3 と同じ問題）。

## 10. メール系の検証

### 10.1 何が制約か

Supabase 標準のメール送信は**1時間に2通まで**である（02 R2 / 01 §4 / 03 §3）。
本教材はメールを使う機能が2つあり（FR13 メール確認 / FR14 パスワード再発行）、
**複数アカウントを作る演習が章をまたいで何度も出てくる。**

メールを消費する操作を数え上げると次になる。

| 操作 | 画面 | 何通 |
|---|---|---|
| 新規登録 | 新規登録 | 1 |
| 確認メールの再送 | メール確認待ち | 1（押すたび） |
| パスワード再発行の申請 | パスワード再発行の申請 | 1（押すたび） |

**アカウントを2つ作るだけで2通に届く。**そこへ「再送を押してみる」が1回でも入ると上限を超える。
§5 の RLS 検証はアカウント2つが前提であり、06 §3.2 の通知の確認も2アカウントが要る。
**つまり、上限は教材の中で必ず当たる。**

### 10.2 B14 が未決であることを踏まえた書き方

**【未決 B14】カスタム SMTP の要否。期限は章分割表の凍結前（B1）。**
16 が 2026-07-28 に期限を再設定したものが正本である。

**期限について、他の文書を引かないこと。**
`01_要件定義書.md` §4 と `02_技術選定書.md` §7 は「捨て試作で実測してから確定する」のままだが、
**捨て試作は 2026-07-27 に完了しており、その期限はもう存在しない。**
01・02 を引いて期限を書くと 16 A3 に反する記述になる。03 §3 は再設定後の文言になっている。

したがって本節は **B14 が「要る」に転んでも「要らない」に転んでも成立する手順**だけを書く。

### 10.3 まず測る（手順を確定する前に）

B14 の文面が「**実際に何通目で止まるかを確かめてから決める。推測で決めない**」である。
本節の手順もそこに従属するので、先に測る項目を並べる。

| # | 測ること | なぜ要るか |
|---|---|---|
| N1 | **何通目で止まるか** | 「1時間に2通」が登録・再送・再発行を合算した数なのか、種別ごとなのかで演習の設計が変わる |
| N2 | **上限に当たったときに何が返るか** | 04 §1.4 が「これが分かっていないとメール確認待ち画面のエラー表示（E2）が書けない」と書いている |

### 10.4 上限に当たらないための手順（B14 が閉じるまでの暫定）

**以下は「こうする」ではなく「候補」である。**N1〜N3 を測る前に確定できない。

| # | 候補 | 何が要るか |
|---|---|---|
| C1 | **アカウントを使い捨てにせず、章をまたいで同じ2〜3個を使い回す** | 章の開始状態にアカウントが含まれることになる。**B10（シードデータ方針）と同じ判断**になる |

### 10.5 テスト用のメールアドレス

2つ目以降のアカウントに使うアドレスをどう用意するかが決まっていない。
