## 2. テーブル定義

### users

**位置づけが変わった**: 認証情報（メールアドレス・パスワード・メール確認の状態）は
Supabase が管理する `auth.users` が持つ。本テーブルは**アプリが表示に使う公開プロフィール
だけ**を持ち、`auth.users` と同じ id で1対1に対応する。

| カラム | 型 | 制約 | 備考 |
|---|---|---|---|
| id | uuid | PK, **FK → auth.users.id** | Supabase Auth のユーザーと同じ id を使う。自分で採番しない |
| username | varchar(30) | UNIQUE, **NULL 可** | 表示ID・プロフィールURL用（ログイン認証はemailで行う — Codex R2 MAJOR11で確定）。**NOT NULL を外した理由は下記「登録直後は空である」** |
| display_name | varchar(50) | **NULL 可** | 同上 |
| bio | varchar(160) | NULL | |
| avatar_url | text | NULL | |
| header_url | text | NULL | |
| created_at | timestamptz | NOT NULL, default now() | |
| updated_at | timestamptz | NOT NULL, **default now()** | 既定値が無いとトリガーからの INSERT が落ちる |

**削除したカラム**:
- `password_hash` — パスワードのハッシュ化と保管は Supabase Auth の責務。アプリの DB に
  パスワードを一切置かない
- `email` — 正本は `auth.users.email`。ここに複製すると2箇所が食い違う

**行の作られ方**: `auth.users` に行ができた時点で、DB のトリガー関数が本テーブルへ
対応する行を作る。アプリ側の書き忘れで「認証はできるがプロフィールが無い」状態を
生まないため。

#### 登録直後は username と display_name が空である（2026-07-27 決定・16 B20）

登録画面で受け取るのはメールアドレスとパスワードだけ（01 FR1）なので、
**トリガーが動く時点で username に入れる値がどこにも無い**。ここを NOT NULL のままにすると、
トリガーの INSERT が制約違反で落ちる。そして `auth.users` へ行を入れた処理は
**トリガーが落ちると丸ごと取り消される** ため、**新規登録そのものが失敗する**。
利用者の画面には原因の分からないエラーが出る。

そこで次のように決めた。Supabase 自身が公開している手順と同じ形である。

1. **`username` / `display_name` の NOT NULL を外す**（UNIQUE は残す）。`updated_at` は既定値を持たせる。
2. **トリガーは id と日時だけを埋める**。関数には `security definer` と `set search_path = ''` を付ける
   （前者は行レベルセキュリティを越えて挿入するため、後者は同名の別オブジェクトに
   すり替えられるのを防ぐため。どちらも Supabase 公式の手順に含まれている）。
3. **username と display_name は、初回ログイン後のプロフィール設定画面で本人が入れる**。
   ここは通常の更新なので、username が既に使われていれば **DB の UNIQUE 制約違反が
   そのままアプリへ返り**、「このIDは使われています」と画面に出せる。
   トリガーの中で重複させると、同じ事象が「登録に失敗しました」になって原因が読めない。
4. **登録画面で受け取った値をそのまま信用しない**。Supabase の利用者メタデータ
   （`raw_user_meta_data`）は**利用者本人が後から書き換えられる**と公式が明記しているため、
   権限や一意性の判断に使わない。必ず DB 側の制約で受け止める。

**この決定は画面の流れにも波及する**: 登録直後は「プロフィール未設定」の状態が存在する。
初回ログイン時にプロフィール設定画面へ誘導する導線を 03・04 に置く。

**まだ決めていないこと**: username を最終的に必須にするか（後から NOT NULL を付けるか、
アプリ側の誘導だけで済ませるか）、未設定の利用者を他人のタイムラインにどう表示するか。
どちらも Phase 1 で決める。

## 3. 設計判断メモ

- **posts テーブルを1本化した理由**: 通常投稿・リプライ・リポスト・引用リポストを
  別テーブルに分けると、タイムライン取得クエリが複数テーブルのUNIONになり複雑化する。
  `reply_to_post_id` / `repost_of_post_id` の自己参照で表現することで
  クエリを単純化し、初心者にも追いやすい設計にする
- **論理削除（deleted_at）を採用した理由**: リプライ元投稿が削除されてもスレッド構造を
  破壊しないため。物理削除だと `reply_to_post_id` が指す先を失う
- **未決定事項（詳細設計フェーズで確定）**: タイムライン生成をプッシュ型
  （投稿時に各フォロワーのタイムラインへ書き込む）にするか、
  プル型（閲覧時にフォロー中ユーザーの投稿をJOINして取得する）にするかは、
  想定規模（非機能要件）と学習コストのバランスを見て `04_詳細設計書.md` で確定する。
  初期案はプル型（実装がシンプル）を採用する

## 5. RLS（行レベルセキュリティ）方針

### なぜ本書に RLS の節が要るのか

サーバーを自分で書かない構成では、アプリが DB を直接叩く。つまり
**「他人の投稿を消せない」「他人になりすまして投稿できない」を守る場所が DB しかない**。
アプリ側のチェックだけでは、アプリを改造した利用者に素通しされる。

RLS は「この行を読んでよいか／書いてよいか」を DB 自身に判定させる仕組みで、
判定式の中で `auth.uid()`（＝いまリクエストしている本人の id）を使える。

**本教材で新しく教える中心概念はここ**（`00_企画概要.md` の題材理由に対応）。

### 全テーブル共通の原則

1. **すべてのテーブルで RLS を有効にする。** 有効にし忘れたテーブルは全公開になる
2. **書き込み系は必ず `auth.uid()` と突き合わせる。** 「自分の行だけ」を式で表現する
3. **読み取りは本教材では原則全公開**（SNS の投稿は公開前提のため）。
   ただし `notifications` と `bookmarks` は本人のみ

### テーブルごとの方針

| テーブル | SELECT | INSERT / UPDATE / DELETE |
|---|---|---|
| users | 全員 | 自分の行のみ（`id = auth.uid()`）。INSERT はトリガー経由なので直接は許可しない |
| posts | 全員（`deleted_at IS NULL`） | INSERT / UPDATE は `author_id = auth.uid()` の行のみ。**DELETE は誰にも許可しない**（下記★） |
| post_media | 全員 | 親 `posts` の author が自分である場合のみ |
| likes | 全員（いいね数の表示に要る） | `user_id = auth.uid()` の行のみ |
| follows | 全員（フォロー一覧の表示に要る） | `follower_id = auth.uid()` の行のみ |
| notifications | **本人のみ**（`recipient_id = auth.uid()`） | アプリからの INSERT は許可しない（DB トリガーが作る）。UPDATE は既読フラグのみ本人可 |
| hashtags | 全員 | ログイン済みなら INSERT 可（投稿からタグが生まれるため）。UPDATE / DELETE は不可 |
| post_hashtags | 全員 | 親 `posts` の author が自分である場合のみ |
| bookmarks | **本人のみ**（`user_id = auth.uid()`） | `user_id = auth.uid()` の行のみ |

### ★ RLS だけでは守れない2つのこと（2026-07-27 の別ファミリーレビューで判明）

旧構成では NestJS の処理が暗黙に守っていた制約が、サーバーを外したことで消えている。
**RLS は「どの行を触れるか」しか決めない。** 次の2点は別の手段が要る。

| 守れないこと | 何が起きるか | 対処 |
|---|---|---|
| **列を絞れない** | `notifications` の「UPDATE は既読フラグのみ本人可」は RLS では書けない。行さえ自分のものなら `actor_id` も `type` も `created_at` も書き換えられる | `authenticated` からテーブル全体の UPDATE 権限を外し、`read_at` 列だけに GRANT する（列単位の権限）。または既読化だけを行う関数を1本用意してそれだけ公開する |
| **DELETE を論理削除に変えられない** | `posts` は「リプライ元が消えるとスレッド構造が壊れる」ため論理削除（`deleted_at`）と決めた。しかし DELETE を許すと、改造したアプリから物理削除できてしまう | `posts` の DELETE は誰にも許可しない。削除は `deleted_at` を立てる UPDATE として行う |

**教材での扱い**: この2点は「RLS を書けば安心」という誤解を正す題材になる。
RLS の章の最後に、**RLS を書いたうえでなお通ってしまう操作**を1つ実演し、
列単位の権限で塞ぐところまでを見せる。

### ★ クライアントに埋め込んでよいキーと、絶対に埋め込んではいけないキー

モバイルアプリが Supabase を直接呼ぶ構成では、**アプリの中にキーが入る**。
Supabase のダッシュボードには複数のキーが並んでおり、取り違えると RLS が丸ごと迂回される。

| キー | アプリに入れてよいか | 理由 |
|---|---|---|
| publishable key（公開用） | **入れてよい** | RLS が効く。公開される前提で作られている |
| secret key / `service_role` | **絶対に入れない** | **RLS を迂回する。** 入れた時点で全ユーザーの全データが読み書きできる |

初心者が最も踏みやすい事故なので、**キーを扱う最初の章で明示する**。
「どっちを使うか分からなければ、名前に secret と付いているものは使わない」と書く。

### Storage（画像）の扱い

画像の実体は Supabase Storage に置き、そちらにも同じ考え方のポリシーを書く。
**アップロードできるのは自分のフォルダ配下だけ**にし、閲覧は全員可とする。
`post_media.url` はその公開 URL を持つ。

### 教材での扱い方

RLS は「後からまとめて書く」と必ず抜ける。**テーブルを作る章でそのテーブルの
ポリシーも一緒に書く**構成にし、章末に「アプリを改造して他人の行を触ろうとすると
DB に拒否される」ことを実際に確かめる手順を置く。
これが本教材でセキュリティを扱う唯一の形になる（`01_要件定義書.md` 非機能要件と対応）。
