# 登録不明と入力喪失の回復比較

状態: 未採用・未実装・未実測。保存API具体案で明らかになった回復不能ケースへの追加採否提案。元v7の「不存在/legacyへfenceなし」を維持したまま解決済みとはしない。以下B案はこの原候補の制約を変更するため、原WRECと04/05/06/08/16への同時採否が必要。

## 対象と対象外

対象は、正常本人・通常Auth・同project/type/keyと採用WREC契約版のcontextが残り、登録の返答が不明になり、exact inputは失ったがserverには当該予約が見つからないケース。不存在readは今後の遅延登録や保存を排除する証拠ではない。

key/context自体も失った場合、旧版/legacy、別本人/project、採用契約版を確認できない場合はB案で回復した扱いにしない。正常本人のserver履歴から既存予約/terminalを見つける原経路へ。serverにも記録がなく未知のkeyの遅延要求が残り得る状況の全面回復は未設計。B案は全端末記録消失の保証を追加しない。

| 候補 | 体験 | 保証と制約 | 採否 |
| --- | --- | --- | --- |

| C 登録と保存を一つの論理dispatchへ | 登録専用の待ちを減らす | 応答喪失と同key再送の規律は依然必要。既存before-save登録証明/画像準備/章の分量を組み直し、未知keyを自動回復する保証はない | 原章・予約設計への変更が広く、今回の修正には採らない |

原APIを変更せず「serverにないので新keyへ」で抜ける案は採らない。応答不明を失敗や未送信とみなすことになり、遅延要求による二重保存を排除できない。

## B案の唯一の終了手順

1. 正常Auth/用途/project/ownerと、残ったtype/key/採用契約版を確認する。本人が当該要求を今後保存しない選択を明示する。入力保持は要求しない。他のkeyをまとめて閉じない。
2. serverはowner/project ledger lock→当該type/key lockの順で排他する。新操作のadmission判定とは別経路にし、自身の不明/予約で終了が自己ブロックされないようにする。
3. stateを再読取する。既存successならそのtrusted receiptを返し、未保存とは表示しない。既存closedなら同receiptを返す。reservedなら現行と同じuser_cancelled閉鎖をcommitする。
4. 既知採用WREC keyが不存在なら、当該type/keyに直接closed_unsaved(reason=user_cancelled)をcommitする。これは新契約によるcancel-before-registrationで、元の予約が存在したと偽装しない。originを区別し、canonical payload/target resultなしを許す閉鎖専用recordとserver生成immutable receiptを同取引で作る。reservedを仮作成して入力検証を飛ばす方式にはしない。原schema/APIでこのterminal形を別途採用する。
5. 返答不明なら、同keyの確認/明示終了再送へ。新keyを生成せず、閉鎖成功とは表示しない。commit済みtrusted receiptだけでpendingを終了する。
6. CLOSED-01候補で当該終了結果を表示し、本人確認後にそのreceiptをackする。通常本人履歴の他の未確認操作とserver admissionを再判定してから別の新保存を許す。同keyを再利用/再openしない。新入力は空欄から始め、失った入力を保存済みとして復元しない。

新しいclosed originはstate/reasonを増やす提案ではなく、入力payloadを持たず登録前終了したterminalの証拠種別。ただし原schemaのnullable/参照制約、trusted receipt/API結果の判別、画面文言、保持/migrationを変えるため原採否は省略しない。

## 全writerへ追加する条件

- 登録再送、遅延登録、save、終了、直接DMLを含む全採用経路が同じlockとterminal先行読取へ従う。cancel-before-registrationを見た登録はreservedを作らず同closed receiptを返す。保存はmutateしない。
- 当該閉鎖recordはpayloadがないため、登録の比較入力検証より前に本人/type/key/契約版とterminalを判定する。閉鎖に入力一致を要求せず、欠落payloadを埋める再登録をしない。別ownerの結果は返さない。
- 閉鎖専用recordは本人の未確認terminal履歴に含め、ack前に新key admissionを許可しない。ただし別の未確認操作が残れば当該ackだけで新保存は許可されない。
- origin/receiptの最小identityを消去して同keyを再利用できる設計にしない。保持期間と遅延要求の有効期間を同時に決める。legacyへ遡及せず、既存successをcancel-before-registrationへ変換しない。
- 画像の一時資源があっても、closureはbytes不存在/回収完了ではない。serverの画像準備recordと採用回収規律を照合し、clientが返答不明のまま削除しない。

## 保持・旧writer・濫用の採用条件

最小fence identityは、同契約版でserverが受理し得るすべての登録/保存/直接mutation要求の最大有効期間を超えて保持する。現在その有効期間が定義されていないので、第一候補ではackや単純TTLで最小identityを消去しない。期限付きの保持へ変える場合は、旧epoch/契約版をserverで確実に受理不能にしてから消去する。client時計/自己申告versionだけで失効を判定しない。保持不能/期限無効化未成立なら「今後保存しない」保証もB採用も成立させない。

Bの保証はB対応のserver制御下の全writerに限る。有効化前に同owner/projectへ届く旧登録/保存/直接DMLにもterminal先行読取を適用するか、旧経路の権限・受理gateをserver側で失効/拒否する。旧clientや既発行要求が残っても迂回できないことを通常権限で確認する。legacy対象外という記述は、保証を迂回する旧writerの併存を許可する意味ではない。この導入条件が満たせなければB画面とreceiptを有効化しない。

payloadなしclosureのreceiptが証明するのは、「このowner/project/type/keyについてB対応writerの将来mutationをfenceしたこと」だけ。元の要求が生成/送信/登録されたこと、元payload、過去の単なる不在read、画像bytes不存在を証明しない。既存successを確認したときだけ既存success receiptを返す。serverには端末のkey生成を真正証明する能力を追加していない。

closure作成はserverでowner/project単位のrate・保持量quotaを適用し、同key再送は既存receiptを返して新recordを増やさない。具体枠・窓・待ち方は原採否/負荷測定へ返し、数値を推測しない。枠超過では新closureを作らず、確定終了や新保存許可を返さない。既存keyの確認/既存receipt再送と本人のackは、新しい不存在key作成quotaの自己ブロックへ混ぜない。任意key作成や連続ackによる濫用でも他ownerの状態を変更せず、既存操作や最小fenceを消去せず、本人履歴のページ/網羅性を虚偽にしない受入を要求する。通常本人の正当な回復もquotaで待ちになる限界と、費用/保存量/共有サービス影響を測る。未測定では濫用耐性や常時回復可能を保証しない。

## 画面の未適用差分

結果確認画面に「入力を復元できません。この保存要求を終了しますか」という候補を追加する。選択だけではclosed扱いにしない。成功receiptが返れば保存済み結果へ、閉鎖receiptなら「この保存要求は終了しました。新しく入力できます」という候補へ。ただし実際の新保存はack/本人履歴/admissionを別途満たす必要がある。closure通信不明なら同結果確認に残る。文言と導線はまだ基礎26＋追加3の正本へ反映していない。

## 必須プレモーテムと判定証拠

| 競合/故障 | 必要な結果 |
| --- | --- |
| 終了commit→遅延登録→save | 同closed receipt、reserved/mutationなし |
| 登録commit→終了→遅延save | reservedからclosed、mutationなし |
| 登録→save success→終了 | success receiptを返す。未保存案内/巻き戻しなし |
| 終了と登録の両順序、同key再送 | owner/key排他、terminal一つ、closedを再openしない |
| 終了commit後に返答喪失 | 同key確認でreceiptを再発見、別key自動生成なし |
| 入力喪失/key保持と、keyも喪失 | 前者のみB対象。後者を同じ回復成功にしない |
| 別owner/別project/契約不明/legacy | 当該結果の漏えい/閉鎖/移行偽装なし |
| ack不明・他に未確認操作・履歴不完全 | 当該closed表示を保ち、新保存の許可を別判定 |
| ack後/保持期限後の遅延要求 | 最小identityが残るかserver期限gateが拒否。再openなし |
| B導入前に発行された旧writer/直接DML | 新規B閉鎖を迂回せず、server受理gate/権限で拒否か同terminalを読む |
| 任意key大量作成/同key再送/連続ack | server枠/保持quota、重複recordなし、他owner隔離、既存回復・履歴を壊さない |
| 孤児画像・回収・消去後の遅延要求 | DB closureとbytes結果分離、key再openなし |
