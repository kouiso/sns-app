# 13. 記録・進捗管理規約

ステータス: ドラフト（局長レビュー待ち）

## 1. 目的

前作task-appで起きたプロセス起因の手戻り
（161ファイル混合コミットのtriageに1週間 / ゲート違反の蓄積でコミット不能 /
configと教材本文の矛盾が5.5ヶ月放置 / 決定が会話の中に埋もれて後から覆る）
を、記録と進捗管理のルールで構造的に防ぐ。

## 2. 決定の記録（ADR: Architecture Decision Record 方式）

- すべての設計判断は `material/decisions/` 配下に1決定=1ファイルで記録する
  - ファイル名: `YYYYMMDD-短い件名.md`
  - 中身: 決定 / 背景 / 検討した代替案と却下理由 / 影響するドキュメント
- **会話やチャットの中だけの決定は「未決定」として扱う。** ファイルに落ちて初めて決定
- 既に本文書群（00〜15）に反映済みの決定は改めてADR化しない。ADRが要るのは
  **本文書群の記述を覆す・追加する判断**が出たときのみ（二重管理の防止）
- 決定が覆るときは、旧ADRを消さず新ADRから「supersedes: 旧ファイル名」で参照する

### 2.1 「記述なし」を主張するときの調査規約（2026-07-25 実際の誤検出から追加）

日本語文書の検索は表記ゆれ（ハイフン／半角・全角スペース／カタカナ／送り仮名）で
簡単に空振りする。実例: `docker-compose` で検索して0件だったため「開発環境の記述なし」と
断定したが、実際は `04_詳細設計書.md` に「Docker Compose構成」と記述済みだった。

よって、**検索ヒット0を根拠に「その記述は存在しない」と結論づけてはならない。**
断定の前に最低限これを行う:

1. 語を分解した別パターンで再検索する（`docker-compose` → `Docker` / `Compose` / `開発環境`）
2. 関連文書（特に未着手文書の**目次予定**）を目視する — 未着手＝記述なし、ではない
3. 「無い」と書くときは、何をどう探して無かったかを証拠として併記する

この規約は未決定事項の棚卸し（`16_決定バックログ.md`）と、教材本文の事実確認の
両方に適用する。

## 3. Git運用規約

| ルール | 前作のどの事故を防ぐか |
|---|---|
| 1つの作業単位 = 1ブランチ = 1PR。教材1章は最大2PR（実装PR〔実装変更が無い章はN/A証跡で代替〕+ 教材PR）で構成し、それぞれ別ブランチ（Codex R5 M4対応） | 161ファイル混合コミット（issue #101） |
| 種類の違う変更（教材本文/スクリプト/設定）を同一コミットに混ぜない | 同上 |
| 章の教材PRは、その章の G6 対照版2本（`g6/<章ID>/plain.md`・`minus.md`）の作成・更新を**同じPRに含める**。改訂タグを打つ実装PRでも同様（10 §4・D17-5） | 対照版が本物と別PRで動くと、比較の対象が本物と別内容の文書になり、G6 read の勝敗が「改訂で良くなったか」を測らなくなる |
| ゲートFAILの変更はマージ禁止（CI必須化）。「あとで直す」の先送り禁止 | 違反蓄積でコミット不能（issue #258） |
| 章の実装PRのマージ条件は「**触った面すべての累積証拠**（10 §4の累積式 — 章種別ラベルで弱いゲートを選ぶことは不可）＋マージ時に章タグ付与」。教材整合チェック（G5）は**教材PR側**で実行し、実装PRには課さない（Codex R3 C1 / R7 M1対応） | BLOCKED enum 1.5ヶ月放置 |
| コミットメッセージは「何を・なぜ」。「進捗コミット」のような無情報メッセージ禁止 | 後から追跡不能になった諸事例 |
| **組版の生成物を git で追跡しない**（2026-08-06 追加。出力 PDF / EPUB / `.vivliostyle/` の中間 HTML と `publication.json` / 組版用の派生 md）。配布物は CI かローカルで生成する。`.gitignore` に記載する | 実測で `vivliostyle build` のたびに `.vivliostyle/`（20K）と PDF（1章 290KB）が作業ディレクトリに生まれる。教材PRのたびに PDF がバイナリ差分として積み上がると §1 が防ごうとしている「後から追跡不能」に直結する |
| **配布物のビルドは清潔な専用ディレクトリで行う**（2026-08-06 追加） | 実測で、作業ディレクトリに置いた PNG が EPUB へ全部同梱された（15 files 中6件）。webpub でも `listings/*/assets/` の画像が丸ごとコピーされた |

例外（Codex R2 MAJOR7対応）: 文書間の矛盾を解消する整合修正は、矛盾している両文書を
**同一PR**で直してよい（14の「矛盾を見つけたら同一PRで直す」ルールと衝突させない。
この場合は「1つの矛盾の解消」を1論理変更として扱う）。

## 4. 進捗の見える化（進捗台帳）

- `material/PROGRESS.md` を単一の進捗台帳として置く（このファイルが常に最新の正）
- 計画フェーズ中: 文書00〜16それぞれの状態
  （`material/18_章分割表.md` を実在させた時点で 00〜18 へ広げる — D1-6）
  （ドラフト / 局長レビュー中 / 承認済み / 改訂中）を表で管理
- 伴走フェーズ中: 章単位の状態を**実装と教材の二軸**で管理（Codex R4 M6対応 —
  実装マージから教材完成までの間の実状態を台帳が表現できるようにする）:
  実装軸（未着手 / 実装中 / 実装マージ済み・タグ付与済み / 対象外・タグ付与済み〔実装変更の
  無い章。N/A証跡つき — Codex R5 M4対応〕）×
  教材軸（未着手 / ドラフト / G3通過 / G4通過 / G5通過 / G6実走済み / 局長審査 /
  マージ済み / **改訂待ち〔`material/drift/台帳.md` にその章の未処置ITEMが1件以上ある〕** /
  検証待ち〔非常停止中マージのバックフィル待ち — §7〕）（Codex R1 m2 / R3 M8対応。
  2026-08-06 に「改訂待ち〔乖離分類(b)〕」と「外部起因対応中〔乖離分類(c)〕」を1状態へ統合 — D20-5）。
  **分類(a)(b)(c)の別は ITEM 行が正本であり、PROGRESS 側に再掲しない。**
  「改訂待ち〔乖離分類(b)〕」という名前は、10 §4 が「分類(a)(b)は引用方式では発生しない」と
  宣言した状態の名前になっていて、台帳と台帳の再掲が食い違う経路を作っていた。
  複数章・全体に係る場合に PROGRESS 冒頭へ全体ブロック行を置く運用は残す
- 更新タイミング: 状態が変わったPRの中で**同時に**更新する（台帳更新を別作業にしない —
  別作業にした瞬間に乖離が始まる）

## 5. 方針と実体の同期チェック（前作ZIP事件対策）

前作では「ZIP配布しない」という方針(config)と「ZIPを展開して」という教材本文が
5.5ヶ月矛盾したまま放置された。原因は方針と実体が別ファイルにあり、
同期を強制する仕組みがなかったこと。

- 本作では、方針を定めた文書（00〜15）に対して、教材本文がそれと矛盾しないかを
  検査する `check_policy_sync.py`（仮称）を教材執筆開始前に用意する
  - 最低限の検査対象: 配布形式の記述 / **不採用スタック名の混入**（Capacitor / NestJS /
    Redis / BullMQ / MinIO / TanStack Router / Prisma / bcrypt / Xcode などが教材本文に
    登場したらFAIL。2026-07-26 の構成振り直しで対象語が入れ替わった）/ 登場人物名の統一
- 方針文書を改訂したら、同じPRで検査ルールも更新する
- **★ 2026-08-06: 配布形式の語彙が入れ替わった。** 16 B9 を「教材本文＝PDF 正本・EPUB 併産」で
  決着させたため、検査対象語は `ZIP` / `Webサイト` / `PDF` / `EPUB` / `webpub` になる。
  **`check_policy_sync.py` は未実装である。**上の行の要求（同じPRで検査ルールも更新する）を
  満たすため、**B9 の記述をこれ以上書き換える改訂は、検出器の実装より先に走らせない**。
  現時点で配布形式の語彙が登場するのは 11 §5 ／ 16 B9 ／
  `decisions/task-app資産棚卸し.md` の3か所で、2026-08-06 にすべて同時に更新した

## 6. ふりかえりの記録

- 各フェーズ完了時（局長承認が出た時）に、`material/retrospectives/` に
  そのフェーズの「うまくいったこと / 手戻りかけたこと / 次フェーズへの変更」を
  1ファイル残す
- 手戻り対応表（`10_教材制作フロー.md` §1）は生きた文書として扱い、
  本作で新たな手戻りが発生したら**同じ表に行を追加**する（17件目、18件目…）。
  対応表に載らない手戻りは「なかったこと」になるのが最悪の結末
- **追記の運用**（2026-08-06 追加。`decisions/D22_記録運用の確定.md` D22-1〜D22-5）:
  - **判断者**は受注側（副長＋レビュー担当）。書いた本人以外のレビュー承認を要求し、
    セルフ承認は禁止。局長承認が要るのは、追記行の「対策」が凍結物（スタック・文体スペック・
    章分割表）または G0〜G6 のゲート構成の新設・変更を求める場合だけで、
    **その場合も行の追加自体を承認待ちにしない**（記録が遅れるほど再現が困難になるため）
  - **載せる基準は3条件の同時成立**: (1) 完了・凍結・承認したとみなしていた成果物または決定を、
    後から作り直した／撤回した／やり直した (2) その作業が現に発生した（予測・懸念ではない）
    (3) ファイル行・コミットSHA・記録の引用のいずれかで証拠を指せる。
    **未発生の穴は 16 へ／誤検知1件は §7 の回帰サンプルへ／外部起因の一過性失敗は
    drift 台帳の分類(c) ITEM へ**送り、この表には載せない
  - **契機は4つ**: (1) やり直しが発生したその場（作り直しPR・撤回記録と同じPRで行を足す）
    (2) 各フェーズ完了時のふりかえり（§6 前段）— その期間の追記行番号一覧か「追記なし」を必ず書く
    (3) 敵対・外部レビューの指摘が上の3条件を満たすと判定されたとき（処置台帳に行き先を記録）
    (4) ゲートの非常停止・期限切れ・完了条件の未達が確定したとき
  - **番号は17から連番、欠番なし、削除・再利用禁止。** 誤って載せた行は削除せず、
    打ち消し線と取り下げ理由を残す。同じ根本原因の別の現れ方は行を分けず既存行の証拠欄へ
    追記し、対策が別々に必要になったときだけ分ける。列は4列のままにし、出どころ
    （前作か本作か）は証拠欄の先頭に書く
  - **「対策」列を空欄にしてよいのは、16 の B番号または `material/decisions/` の D番号を
    書いた場合だけ。** Phase をまたいで対策未定のまま置かない（次フェーズの完了条件を
    判定する時点で、対策未定の行が残っていたらそのフェーズを完了と宣言しない）

## 7. ゲート例外・誤検知の運用（Codex R1 M13対応 — 前作#12/#15の再発防止）

**2026-08-06 に設計を変更した**（`decisions/D16_ゲート例外の設計変更.md`）。
旧方式は「本文の中に免除の合図を置く」形で、捨て試作の G5 で3ラウンド連続で迂回された。
教材本文がコード例に同じ文字列を含んだ瞬間にゲートが外れる。

- **適用対象**: **G3 の機械チェック項目のうち 構造・文体・混入検査・方針同期チェック の4つ**。
  「開発ログ存在」は適用対象から**外す**（D16-7。存在確認は `test -f dev-logs/<章ID>.md` の
  真偽であり、条件つきで通す余地が無い）。「方針同期チェック」は 10 §3 が G3 の項目に
  含めているのに §7 の列挙から漏れていたため**加える**（D16-8）。
  テスト・**RLS検証**・実機確認・ビルド・累積証拠ゲート・G5・G6には適用できない
  （旧記述の「OpenAPI照合」は構成振り直しで消滅し、その位置を RLS 検証が引き継いだ
  — 10 §4 の累積式マージ条件と対応）— これらを
  通せない場合の経路は非常停止＋バックフィル検証のみ（Codex R8 M3対応）。
- **合図を教材本文の中に置かない**（D16-1）。`<!-- quality-exception: 理由 -->` は**廃止**する。
  **本文に書かれた文字列は、どこに書かれていてもゲートの判定材料にしない。**
- **免除簿はリポジトリ直下の `gate-exceptions.tsv` 1本**（D16-2）。章ごとにファイルを分けない。
  読み取りは `scripts/curriculum-qa/gate_exceptions.py` 1本に集約する。
- **1行は6列 TSV**（D16-3）: `章ID / 検査ID / ルールID / 上限件数 / 理由 / 申請PR番号`。
  `#` 始まりと空行はコメント。行番号・文字位置は列に持たせない（本文が1行ずれるだけで
  免除が外れる／別の箇所に効く）。上限件数は正の整数で、その行が抑止してよい指摘の最大数。
  **理由が空の行は FAIL。承認者の列は置かない**（次項）。
- **承認は免除簿に書かせず、CI が GitHub の PR レビューを直接見る**（D16-4）。
  免除行が追加・変更された PR には「**PR 作成者以外のアカウントによる approve が1件以上**」を
  要求する。既存行に触れていない PR には要求しない。作成者以外かどうかは CI 側で
  `reviewer != PR author` を自分で比較し、GitHub が自己 approve を拒否する挙動に依存させない。
  **⚠️ これで機械化できたのは「セルフ承認禁止」の側だけである。**「局長または委任された
  レビュー担当」という**承認者資格の側は1行も検査されない**（名簿が存在しないため）。
  リポジトリは公開なので、この条件のままでは第三者の approve でも免除が通る。
  よって **C10（委任先の名簿）が確定するまで、免除簿の運用を開始しない**。
  名簿未確定を FAIL 条件として `gate_exceptions.py` に持たせる。
- **件数上限は1章につき最大3件**（据え置き。D16-5）。`gate_exceptions.py` が簿の全行を
  章IDでグループ化し、**章IDごとの行数**が3を超えたら FAIL。検査IDごとではなく章ごとの合計で数える。
- **検査は「簿を丸ごと」**（D16-6）。次のいずれかで非ゼロ終了する:
  (1) 簿が読めない／パース失敗（ERROR で止める） (2) 列数が6でない・上限件数が正の整数でない・
  理由が空の行がある (3) 章IDが章分割表に無い／tombstone 済み (4) 検査ID・ルールIDが
  その時点の G3 の語彙に無い (5) 章IDごとの行数が3超 (6) **実際の抑止件数が0の行がある**（残留行）
  (7) 実際の抑止件数が上限件数を超える (8) 免除行があるのにその PR に承認が無い
  (9) C10 の名簿が未確定。加えて、免除した章ID・検査ID・ルールID・抑止件数を毎回標準出力へ出す。
  **簿が空（全部コメント）なのは正常で FAIL にしない。**
- **誤検知を見つけたら**: (1) そのPRは免除簿に1行足して通す（理由と申請PR番号を書く）→
  (2) 同じPR内で、誤検知した実文をゲートの回帰サンプル（検知テスト）に追加 →
  (3) ゲート本体の修正は**別PR**にする
  （前作PR #268の「ゲート修正自体のバグ」を教材PRに混ぜない）→
  (4) ゲートを直したら、残留行になった免除行を消す（条件6 が消し忘れを落とす）
- **非常停止**: ゲートの不具合で複数のPRが止まった場合、当該ゲートだけを一時的に必須から
  外す判断は局長承認で行い、ADRに記録する（黙って外さない）。ADRには (a)責任者
  (b)復旧条件 (c)期限（最大7日、延長は再承認）を必記し、復旧タスクを同時に起票する
  （「一時的」の恒久化を防ぐ — Codex R2 MINOR3対応）。**非常停止中にマージされた章は、
  ゲート復旧後に当該ゲートを再実行（バックフィル検証）するまでPROGRESS上「検証待ち」とし、
  Phase 3完了条件に含めない**（未検証マージの恒久化を防ぐ — Codex R4 M7対応）
- **廃止した記法の残存を探す検査は作らない**（D16-1 の後半）。旧記法 `<!-- quality-exception: -->`
  は本文に書かれても判定材料にならないので、残っていても無害である。残存検知を足すと、
  「本文の文字列を読んでゲートの挙動を変える」経路が別の形で戻ってくる。
  代わりに G3 の検知テストへ **「旧記法を地の文に書いても FAIL のまま」** を1本入れる。
  この回帰検査が、本文由来の免除経路が復活していないことを毎回証明する。
- **G5 の免除簿（`prototype-chapter/g5-exempt.txt`）とは挙動が違う。** あちらは
  「簿に載せた時点で FAIL」まで閉じており、条件つきで通る本節の簿とは別物である
  （§7 の適用対象に G5 は含まれないので直接の矛盾ではない）。統合するかどうかは **B46**
