# 13. 記録・進捗管理規約

ステータス: ドラフト（局長レビュー待ち）

## 1. 目的

前作task-appで起きたプロセス起因の手戻り
（161ファイル混合コミットのtriageに1週間 / ゲート違反の蓄積でコミット不能 /
configと教材本文の矛盾が5.5ヶ月放置 / 決定が会話の中に埋もれて後から覆る）
を、記録と進捗管理のルールで構造的に防ぐ。

## 2. 決定の記録（ADR: Architecture Decision Record 方式）

- すべての設計判断は `material/decisions/` 配下に1決定=1ファイルで記録する
  - ファイル名: `YYYYMMDD-短い件名.md`
  - 中身: 決定 / 背景 / 検討した代替案と却下理由 / 影響するドキュメント
- **会話やチャットの中だけの決定は「未決定」として扱う。** ファイルに落ちて初めて決定
- 既に本文書群（00〜15）に反映済みの決定は改めてADR化しない。ADRが要るのは
  **本文書群の記述を覆す・追加する判断**が出たときのみ（二重管理の防止）
- 決定が覆るときは、旧ADRを消さず新ADRから「supersedes: 旧ファイル名」で参照する

## 3. Git運用規約

| ルール | 前作のどの事故を防ぐか |
|---|---|
| 1つの作業単位 = 1ブランチ = 1PR。教材1章は最大2PR（実装PR〔実装変更が無い章はN/A証跡で代替〕+ 教材PR）で構成し、それぞれ別ブランチ（Codex R5 M4対応） | 161ファイル混合コミット（issue #101） |
| 種類の違う変更（教材本文/スクリプト/設定）を同一コミットに混ぜない | 同上 |
| ゲートFAILの変更はマージ禁止（CI必須化）。「あとで直す」の先送り禁止 | 違反蓄積でコミット不能（issue #258） |
| 章の実装PRのマージ条件は「**触った面すべての累積証拠**（10 §4の累積式 — 章種別ラベルで弱いゲートを選ぶことは不可）＋マージ時に章タグ付与」。教材整合チェック（G5）は**教材PR側**で実行し、実装PRには課さない（Codex R3 C1 / R7 M1対応） | BLOCKED enum 1.5ヶ月放置 |
| コミットメッセージは「何を・なぜ」。「進捗コミット」のような無情報メッセージ禁止 | 後から追跡不能になった諸事例 |

例外（Codex R2 MAJOR7対応）: 文書間の矛盾を解消する整合修正は、矛盾している両文書を
**同一PR**で直してよい（14の「矛盾を見つけたら同一PRで直す」ルールと衝突させない。
この場合は「1つの矛盾の解消」を1論理変更として扱う）。

## 4. 進捗の見える化（進捗台帳）

- `material/PROGRESS.md` を単一の進捗台帳として置く（このファイルが常に最新の正）
- 計画フェーズ中: 文書00〜15それぞれの状態
  （ドラフト / 局長レビュー中 / 承認済み / 改訂中）を表で管理
- 伴走フェーズ中: 章単位の状態を**実装と教材の二軸**で管理（Codex R4 M6対応 —
  実装マージから教材完成までの間の実状態を台帳が表現できるようにする）:
  実装軸（未着手 / 実装中 / 実装マージ済み・タグ付与済み / 対象外・タグ付与済み〔実装変更の
  無い章。N/A証跡つき — Codex R5 M4対応〕）×
  教材軸（未着手 / ドラフト / G3通過 / G4通過 / G5通過 / G6実走済み / 局長審査 /
  マージ済み / 改訂待ち〔乖離分類(b)〕 / 検証待ち〔非常停止中マージのバックフィル待ち —
  §7〕）（Codex R1 m2 / R3 M8対応）
- 更新タイミング: 状態が変わったPRの中で**同時に**更新する（台帳更新を別作業にしない —
  別作業にした瞬間に乖離が始まる）

## 5. 方針と実体の同期チェック（前作ZIP事件対策）

前作では「ZIP配布しない」という方針(config)と「ZIPを展開して」という教材本文が
5.5ヶ月矛盾したまま放置された。原因は方針と実体が別ファイルにあり、
同期を強制する仕組みがなかったこと。

- 本作では、方針を定めた文書（00〜15）に対して、教材本文がそれと矛盾しないかを
  検査する `check_policy_sync.py`（仮称）を教材執筆開始前に用意する
  - 最低限の検査対象: 配布形式の記述 / 技術スタック名（不採用にしたTanStack Start等が
    本文に登場したらFAIL）/ 登場人物名の統一
- 方針文書を改訂したら、同じPRで検査ルールも更新する

## 6. ふりかえりの記録

- 各フェーズ完了時（局長承認が出た時）に、`material/retrospectives/` に
  そのフェーズの「うまくいったこと / 手戻りかけたこと / 次フェーズへの変更」を
  1ファイル残す
- 前作の手戻り16件表（`10_教材制作フロー.md` §1）は生きた文書として扱い、
  本作で新たな手戻りが発生したら**同じ表に行を追加**する（17件目、18件目…）。
  対応表に載らない手戻りは「なかったこと」になるのが最悪の結末

## 7. ゲート例外・誤検知の運用（Codex R1 M13対応 — 前作#12/#15の再発防止）

- **例外承認**: 適用対象は**G3の機械チェック項目（構造・文体・混入検査・開発ログ存在）のみ**。
  テスト・OpenAPI照合・実機確認・ビルド・累積証拠ゲート・G5・G6には適用できない — これらを
  通せない場合の経路は非常停止＋バックフィル検証のみ（Codex R8 M3対応）。
  どうしてもG3のルールに従えない正当な理由がある場合のみ、該当箇所の直前に
  `<!-- quality-exception: 理由 -->` を書いて通す。例外は1章につき最大3件。理由なし例外は
  G3でFAIL。例外には**承認者の記録**が必要 — PRレビューで局長または委任されたレビュー担当が
  承認コメントを残す（書いた本人のセルフ承認は禁止。Codex R4 M7対応）
- **誤検知を見つけたら**: (1) そのPRは例外記法で通す → (2) 同じPR内で、誤検知した実文を
  ゲートの回帰サンプル（検知テスト）に追加 → (3) ゲート本体の修正は**別PR**にする
  （前作PR #268の「ゲート修正自体のバグ」を教材PRに混ぜない）
- **非常停止**: ゲートの不具合で複数のPRが止まった場合、当該ゲートだけを一時的に必須から
  外す判断は局長承認で行い、ADRに記録する（黙って外さない）。ADRには (a)責任者
  (b)復旧条件 (c)期限（最大7日、延長は再承認）を必記し、復旧タスクを同時に起票する
  （「一時的」の恒久化を防ぐ — Codex R2 MINOR3対応）。**非常停止中にマージされた章は、
  ゲート復旧後に当該ゲートを再実行（バックフィル検証）するまでPROGRESS上「検証待ち」とし、
  Phase 3完了条件に含めない**（未検証マージの恒久化を防ぐ — Codex R4 M7対応）
