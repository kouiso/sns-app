## 1. 正本教材から抽出した文体スペック

局長の既存教材（「変数と定数_第3稿」「関数_第2稿」等を実際に読んで分析）から、
以下を本教材の文体スペックとして凍結する。

### 1.1 形式: 話者ラベルつき対話台本

```
磯貝）まず、文法における一番最初の概念として、変数と定数というものがあります。
阿部）はい。よろしくお願いします。
```

- 話者ラベルは「名前）」形式（全角閉じ括弧）で行頭に置く
- 地の文は原則使わない。説明はすべて先生のセリフとして書く
- 見出し・コードブロック・図表は対話の外に通常のMarkdown要素として置く

### 1.2 先生（磯貝）のセリフの特徴

| 特徴 | 実例（正本より） |
|---|---|
| です・ます調ベース＋自然な口語混じり | 「じゃあ何で"let"で書くんだって話になりそうだけど」 |
| 具体物への例え | 変数=「箱」、再代入=「りんごを出してオレンジを入れる」 |
| 手を動かさせる指示 | 「これを実行してみましょう。Runボタンをクリックしてみてください」 |
| 出力結果を一緒に確認 | 「"りんご"、"りんご"って出ましたね」 |
| 難しい背景は気楽に流す | 「ちょっと難しい話だから、ああそうなんだという程度で読んでください」 |
| 覚えるべき用語は明示 | 「用語として頭に入れておいてください」 |

### 1.3 生徒（阿部）の4つの役割

生徒は相槌要員ではない。以下の役を果たす（1・2・4は全章必須、3は開発ログ連動の
条件つき — Codex R3 MINOR4対応）:

1. **質問する**: 学習者が抱く疑問を代弁する
2. **誤答する**: もっともらしい間違いをして、先生が正す（例: 呼び出す関数を取り違える）
3. **エラーを踏む**（条件つき — Codex R1 M10対応）: 開発ログ（10 §5）に「教材に載せる価値: 高」の
   詰まりがある章のみ。無い章では架空のエラーを創作せず、質問・誤答・復唱で構成する
4. **復唱まとめ**: 章末に学んだことを自分の言葉で要約し、先生が補足・確認する

### 1.4 章の骨格（**章の骨格の正本はここ1箇所**。2026-08-06 に7要素へ確定 — D5-1）

骨格は 12 §1.4・11:79・11:85-86・15:45 の4箇所に分かれて食い違っていた。
どれを満たせば章が完成かが章ごとのその場判断になるため、本節へ一本化する。
順序は下のとおりで、入れ替えない。

| # | 要素 | 必須条件 |
|---|---|---|
| 1 | 章タイトル ＋「この章でできるようになること」＋ 前章からの接続1文 ＋ 前提（環境・既習事項） | 全章必須 |
| 2 | **完成品の地図** — 完成品SNSの画面図の中で「今日作るのはここ」を示す（11:85-86 由来。新設） | 全章必須 |
| 3 | 対話で概念導入（例え話→コード実行→出力確認）。**この中に「最初に目に見える結果」を置く** | 全章必須 |
| 4 | 生徒のエラー体験→先生と解決 | 開発ログに「教材に載せる価値: 高」の詰まりがある章のみ |
| 5 | 生徒の復唱まとめ→先生の締め | 全章必須 |
| 6 | **よくあるエラーと対処**（章末。11:79 由来。新設） | 振り分けの結果が1件以上ある章のみ |
| 7 | 演習問題（正本と同じく本文と対で用意する。解答は別掲） | 全章必須 |

**要素4と要素6の振り分け**（D5-2）: 開発ログ・G6記録の1エントリは、要素4か要素6の
**どちらか一方だけ**に現す。

- 「教材に載せる価値: 高」 → **要素4**（対話で再現する）
- それ以外（価値 中／低・`ai-artifact`・G6実走で出た詰まり・実行体が教材外知識で
  補完した箇所） → **要素6**（章末に列挙する）

**要素6の中身は実記録由来のみで、創作しない。** 検査は
「要素6へ振り分けられたエントリ数 = 章の要素6の項目数」の突合で行い、
**0件どうしの一致は PASS**（記録が0件の章では節そのものを置かない）。
G6RUN で新たに観測された詰まりは、教材PR提出前に要素6へ反映する。
突合を新規スクリプトで作るか既存の検査を手直しするかは B31 の分類結果待ち（B39 と同層）。

**章の骨格ではなく章分割表の列で持つもの**（D5-3）: 11 の原則4（地図）・原則5（見える変化）と
15:45 の「最初の結果」は、章単位ではなく**並びの上でしか判定できない**ものを含むため、
`material/17_章分割表.md` の列（`地図` / `見える変化` / `最初の結果`）として持ち、G1 で検査する
（10 §3 G1 を見よ）。要素2・要素3 はその列の値を章本文で実際に果たす側にあたる。

## 2. AI臭さ排除規則（前作PR #266事件の再発防止）

前作では誇大・情緒的・トレーラー調のAI文体が混入し、局長から
「こういう誇大表現みたいなもの、やめてくれ」という直接苦情に至った（491行削除の書き直し）。
本作では以下を**執筆開始前から機械ゲートで**禁止する。

### 2.1 禁止表現カテゴリ

| カテゴリ | 例（すべて禁止） |
|---|---|
| 誇大・煽り | 「ついに」「いよいよ真の」「〜する日です！」「魔法のような」 |
| 情緒・詩的 | 「本当に外へ出るのだから」「かなり気持ちいい日」「ちょっと自慢してよい」 |
| AI構文 | 「〜と言えるでしょう」「重要なのは〜という点です」の乱発、箇条書き全太字の並列構造 |
| 英語直訳調 | 「〜することができます」の乱発（→「〜できます」）、「それでは〜していきましょう」の機械的反復 |
| 関西弁・タメ口 | 教材本文では全面禁止（前作で混入→35ファイル一括変換の原因） |
| 記号 | 教材本文で絵文字禁止。強調は太字のみ |

**この表に語を足したら、同じPRで検出器と検知テストも足す。** 6カテゴリの機械強制の実体は
`prototype-chapter/prh/sns-app.yml`（57ルール）で、検知テストは
`prototype-chapter/prh/testdata/`（陽性 `positive.md` / 陰性 `negative.md` / 実行器 `run.sh`）。
表と辞書が離れると、方針だけがあって検出されない語ができる（前作ZIP事件と同型）。
絵文字の検出は `/[^\x00-￿]/`（BMP の外の全コードポイント）と
`/[☀-➿]|[⬀-⯿]|️/` の2ルールで行う。矢印（U+2190〜U+21FF）は
絵文字ではないので対象に入れない。★（U+2605）は記号面に含まれるため対象になる。
常体（タメ口）を見るルールの語尾境界は**行末に限る**（行の途中で終わる終止形は検出しない）。
行途中まで拾う版は捨て試作3本に対し 真1 : 偽2 で、動作の列挙や太字ラベルを誤検知した（D8-2）。
1行に複数の文があり常体が行の途中で終わる形をどう検出するかは未決（D8 U8-1）。

### 2.2 対話形式ならではの追加規則

- 生徒のセリフを「はい」「なるほど」だけの相槌にしない（4役割のどれかを果たす）
- 先生のセリフ1つを272文字以内目安（正本の最長実測値）。超えるなら生徒の相槌ではなく
  **意味のある応答**を挟んで分割する
- 話者ラベルの整合: 「磯貝）」「阿部）」以外の話者を登場させない（ラベル表記ゆれ禁止）
