# 02. 技術選定書

ステータス: ドラフト（局長レビュー待ち）

## 1. 選定方針

「プラットフォームが変わっても TypeScript があれば何でもできる」を体感させることが
本教材の主目的（`00_企画概要.md`）。したがって技術選定の第一基準は
**フロントエンド・バックエンドを一貫して TypeScript で統一できるか**、
第二基準は **1つのコードベースで Web と モバイル（iOS/Android）の両方を
配信できるか** とする。

## 2. フロントエンド／モバイル配信方式の比較検討

局長から候補として挙がった2案を比較する。前提として、TanStack Start
（局長呼称: TanStack Starter）は **1つのフレームワークで「Native以外」＝
Web表示とサーバー機能（SSR・APIハンドラ等）を丸ごとカバーするフルスタック
フレームワーク**（Next.js相当の位置づけ）であることを踏まえる。

| 観点 | 案A: React Native + TanStack Start + NestJS | 案B: Capacitor + React（素のSPA）+ NestJS |
|---|---|---|
| 構成要素の数 | Native部分はRN、Web部分＋サーバー機能はTanStack Start、主バックエンドはNestJS ＝ **3つの技術要素の組み合わせ** | Capacitorが素のReact（WebのSPA）をそのままNativeへ包むため、**フレームワークはReact本体のみで完結**。主バックエンドはNestJSのみ |
| コードベースの統一度 | UI層（View/Text/Pressable等）がWeb版Reactと別物。**言語（TypeScript）は共通だが、コンポーネントは書き直しが必要** | UI層はブラウザ標準のReact（div/span/button）のまま。**Web版と全く同じコンポーネント・同じコードでWeb/iOS/Androidに配信できる** |
| フルスタックフレームワークの必要性 | Web版にSSR・サーバー機能が欲しいなら要（TanStack Start導入） | Capacitorの中身はただのクライアントSPAなので、SSRやサーバー機能を持つフルスタックフレームワークを導入する理由がない。データ・ビジネスロジックはNestJSに集約すれば足りる |
| 学習コストの積み上げ方 | `task-app`（Web/Next.js）からの知識の再利用度が低い（RNのコンポーネント層を作り直すため） | `task-app` で学んだReactコンポーネントの書き方・状態管理をほぼそのまま再利用できる。差分は「Capacitorのネイティブプラグイン呼び出し」のみに絞れる |
| ネイティブ機能へのアクセス | ネイティブAPIに直接アクセス（真のネイティブ体験） | Capacitorプラグイン経由でカメラ・プッシュ通知等にアクセス可能（ネイティブそのものではなく橋渡し） |
| 教材としての「TypeScript Everywhere」ストーリーの強さ | 「同じ言語ならどこでも書ける」を示すが、コード自体・技術要素数は増える | 「同じコードがどこでも動く」を最少構成で示せる。ストーリーとしてより強い |

### 決定: 案B（Capacitor + React〔素のSPA〕+ TanStack Router + NestJS。TanStack Startは不採用）を採用

**理由:**
1. 本教材の核心的な学習目標である「1つのコードベースで複数プラットフォームに配信する」を
   最も素直に体現できる
2. Capacitorのアプリはただのクライアント側SPAであり、SSR・サーバー機能を持つ
   TanStack Startを導入する理由がない。導入すれば学習コストが増えるだけで見返りが薄い
3. サーバー側の責務を全部NestJSに集約する、シンプルな役割分担ができる
   （Web/モバイル側＝画面表示のみ、NestJS側＝データとビジネスロジック）
4. `task-app` で習得したReactの知識をそのまま活かせるため、学習者はモバイル配信の
   差分（Capacitorのビルド・ネイティブプラグイン）に集中できる

**画面遷移の仕組みは別途必要 → TanStack Router（ルーター単体）に確定**
本教材は画面が12個ある（`03_基本設計書.md`）ため、クライアントサイド
ルーティングの仕組みは必要になる。不採用にしたのはTanStack **Start**
（SSR込みのフルスタックフレームワーク）であって、TanStack **Router**
（ルーター単体）はフロントエンドだけで完結して使える別物である。
Routerは型安全性が現行ルーターの中で最も強く、「TypeScript Everywhere」の
テーマに最も合うため、局長判断によりこちらを採用する（React Routerも
検討したが、型安全性の差でTanStack Routerを選んだ）。

**React Native は不採用にするが、捨てるわけではない。**
RNルートを採用する場合、Native部分はRNで作れても、Web版とサーバー機能を
カバーするにはTanStack Start等の別フレームワークが別途必要になり、
技術要素が増える（RN + TanStack Start + NestJS の3点セット）。
「真のネイティブUIとハイブリッド（Capacitor）の違い」を対比として学ぶ教材を、
本シリーズの後続教材として別途提案する（`09_教材シリーズロードマップ.md` 参照）。
そこでは React Native + TanStack Start（Web/サーバー側）+ NestJS という、
今回あえて採らなかった構成そのものを教材化する。

## 3. 技術スタック（確定案）

| 層 | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | React 19 + Vite + TypeScript（素のSPA、フルスタックフレームワークは使わない） | Next.jsやTanStack StartのようなSSR前提のフレームワークに依存しないクライアントSPA構成にすることで、Capacitorでのモバイル配信と両立させる（前作はNext.js SSRだったため、あえて構成を変えて別パターンを学ばせる） |
| ルーティング | TanStack Router（ルーター単体。TanStack Start＝フルスタック機能は使わない） | 型安全性（ルートパラメータ・検索パラメータまで型チェックされる）が現行ルーターの中で最も強く、「TypeScript Everywhere」という本シリーズのテーマに最も合致する。ルーター単体はクライアントサイドルーティングのみでSSR不要な素のSPA構成（Capacitor）にそのまま載る |
| モバイル配信 | Capacitor | 同一Reactコードベースを iOS/Android のネイティブシェルに封入 |
| UIコンポーネント | shadcn/ui + Tailwind CSS | 前作と同じ選定で学習の連続性を確保 |
| バックエンド | NestJS + TypeScript | Web/モバイル双方のクライアントに対する単一API。DIとモジュール構造を学べる（前作のtRPCとは異なるアーキテクチャパターンとして提示） |
| API方式 | REST（OpenAPI仕様書を`06_API設計書.md`で定義） | tRPCは前作で経験済みのため、あえて標準的なREST + OpenAPIを採用し、他社開発現場でも通用する設計知識を補う |
| DB | PostgreSQL + Prisma | 前作と同一。ORMの再利用性を確認しつつ、スキーマ設計は今回のドメイン（SNS）に合わせて新規に行う |
| リアルタイム通信 | NestJS WebSocket Gateway（Socket.IO） | 通知・タイムライン即時反映のため。前作にはなかった要素 |
| キャッシュ／レート制限 | Redis | フィード生成のキャッシュ、ログインAPIのレート制限に使用 |
| 非同期ジョブ | BullMQ（Redis backend） | 通知のファンアウト処理、画像のサムネイル生成を非同期化 |
| メディアストレージ | S3互換ストレージ（開発環境はMinIOでローカル代替） | 画像アップロードの実装パターンを学ぶ |
| 認証 | JWT（アクセストークン）+ リフレッシュトークン | 前作より一段深い認証パターン（トークンローテーション）を学ぶ |
| 学習者の開発環境 | Docker Compose（PostgreSQL / Redis / MinIO を1コマンドで起動） | 初心者にミドルウェアの個別インストールをさせない（Codex R1 M19対応）。構成の詳細は `04_詳細設計書.md` で定義 |
| テスト | Vitest（ユニット）+ Playwright（Web E2E） | 前作と同一ツール。モバイル（Capacitor）のネイティブ機能E2Eは対象外とし、Web版ビルドに対するE2Eで代替する（下記「既知の限界」参照） |

## 4. 既知の限界（教材として正直に明記する）

- Capacitorアプリのうち、真にネイティブでしかテストできない挙動（カメラ権限ダイアログ、
  実機ビルド固有の挙動等）は Playwright ではカバーできない（OSプッシュ通知はスコープ外のため
  試験対象にも含めない — Codex R2 MAJOR3対応）。本教材では
  「手動での実機確認手順」を`08_テスト計画書.md`に明記し、自動化の対象外と正直に扱う
- リアルタイム通知（WebSocket）の負荷試験・スケールアウト設計は対象外
  （非機能要件の「想定規模」を参照）
