# 02. 技術選定書

ステータス: ドラフト（局長レビュー待ち）

## 1. 選定方針

「プラットフォームが変わっても TypeScript があれば何でもできる」を体感させることが
本教材の主目的（`00_企画概要.md`）。したがって技術選定の第一基準は
**フロントエンド・バックエンドを一貫して TypeScript で統一できるか**、
第二基準は **1つのコードベースで Web と モバイル（iOS/Android）の両方を
配信できるか** とする。

## 2. フロントエンド／モバイル配信方式の比較検討

局長から候補として挙がった2案を比較する。

| 観点 | 案A: React Native + TanStack Router | 案B: Capacitor + React + TanStack Router |
|---|---|---|
| コードベースの統一度 | UI層（View/Text/Pressable等）がWeb版Reactと別物。**言語（TypeScript）は共通だが、コンポーネントは書き直しが必要** | UI層はブラウザ標準のReact（div/span/button）のまま。**Web版と全く同じコンポーネント・同じコードでWeb/iOS/Androidに配信できる** |
| ルーティング機構との相性 | ⚠️ TanStack Router は Browser History API / メモリ履歴を前提に設計されており、React Native の非DOM環境・独自ナビゲーションスタックとは設計思想が食い違う。React Native の標準は React Navigation または Expo Router。無理に組み合わせると教材として不自然なパターンを教えることになる | ✅ Capacitor は WebView に通常のWebアプリを表示する方式のため、TanStack Router はそのままブラウザと同じ動作をする。相性の問題が発生しない |
| 学習コストの積み上げ方 | `task-app`（Web/Next.js）からの知識の再利用度が低い（コンポーネント層を作り直すため） | `task-app` で学んだReactコンポーネントの書き方・状態管理をほぼそのまま再利用できる。差分は「Capacitorのネイティブプラグイン呼び出し」のみに絞れる |
| ネイティブ機能へのアクセス | ネイティブAPIに直接アクセス（真のネイティブ体験） | Capacitorプラグイン経由でカメラ・プッシュ通知等にアクセス可能（ネイティブそのものではなく橋渡し） |
| 教材としての「TypeScript Everywhere」ストーリーの強さ | 「同じ言語ならどこでも書ける」を示すが、コード自体は別物になる | 「同じコードがどこでも動く」を示せる。ストーリーとしてより強い |

### 決定: 案B（Capacitor + React + TanStack Router）を採用

**理由:**
1. 本教材の核心的な学習目標である「1つのコードベースで複数プラットフォームに配信する」を
   最も素直に体現できる
2. TanStack Router との技術的な相性の問題（案Aの⚠️）を回避できる
3. `task-app` で習得したReactの知識をそのまま活かせるため、学習者はモバイル配信の
   差分（Capacitorのビルド・ネイティブプラグイン）に集中できる

**補足: 「TanStack Router」と「TanStack Query」は別物**
TanStackという名前のライブラリ群には画面遷移担当の「TanStack Router」と、
データ取得・キャッシュ担当の「TanStack Query」があり、この2つは別物である。
TanStack QueryはWeb/React Nativeどちらでも普通に使われるプラットフォーム非依存の
ライブラリだが、TanStack Routerはブラウザの URL・戻る/進む履歴を前提にした
Web向けの仕組みであり、React Nativeでは使わない（React NativeはReact Navigation
または Expo Router を使う）。「TanStackはReact Nativeでもよく使われる」という
印象はQueryの話であり、Routerの話と混同しないよう注意する。

**React Native は不採用にするが、捨てるわけではない。**
「真のネイティブUIとハイブリッド（Capacitor）の違い」を対比として学ぶ教材を、
本シリーズの後続教材として別途提案する（`09_教材シリーズロードマップ.md` 参照）。
そこでは React Native + Expo Router（RN標準のルーター）という、
技術的に素直な組み合わせを採用する。

## 3. 技術スタック（確定案）

| 層 | 技術 | 選定理由 |
|---|---|---|
| フロントエンド | React 19 + Vite + TypeScript | Next.jsのSSRに依存しないクライアントSPA構成にすることで、Capacitorでのモバイル配信と両立させる（前作はNext.js SSRだったため、あえて構成を変えて別パターンを学ばせる） |
| ルーティング | TanStack Router | 型安全なルーティング。Web/Capacitor両対応 |
| モバイル配信 | Capacitor | 同一Reactコードベースを iOS/Android のネイティブシェルに封入 |
| UIコンポーネント | shadcn/ui + Tailwind CSS | 前作と同じ選定で学習の連続性を確保 |
| バックエンド | NestJS + TypeScript | Web/モバイル双方のクライアントに対する単一API。DIとモジュール構造を学べる（前作のtRPCとは異なるアーキテクチャパターンとして提示） |
| API方式 | REST（OpenAPI仕様書を`06_API設計書.md`で定義） | tRPCは前作で経験済みのため、あえて標準的なREST + OpenAPIを採用し、他社開発現場でも通用する設計知識を補う |
| DB | PostgreSQL + Prisma | 前作と同一。ORMの再利用性を確認しつつ、スキーマ設計は今回のドメイン（SNS）に合わせて新規に行う |
| リアルタイム通信 | NestJS WebSocket Gateway（Socket.IO） | 通知・タイムライン即時反映のため。前作にはなかった要素 |
| キャッシュ／レート制限 | Redis | フィード生成のキャッシュ、ログインAPIのレート制限に使用 |
| 非同期ジョブ | BullMQ（Redis backend） | 通知のファンアウト処理、画像のサムネイル生成を非同期化 |
| メディアストレージ | S3互換ストレージ（開発環境はMinIOでローカル代替） | 画像アップロードの実装パターンを学ぶ |
| 認証 | JWT（アクセストークン）+ リフレッシュトークン | 前作より一段深い認証パターン（トークンローテーション）を学ぶ |
| テスト | Vitest（ユニット）+ Playwright（Web E2E） | 前作と同一ツール。モバイル（Capacitor）のネイティブ機能E2Eは対象外とし、Web版ビルドに対するE2Eで代替する（下記「既知の限界」参照） |

## 4. 既知の限界（教材として正直に明記する）

- Capacitorアプリのうち、真にネイティブでしかテストできない挙動（プッシュ通知の実機受信、
  カメラ権限ダイアログ等）は Playwright ではカバーできない。本教材では
  「手動での実機確認手順」を`08_テスト計画書.md`に明記し、自動化の対象外と正直に扱う
- リアルタイム通知（WebSocket）の負荷試験・スケールアウト設計は対象外
  （非機能要件の「想定規模」を参照）
