## 1. 選定方針

「プラットフォームが変わっても TypeScript があれば何でもできる」を体感させることが
本教材の主目的（`00_企画概要.md`）。技術選定の基準を次の順に置く。

1. **一貫して TypeScript で書けるか**
2. **1つのコードベースで iOS / Android / Web を配信できるか**
3. **学習者が最初の1章で挫折しないか**（`11_ターゲット・ペルソナ・UX定義.md` 原則「3分で目に見える結果」）
4. **制作側が1教材で抱える技術要素が多すぎないか**

3 と 4 は 2026-07-26 の振り直しで追加した基準である。旧構成はこの2つを満たしていなかった。

## 2. モバイル配信方式の比較検討

### 比較表

| 観点 | 案A: Expo (React Native) | 案B: Capacitor + React SPA |
|---|---|---|
| 題材との相性 | モバイルアプリを作る道具。SNS はモバイルで使うもの | Web アプリをモバイル／デスクトップにも出す道具。**デスクトップ版 SNS に合理性が無いため、採用動機の半分が働かない** |
| 最初に画面が出るまで | Expo Go を入れて QR を読むだけで自分の実機に出る | Xcode / Android Studio のセットアップが要る。**旧 `15_カリキュラム骨子案.md` が「最大の挫折ポイント」と自認していた工程** |
| Web への配信 | Expo の web 出力で同一コードから配信できる（SDK 50 から Metro バンドラー、SDK 54/56 で first-class web support） | Vite ビルドをそのまま Web に出す |
| UI 層の書き方 | `View` / `Text` / `Pressable`。ブラウザの `div` とは別物 | ブラウザ標準の `div` / `span` / `button` |
| ネイティブ機能 | ネイティブ API に直接アクセス | プラグイン経由の橋渡し |
| ルーティング | Expo Router がファイルベースのルートを native と web で同一に回す | 別途ルーターの選定が要る |
| 技術要素の数 | Expo 1つ | Capacitor + ルーター + ビルドツール |

### 決定: 案A（Expo (React Native)）を採用

理由を重い順に書く。

1. **題材とプラットフォームを噛み合わせる**。SNS はモバイルで使うもので、デスクトップ版に
   合理性が無い。Capacitor の売りである「Web アプリをデスクトップにも出せる」が、
   この題材では価値を生まない
2. **最大の挫折ポイントが構造的に消える**。旧構成は Xcode / Android Studio のセットアップを
   自ら「最大の挫折ポイント」と書いていた。Expo Go は QR を読むだけで実機に出るため、
   この山ごと無くなる
3. **物語の順序が良くなる**。旧構成は「終盤でやっとスマホに入る」だった。新構成は
   **1章目から自分のスマホで動く**。原則「3分で目に見える結果」「毎章、見える変化1つ以上」が
   格段に作りやすくなる
4. **看板が強化される**。Expo 公式が「1つのコードベースで Android / iOS / Web」を掲げており、
   シリーズの看板「TypeScript Everywhere」とそのまま一致する
5. **振り直しの最安点である**。実装コードは1行も存在しない。前作 `task-app` の手戻り #8
   （MUI → Tailwind の移行）は執筆着手後に起きた事故で、そこと比べれば移行コストはゼロ

**UI 層が Web の React と別物になる点は、承知のうえで受け入れる。** 旧構成が
「同じコードがどこでも動く」を最少構成で示せると評価していた点は事実だが、
その代償として払っていたのが上記 1〜3 であり、教材としては割に合わない。

## 3. バックエンドの比較検討

### 決定: Supabase を採用し、NestJS は独立教材へ分離する

| 観点 | 案A: Supabase | 案B: NestJS + PostgreSQL/Prisma + Redis + BullMQ + MinIO |
|---|---|---|
| 学習者が触る要素 | Supabase 1つ（DB / 認証 / リアルタイム / ストレージが同居） | 5つ |
| 制作側の負担 | SNS の作り方を教えることに集中できる | **SNS に加えてサーバーフレームワークまで教える必要がある** |
| リリースの手間 | ホスティング済み | 自前で用意する |
| 「サーバーを自分で作る」学習 | **本教材からは消える** | 学べる |
| DB | PostgreSQL（Supabase の実体） | PostgreSQL |

理由:

1. **1教材に道具を詰め込みすぎていた**。SNS を作る学習と、サーバーフレームワークを学ぶ学習は
   別の目的であり、1本に同居させると分量と難易度の両方が跳ね上がる
2. **リアルタイムの重み付けを下げた**。旧構成は自前 WebSocket と BullMQ で通知の
   ファンアウトまで作る設計だったが、本教材で重視するのはネイティブ機能であり、
   リアルタイムはそこまで作り込まない。Supabase Realtime で足りる
3. **消える学習は捨てずに移す**。「サーバーを自分で作る」は
   `09_教材シリーズロードマップ.md` の NestJS 教材（第3弾）へ正式に位置づける

## 4. 技術スタック（確定案）

| 層 | 技術 | 選定理由 |
|---|---|---|
| クライアント | Expo (React Native) + TypeScript | §2 の決定。1つのコードベースで iOS / Android / Web |
| ルーティング | Expo Router | ファイルベース。native と web で同一のルート定義が回る |
| バックエンド | Supabase | PostgreSQL / 認証 / リアルタイム / ストレージが1つに揃う |
| DB | PostgreSQL（Supabase の実体） | `05_DB設計書.md` のテーブル定義がそのまま載る |
| 権限制御 | RLS（Row Level Security ＝ 行レベルセキュリティ） | 「誰がどの行を読み書きできるか」を DB 自身に守らせる。本教材で新たに教える中心概念の1つ |
| 認証 | Supabase Auth | メール確認は標準挙動。パスワード再発行は `resetPasswordForEmail` |
| リアルタイム | Supabase Realtime | 通知・タイムラインの即時反映 |
| メディア | Supabase Storage | 画像アップロード |
| ネイティブ機能 | Expo の各モジュール（カメラ等） | 局長方針「native の機能が簡単に作れればいい」に対応 |
| Web 配信 | Expo の web 出力 | 同一コードベースから Web を出す。看板の証明 |
| テスト | `08_テスト計画書.md` で確定（Phase 1） | 04 と 06 の確定が着手条件のため本書では確定しない |

## 5. 既知の限界（教材として正直に明記する）

| # | 限界 | 教材での扱い |
|---|---|---|
| R1 | モバイルでメール確認を成立させるにはディープリンク（メール内のリンクからアプリを開く仕組み）の実装が要る。「Supabase を使えばメール確認がタダで付く」わけではない | 難易度は上がるが実務で頻出する題材なので、正面から扱う |
| R2 | Supabase 標準のメール送信は1時間に2通までの制限がある。複数アカウントを作る演習（タイムライン・通知・フォローの章）が詰まる可能性がある | **カスタム SMTP の要否を捨て試作で実測してから確定する。現時点では未確定と明記する** |
| R3 | 無料枠は DB 500MB / RAM 500MB で、自動バックアップが無い | 学習用途では足りる。バックアップが無いことは教材内で制約として明示する |
| R4 | 「サーバーを自分で作る」学習が本教材から消える | `00_企画概要.md` の目的文を「シリーズ全体で満たす」形に書き換え、NestJS 教材（第3弾）へ位置づける |
| R5 | 実機でしか確認できない挙動（カメラ権限ダイアログ等）は自動テストでカバーできない | 手動での実機確認手順を `08_テスト計画書.md` に明記し、自動化の対象外と正直に扱う |

## 6. 旧構成から消えた決定・道具

振り直しにより、以下が不要になった。**道具が減ることは工程の軽量化そのものなので記録に残す。**

- **API 方式「REST + OpenAPI 文書先行」の決定が消滅**。Supabase はクライアント SDK 経由で
  DB を叩くため、自前 API の仕様書を正本に置く前提が成立しない
  → **`14_マスターロードマップ.md` Phase 2 の「OpenAPI 照合コンパレータ」も不要**
- 自前 JWT + リフレッシュトークンの実装が消滅（Supabase Auth が担う）
- Redis / BullMQ / MinIO / Docker Compose によるミドルウェア起動が消滅
- TanStack Router の選定が消滅（Expo Router が native と web の両方を担うため）
