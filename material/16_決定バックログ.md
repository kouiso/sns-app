# 16. 決定バックログ（実装前に決め切る事項の一元台帳）

ステータス: ドラフト（局長レビュー待ち）
役割: 実装（Phase 3 伴走）に入る前に決着が要る**全事項**を、誰が・いつ決めるかで
一覧化する。各文書に散らばっていた「Phase 1で確定」「局長判断」を1枚に集約し、
抜け漏れと「会話の中だけの決定」を防ぐ（`13_記録・進捗管理規約.md` §1: ファイルに
落ちて初めて決定 / §2 ADRと対になる**未決定側の正本**）。

## 凡例

- **決める人**: 自分たち（副長＋レビュー担当） / 局長
- **いつ**: P0=今この計画固めで / P1=詳細設計 / P2=道具整備 / P3=伴走 / P4=販売 / 後続=シリーズ2弾以降
- **状態**: 決定（本台帳で確定） / 先送り（＝工程上そこで決めるのが正しい。idleではない） / 局長確認

「先送り」と「idle（怠慢）」は違う。先送り項目には必ず決定タイミング（いつ）を付ける。
タイミングの無い先送りは禁止（＝実質の未決扱い）。C群にも「いつ」を必ず付す。

## A. 本台帳で確定した事項（自分たちで決定）

### A1. 未決定事項の管理方法
本書（16）を**未決定事項の唯一の正本**とする。散在記述は本書へ集約し、各文書は本書を参照する。

### A2. 登場人物名（磯貝／阿部）
Phase 3 開始まで**暫定名として確定**。一括置換できる設計は維持（12 §4）。変えたくなったら差し替える。

### A3. 「先送り」の運用
先送り項目には決定タイミングを必ず付す。無タイミングの先送りは未決扱いに落とす。

### A4. Phase 3 の実装主体と「初心者制約モード」 ★最重要
**問題**: 開発ログ（10 §5）は教材の対話・エラー体験の唯一の原料。AIが手癖で実装すると
記録される詰まりが「AI固有のハマり」になり、初心者が実際に踏む詰まりと別物になる。
大原則1/2（本来の開発フローをなぞる）の土台が空洞化する。

**決定**:
1. 実装の手を動かすのはAI（Codex/Claude）でよい。ただし **「初心者制約モード」** を課す。
2. 初心者制約モードの規則:
   - その章の教材で**まだ教えていない知識・道具を先取りして使わない**（未導入のライブラリ、
     未説明のCLIオプション、未学習の型テクニックを「知っているから」で使わない）
   - エラーが出たら**まずエラーメッセージだけを頼りに1手打つ**。その1手と結果を必ず記録する
   - 公式ドキュメント・エラーメッセージ・既に教材で教えた知識のみを一次情報とする
   - 内部知識で一発正解を書いた場合は、**そこは「詰まりなし」として記録しない**のではなく
     「AIが先回りしたため初心者の詰まりは未観測」と明記する（後述A5の検証で拾う）
3. 開発ログには **friction種別ラベル** を必ず付ける:
   - `beginner`（初心者が確実に踏む。教材の対話に採用する）
   - `ai-artifact`（AI固有・環境固有。教材には採用しない）
   - `unobserved`（AIが先回りして観測できなかった。A5のG6で埋める）
4. `ai-artifact` だけで構成された章は、対話素材が不足しているとみなしG3で警告する。

### A5. G6実走の実行主体＝知識隔離の担保 ★最重要
**問題**: G6（教材実走検証）の存在意義は「教材に書いていない暗黙の前提」の検出。
その章を書いた本人（または同一文脈のAI）が走らせると暗黙知で補完して必ずPASSし、
最も恐れている「実際にやったら詰まる教材」をゲートが素通しする。

**決定**:
1. G6実走は **執筆に関与していない、文脈ゼロの実行体**が行う。同一セッション・同一
   会話文脈での実走は**G6として無効**とする。
2. 実行体に渡してよい入力は **その章までの教材テキストと、章開始時点のスターターのみ**。
   設計書・開発ログ・実装リポジトリを見せてはいけない。
3. 実走中に実行体が**教材外の知識で補完して進んだ箇所**は、それ自体を欠落として記録する
   （「進めたからPASS」ではない）。
4. 実走の結果は10 §4のG6RUN受領証として台帳に残す（既存の受領証契約を流用）。
5. A4の `unobserved` ラベルが付いた箇所は、このG6で詰まるかどうかを**重点確認項目**として渡す。

### A6. G4のAIファミリー割当
**決定**: 生成側＝Claude、レビュー側＝別ファミリー（Codex/GPT系）、代替＝さらに別系統。
「別ファミリーであること」が要件であり、具体的なモデル名は入手可能性で変わるため
G4実行時に**実際に使ったファミリー名を記録する**ことをもって充足とする。
自分の生成物を同一ファミリーでレビューして合格にする経路は禁止。

### A7. 章別チェックポイント（詰まったときの復帰点）
**問題**: ペルソナB（独学者）は質問相手ゼロ。復帰手段が無いと1章の詰まりで完走不能になる。
一方これは前作#1「販売ZIPに完成品混入」の火元そのもの。

**決定**:
1. 章末スナップショットを**配る**（完走率を優先）。
2. ただし**手作業で作らない**。各章タグから機械生成する。
3. **教材本体とは別配布**にし、開始状態スターターへの混入検査（G0成果物）は従来どおり厳格に維持する。
   「配布物が2種類ある」ことを配布形式（B9）の設計前提に含める。
   **★ 2026-08-06 追記: この3項は「別配布」と言うだけで置き場を決めていない。**
   B9 を決めた側から見ると、置き場が決まらないと PDF 本文からスナップショットへの
   リンクが書けない（実測で、相対リンクは PDF 内で `localhost` に焼き付いて死ぬ）。
   **置き場は公開範囲と配布経路そのものなので局長判断とし、C7 として起票した。**
   A7 の決定自体は変えていない。また C3 で完成コードのリポジトリが公開になったため、
   配布は「本体＋スナップショット」の2系統ではなく**3系統**である（B9 決定の4項）。
4. スナップショットには「ここまでの完成コード」であることと、**先の章のコードを含まない**ことを機械検査する。

### A8. コード規約の凍結方針（G5の偽FAIL/偽PASS防止）
**決定**:
1. フォーマッタ＝Prettier（設定は原則デフォルト）、リンタ＝ESLint。
2. コード内コメントは**日本語**（教材の読者が日本語話者のため）。
3. **G5の機械diffは、フォーマッタ適用後の正規化テキストで比較する**。整形差だけでFAILさせない。
4. 具体の設定値（行幅・セミコロン等）はP1で確定し、確定後は伴走中に変更しない。
   変更が要る場合はADR＋全章のG5再実行をセットで行う。

### A9. テストコードをカリキュラムに含めるか
**決定**: **含める**（ただし最小限）。
- 理由: 実装PRのマージ条件がテスト緑（10 §4）である以上、著者リポジトリには全章テストが
  存在する。教材が一切教えないと学習者の手元と章タグのリポジトリが構造的に乖離し、
  大原則1（本来の開発フローをなぞる）と矛盾する。
- 範囲: 「テストを網羅的に書く」ではなく「**壊れたことに気づける最小のテスト**」を教える。
  E2E（Playwright）は主要動線1本に絞る。
- 章位置と分量はP1の章分割（B1）で確定する。

### A10. GitHub／CI基盤の決定タイミング
**決定**: **Phase 2開始までに用意する**（ゲート常設の前提のため。C3から「いつ」を確定）。
- ホスティング＝GitHub。**リポジトリは公開**（C3 で局長が2026-07-26に決定）。
- CI実行基盤は **GitHub Actions に確定**（public のため無料枠が使える）。
  Blacksmith は不要になった。
- ブランチ保護とPRマージ条件はゲート設計（10 §4）の前提なのでPhase 2で有効化する。
- **★ 2026-07-28 実測: 非公開だった間、GitHub Actions は動かなかった。**
  「支払いに問題があるためジョブを開始できない」と返り、失敗した実行は
  [run 30330642584](https://github.com/kouiso/sns-app/actions/runs/30330642584)（commit 4f45912）。
  非公開の Actions は無料枠に上限があるため。**枠を増やす選択は取らなかった。**
  **この失敗そのものは「public なら無料枠で走る」の証拠にならない**。
  「支払いに問題がある」は、無料枠を使い切ったことも、公開にすれば走ることも示さない。
- **★ 2026-07-28 実測（こちらが公開実行の証拠）: 公開へ切り替えたあと、
  同じワークフローが成功している。** 課金の設定は何も変えていない。実行の記録:

  | run | commit | 結果 |
  |---|---|---|
  | [30330748939](https://github.com/kouiso/sns-app/actions/runs/30330748939) | ead9efc | success |
  | [30333492333](https://github.com/kouiso/sns-app/actions/runs/30333492333) | a51cbe5 | success |
  | [30343068791](https://github.com/kouiso/sns-app/actions/runs/30343068791) | fa6e26c | success |

  よって「public なら無料枠で走る」は**実際に走らせて確かめた**。
  **公開そのものは C3 で 2026-07-26 に決定済み**であり、可否を問う論点は残っていない
  （2026-07-28 に公開へ切り替え済み）。C6（教材本文は別の非公開経路で配る）は
  公開と両立する話であって、公開を止める条件ではない。
- **ローカルで `npm run gate` を回して PR 本文へ結果を書く運用は、非公開だった期間の
  暫定措置であり、いまは要らない。** 合否は CI の実行結果で見る。
- **実装リポジトリが公開になる以上、教材本文は必ず別の非公開経路で配る**（C6 と連動）。

### B20 — トリガーは行だけ作り、プロフィールは初回ログイン後に本人が入れる

**決定**: `users` の `username` / `display_name` から NOT NULL を外し、`updated_at` に既定値を持たせる。
トリガーは id と日時だけを埋める。username と display_name はプロフィール設定画面で本人が入れる。

**なぜそうしないと壊れるか**: 登録画面で受け取るのはメールとパスワードだけ（01 FR1）なので、
トリガーが動く時点で username に入れる値が無い。NOT NULL のままだとトリガーの挿入が落ち、
**落ちると登録処理そのものが取り消される**。Supabase 自身が「トリガーが失敗すると
登録を止めうるので十分に検証すること」と警告しており、PostgreSQL の仕様としても
AFTER トリガーはエラーで操作全体を中断する。

**Supabase 公式の手順と同じ形である**ことも確認した。公式が公開しているプロフィール表は
username を含めて**主キー以外が全て NULL 可**であり、Expo 向けの公式チュートリアルでも
プロフィールは登録後の画面から入れている。

**利用者メタデータを信用しない**: Supabase は「登録時に渡す利用者メタデータは
**本人が後から書き換えられる**ので、権限の判断に使う場所ではない」と明記している。
username の一意性は DB の UNIQUE 制約で受け止め、違反をそのままアプリへ返す。
トリガーの中で重複させると「登録に失敗しました」としか出ず、原因が読めない。

詳細と波及先は `05_DB設計書.md` の users テーブルの節に書いた。

## B9 決定: 教材本文の配布形式（2026-08-06）

前提: 局長が **Vivliostyle を教材の組版に使う**と決めた（2026-08-06）。
この決定は覆さない。以下はその上で B9 に何が残るかを実測で詰めた結果である。
実測の全文は `decisions/D23_Vivliostyle採用の影響.md`。

### 選択肢がどう消えたか

- Vivliostyle が出せるのは **PDF / EPUB / webpub（静的 HTML 一式）** の3つだけ（実測）
- **ZIP は C6 で不採用**（局長回答: 「フォルダ共有なら差し替えが全員に届く」）
- **Web サイトは C6 で不要**（局長回答: 「サイト構築は不要」）→ webpub が落ちる
- 残るのは PDF と EPUB。**両方作るコストは出力先を変えたビルド1回分**（実測）

### 決定

1. **教材本文の正本は PDF。** 局長が受け取り、C6 の Drive フォルダ共有で配る対象はこれ。
2. **EPUB を同じソースから併産する。** ただし当面の役割は**機械検査用**である。
   理由: EPUB は ZIP + XHTML で原稿の構造（`<code>` / `<pre class="language-tsx">` /
   相対 `href`）を保つのに対し、**PDF はそれを失う**（バッククォートが消えて `src/` が裸になり、
   行の折り返しで文が分断されて grep が当たらない。実測）。
   パッケージのエントリ名と本文参照を照合する型の検査は EPUB になら移植できる。
   **EPUB を読者にも配るかは C6 の運用に属し、ここでは決めない**（B59 の検証が先）。
3. **webpub は使わない。**
4. **配布は3系統**である（旧記述の「2系統」を訂正）:
   教材本文＝PDF ／ 完成コード＝公開リポジトリ（C3）／ 章末スナップショット（A7）。
   `decisions/task-app資産棚卸し.md` が既に「本作は配布が3系統」と書いており、
   B9 の行だけが2系統のままだった。
5. **配布物のビルドは清潔な専用ディレクトリで行う**（13 §3 に規約化）。
   実測で、作業ディレクトリの PNG が EPUB へ全部同梱された。
6. **本文中の相対リンクを禁止する**（12 §1.1.1 に規約化）。
   実測で、相対リンクは PDF 内に `http://localhost:13000/vivliostyle/...` として焼き付き、
   読者の手元で確実に死ぬ。絶対 URL か章内アンカーだけを使う。
7. **組版の生成物は git 追跡しない**（13 §3 に規約化）。
