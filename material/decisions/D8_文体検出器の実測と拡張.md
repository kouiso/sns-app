## 1. prh の正規表現がどう扱われるか（実測）

辞書を書く前に prh の挙動を測った。3点、書き方が制約される。

**(a) フラグは書けない。`gmu` が強制で付く。**
`/[\u{1F000}-\u{1FAFF}]/u` と書くと、prh は `/.../` の形として認識せず文字列全体をエスケープして壊す:

```
SyntaxError: Error while loading rule 'prh': Invalid regular expression:
/\/\[\u\{1F000\}\-\u\{1FAFF\}\]\/u/gmu: Invalid Unicode escape
    at Object.addDefaultFlags (prototype-chapter/node_modules/prh/lib/utils/regexp.js:125:12)
```

`/u` を外して `\u{...}` だけにしても、prh は**フラグ無しで妥当性を検証してから** `gmu` を付け直すので、
検証段階で落ちる:

```
SyntaxError: Error while loading rule 'prh': Invalid regular expression:
/[\u{1F000}-\u{1FAFF}]/: Range out of order in character class
    at Object.parseRegExpString (prototype-chapter/node_modules/prh/lib/utils/regexp.js:95:12)
```

**(b) よって絵文字の面（BMP の外）はサロゲートペアでも `\u{...}` でも書けない。**
サロゲートペアの範囲 `[\uD83C-\uDBFF][\uDC00-\uDFFF]` はフラグ無し検証は通るが、
最終的に `u` が付くため文字列がコードポイント単位で走査され、1件も一致しない（実測: 🎉 🚀 が素通り）。
文字そのものを書いた `/[🀀-🫿]/` はフラグ無し検証で `Range out of order` になる。
**動いたのは `/[^\x00-￿]/`**。フラグ無しでは何にも一致しない（妥当性検証を通る）が、
`u` の下では BMP の外の全コードポイント＝絵文字の面に一致する。

**(c) `m` が付くので `$` は行末を指す。**これは有効に使える。
話者行の閉じ括弧に `$` を添えると、文中のインライン引用を巻き込まない:

```
probe.md: line 3  磯貝「実行する」ボタンを押します。   ← 一致しない
probe.md: line 5  磯貝「ここでボタンを押す」           ← 一致する（す」が行末）
```

12 §1.1 が「地の文は原則使わない。説明はすべて先生のセリフとして書く」と決めているので、
教材本文の文末はほぼ全部この形になる。常体の検出はここに乗せた。

## 5. check_tone.py と prh の照合

`scripts/curriculum-qa/check_tone.py`（138行・32パターン）の全パターンを1行ずつ並べた
`prh/testdata/check-tone-patterns.md`（47行）を両方に掛けた。

| | 陽性サンプル70行 | check_tone 照合サンプル47行 | 陰性サンプル |
|---|---|---|---|
| textlint（prh＋2preset） | 70 | 47 | 0件（誤検知なし） |
| check_tone.py | 22 | — | 0件（誤検知なし） |

**check_tone.py だけが拾って textlint が拾わない行は 0 行だった。**逆は 49 行ある。

check_tone.py が陽性サンプルで落とした主なものと、その理由:

- 関西弁の語尾が話者行で当たらない。`やで(?:[。！!？?\s]|$)` の境界に「」」が無く、
  12 §1.1 が定めた `磯貝「…やで」` の形では発火しない。「あかん」「ちゃう」「やんか」も同じ理由で素通りした
- 常体の動詞リストが `する｜作る｜動く｜なる｜学ぶ｜読む｜つなぐ｜開く` の8語固定で、
  「押す」「出た」に当たらない
- 誇大・情緒・絵文字・不採用スタック名のパターンを1本も持たない

### 決定 D8-3: prh 辞書を正とし、check_tone.py は移植しない

理由:

1. カバー範囲が包含関係にある（check_tone.py 固有の検出は 0 件）。両方を CI に置くと
   同じ行が2回報告されるだけで、判定は変わらない
2. check_tone.py の境界設計が本作の文体と合っていない。本作は
   12 §1.1 で「地の文は原則使わない。説明はすべて先生のセリフとして書く」と決めており、
   文末は「」」の直前に来る。check_tone.py はその境界を持たないので、移植するなら
   32パターン全部の境界を書き直すことになる。それは移植ではなく作り直しである
3. prh の辞書は G3 の実体である textlint の中で動く。検出器が2系統に分かれると、
   12 を改訂したときに直す場所が2つになる（前作#3 と同型の同期漏れの入口）

**この決定は 10:137-139 と 10:140 の衝突を、10:137-139 の側で解消する。**
ただし 10:140 の但し書き「前作は check_tone.py を持ったうえで、さらに27本を足している」は
別の話であり、本決定は**文体検出**についてのみ 1本で足りると言っている。
残り27本の要否は B31 の分類の対象で、本決定は触っていない。
10 と 12 の記述の直しは shared_edits に入れた。

重複の扱い（両方使う場合ではなく、preset と prh の重複）:

- 「することができます」「することは可能です」は preset-ja-technical-writing の
  `ja-no-redundant-expression` が担当する。prh 側は `(?<!する)` の否定後読みで「する」を外し、
  preset が拾えない「出すことができます」だけを担当する。**同じ行が2回報告されることはない**
  （陽性 line 71 は prh 1件、line 79 は preset 1件）

## 6. `@textlint-ja/preset-ai-writing` を CI の実行経路に入れる

### 実測: 設定キーは正しく、npm のパッケージ名が違っていた

キーの綴りを1文字間違えると文体ゲート全体が消える経路が実在する（D1-8 の fail open と同型）。

  が要るが、それは prh の守備範囲ではない。G3 の検査2（構造チェック）を作るときに合わせて決める
- **`prototype-chapter/.textlintrc.json` とルートの `.textlintrc.json` が同じでない。**
  ルート側だけが `no-mix-dearu-desumasu`（本文=ですます / リスト=である）と
  `filters.comments` を持つ。設定が2つある状態は D1-8 の「定数を1箇所に集約する」と
  同じ問題で、どちらを正にするかはルートの `package.json` が生える時（B2）に決まる。
  なお `no-mix-dearu-desumasu` は文書全体の比率で判定するので1行単位の常体検出には使えない
  （§2 で `である。` を拾ったのは である1 : ですます27 の比率による）。本作の常体検出は
  この rule ではなく prh の4ルールが担う
