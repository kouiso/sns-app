# 第1部 — D22: 16件表への追記規則

## 1. 決定

### [D22-1] 追記の判断者は受注側（副長＋レビュー担当）。局長承認は「対策が凍結物の改訂を伴うとき」だけ

- 行を足すかどうか、何行にするか、証拠として何を書くかは受注側が決める。
  根拠は `16_決定バックログ.md:11` の凡例（決める人＝自分たち〔副長＋レビュー担当〕／局長）で、
  13:86-88 は既に「発生したら同じ表に行を追加する」と決めており、**追記するか否かは決定済み**である。
  残っているのは誰がいつ判定するかだけなので、新しく局長判断を作らない。
- ただし**書いた本人のセルフ承認は禁止**。行を足すPRに、書いた本人以外のレビュー承認を要求する
  （13:99-100 が例外承認について定めている形と同じ）。
- **例外**: 追記行の「対策」列が、凍結物（スタック・文体スペック・章分割表）の改訂、
  または G0〜G6 のゲート構成そのものの新設・変更を要求する場合は、
  大原則4（10:55-57「凍結したものを変えるときは工程を巻き戻す」）の経路に乗せる。
  この場合は行の追加だけ先に済ませ、対策の実装は上流文書の改訂承認を待つ。
  **行の追加を対策の承認待ちにしない** — 13:88 の「対応表に載らない手戻りは
  『なかったこと』になるのが最悪の結末」は、まさに承認待ちの間に消えることを指している。

### [D22-2] 載せる基準は3条件の同時成立。1つでも欠けたら載せない

| # | 条件 | 判定の仕方 |
|---|---|---|
| 1 | **既に完了・凍結・承認したとみなしていた成果物または決定**を、後から作り直した・撤回した・やり直した | 「完了とみなしていた」ことの記録（PROGRESS の行、完了宣言、凍結の記録）を証拠として指せること |
| 2 | その作業が**現に発生した**（予測・懸念・「起きうる」ではない） | やり直しの現物（コミット・ファイル・記録）を指せること |
| 3 | **証拠がある**（ファイルパスと行番号、コミットSHA、記録の引用のいずれか） | 表の証拠欄に書けること |

条件1の根拠は、既存16行の全部がこの形をしていることである（前作 #1 の販売ZIP混入は
完成品を除いたはずのZIPを作り直し、#8 の MUI→Tailwind は凍結したスタックの変更、
#14 は導入完了とみなしたゲートの再導入）。定義を後から広げると、
16件表が「反省の一覧」に変質して 10:12-13 の「1件ずつ潰す形で工程を設計する」が成立しなくなる。

**載せないもの**（別の受け皿がある）:

- **まだ発生していない穴**（設計の不備・未決定）→ `16_決定バックログ.md`（A1: 未決定の唯一の正本）
- **ゲートの誤検知1件**→ 13:101-103 の回帰サンプル追加。繰り返し発生してゲート本体の
  設計を変える事態に至ったときに初めて条件1を満たす
- **外部起因の一過性の失敗**（依存の新リリースで実走が落ちた等）→ drift 台帳の分類(c) ITEM。
  ただし同じ原因で章の改訂を2回以上行ったら条件1を満たす
- **1つの根本原因の別の現れ方**→ 既存行に証拠を追記する（D22-4 の重複規則）

### [D22-3] 契機は4つ。うち1つは「発生時にその場で」

| # | 契機 | 誰が |
|---|---|---|
| 1 | **やり直しが発生したその場**（作り直しのPRを立てる時点、または撤回を記録する時点）。そのPRの中で同時に行を足す | 気づいた者が起票、レビューで確定 |
| 2 | **各フェーズ完了時のふりかえり**（13:83-85）。その期間に足した行番号の一覧、または「追記なし」を必ず書く | 副長 |
| 3 | **敵対レビュー・外部レビューの指摘が条件1を満たすと判定されたとき**。処置台帳（`material/reviews/`）に行き先として記録する | レビュー担当 |
| 4 | **ゲートの非常停止・期限切れ・完了条件の未達が確定したとき**（13:104-109、16 A3 の期限） | 副長 |

契機1を筆頭に置く理由: 13:83-85 のふりかえりだけを契機にすると、フェーズ完了時に
記憶から書き起こすことになり、10:353-354 が開発ログについて禁じた「後からまとめて書くと
美化されて嘘になる」と同じ形になる。**やり直しの現物があるうちに書く。**

契機2で「追記なし」を必ず書く理由は、10:260 の RUN 行が0件でも記録する理由と同じである。
書いていないのが「起きなかった」なのか「書き忘れた」なのかを、後から区別できないため。

### [D22-4] 表の様式 — 番号は連番・欠番なし・再利用禁止。取り下げは打ち消し線で残す

- 番号は 17 から連番。**削除も再利用もしない**（D1-3 で章IDについて決めたのと同じ理由。
  番号が外部から参照された後に別の中身が入ると、参照が黙って別物を指す）。
- 誤って載せた行は削除せず、`~~17~~` の形と取り下げ理由を残す。
  前例が同じリポジトリにある（`16_決定バックログ.md:308` が誤検出だった D2 を
  打ち消し線と理由つきで残している）。
- **重複の扱い**: 同じ根本原因の別の現れ方は行を分けず、既存行の証拠欄に追記する。
  分けると同じ対策が2行に重複し、どちらを潰せば閉じるのかが決まらなくなる。
  対策が別々に必要になったときだけ行を分ける。
- 表題と列見出しが「前作の」で始まったままだと、17行目以降で嘘になる。
  一般化する（shared_edits を見よ）。**列は4列のまま**にする。
  列を増やすと既存16行を全部書き直すことになり、13:42 の「1つの作業単位 = 1ブランチ = 1PR」で
  扱いにくい差分になる。出どころは証拠欄の先頭に書く。

### [D22-5] 「対策」列を空欄にしてよいのは、起票番号を書いた場合だけ

対策が未定でも行は足す（D22-1 の例外の趣旨）。ただし空欄は禁止で、
`16_決定バックログ.md` の B番号か `material/decisions/` の D番号を書く。
**Phase をまたいで未定のまま置かない** — 次のフェーズの完了条件の判定時に、
対策未定の行が残っていたらそのフェーズを完了と宣言しない。

理由: 16 A3 が「タイミングの無い先送りは禁止」を決めており、手戻り表の対策欄だけ
その規律の外に置く根拠が無い。

# 第2部 — D20: 受領証の実行主体と RUN行の再定義

## 3. 決定

### [D20-1] 「伴走フェーズのオーケストレーター」＝受注側の**副長**。走らせる責任者であって、実行主体ではない

- 語の実体は `16_決定バックログ.md:11` の凡例「決める人: 自分たち（**副長**＋レビュー担当）／局長」の
  副長である。10:261 と 14:150 の2箇所にしか現れず定義が無かったので、名前を固定する。
- 責任の範囲は3つ:
  1. RUN・G6RUN を**定刻に発行させる**（10:257 の「各教材PRマージ後および週1回」、
     14:150 の「各パート完了時＋月1回」）
  2. 受領証を `material/drift/台帳.md` へ**記録する**
  3. FAIL 由来 ITEM の**起票と処置追跡**（10:267-271）
- **実行主体ではない**ことを明示する。理由は「実行」の語が2つの意味で使われているため:
  - G6 の実走は 16 A5-1 により「執筆に関与していない、文脈ゼロの実行体」でなければならず、
    同一文脈での実走は G6 として無効である。オーケストレーターは執筆工程の内側にいるので、
    自分で走らせた時点で G6 が無効になる。
  - G4 の判定は 16 A6 により別ファミリーのAIで、発注と受領証の記入がオーケストレーターの側
    （`D15_G4受領証の様式と発注手順.md:148-155`）。
  - RUN（G5 スキャン）は機械実行なので、走らせるのは CI でよい。
    オーケストレーターの責任は「走ったことを台帳で証明できる状態にすること」である。
- **同時に1人**（1つの実行体）。複数人で持つと、走らなかったときに誰の不作為かが決まらない。
- 不在時の代行を置く必要があるが、指名するのは局長とする（14:142 が販売後の引き継ぎ先の
  指名を局長側に置いているのと同じ形）。**具体の代行者は本決定では決めない**（§5 U20-4）。

### [D20-2] RUN行の走査対象を、引用方式のもとで意味のある2つに定義し直す

旧定義（10:258-259）は「走査コミット範囲」＝章タグと HEAD の差分で、
G5 が照合方式だった頃の前提である。10:244-245 は旧方式の記述の生存範囲を
「N/A判定の考え方」と「後続章がコードを変えても後続章のPRを止めない原則」の2点に限定しており、
RUN 行はそこに入っていない。一方 14:128（工程の正本）は今も RUN 受領証の頻度網羅を要求する。

**RUN を廃止しない。** 廃止すると前作#3（実装変更が教材に1.5ヶ月未反映）の検知経路が消え、
監査の対応表（`制作前レディネス監査.md:315`）が D20 をその対策に置いていることと衝突する。
走査対象を、引用方式で**現に検知できないもの**に付け替える。

走査単位は章。章分割表（`material/17_章分割表.md`。D1-6）の生きている章（tombstone を除く）すべて。

| 走査対象 | 何を数えるか | なぜ embedmd では見えないか |
|---|---|---|
| **A** | その章の最新タグ（`chapter/<章ID>` または `chapter/<章ID>-r<K>`）時点の正本（`app/` + `supabase/`）と、HEAD の正本との差分のうち、**その章の教材が引用しているファイルに限ったもの**の行数 | 教材は `listings/<章ID>/`（タグ時点の正本の派生物。D1-5）から引用するので、HEAD の正本がいくら変わっても `embedmd -d` は緑のままになる |
| **B** | `listings/<章ID>/` の全ファイルの行のうち、その章の教材のどの引用範囲にも覆われていない行数 | 10:227-233 が実測つきで明言している。試作では `import` の2行が引用範囲の外にあり、`embedmd -d` は最後まで exit 0 を返し続けた |

記録する項目: 日時 / 走査した章ID一覧 / 走査した2点（最新タグ名と HEAD のコミットSHA） /
A の件数 / B の件数。**0件でも必ず記録する**（10:259-260 の「スキャンが実際に走った証明」は据え置き）。

**走査対象そのものが0件のときは FAIL**（D1-8-3 の共通規約）:
生きている章が0本、走査対象ファイルの集合が空、章分割表が読めない、いずれも非ゼロ終了。
0件を緑で返す経路は、監査が実測で再現した前作#10 の再生産経路そのものである
（`制作前レディネス監査.md:336-355`）。

検出した件数の**分類は既決の (a)(b)(c) をそのまま使う**（10:263-266）。分類の定義は決め直さない。
10:241 は「分類(a)(b)は引用方式では発生しない」と宣言しているので、この宣言が正しければ
A・B は常に0件になり、**RUN の0件記録がその宣言の裏付けになる**。
0件でない回が出たら、宣言が実測で否定されたことになるので、その時点で ADR を1本立てて分類の扱いを決める。
推測で「発生する／しない」を先に決めず、**宣言を検証し続ける仕掛けとして RUN を置き直す**。

契機（10:257「各教材PRマージ後および週1回」）は決め直さない。
ただし全章走査が教材PRごとに現実的かは実測が要る（§5 U20-1）。

### [D20-3] `material/drift/` の器は作る。Phase 3 の最初の実装PRより前に、README と台帳の実体を置く

- 置くもの: `material/drift/README.md`（行の様式。RUN行・G6RUN行・ITEM行・分類(a)(b)(c)・
  処置完了条件を 10:255-284 から転記せず**参照**する。二重管理を作らない）と
  `material/drift/台帳.md`（本体。1ファイル）。
- **「最初の RUN と同時に作る」では足りない。** 監査 `:276` はそう書いているが、
  D1-1 が `curriculum/README.md` を置く理由として挙げたのと同じ問題がある:
  ディレクトリが無い状態は「まだ RUN の時期ではない」と「RUN が走るはずなのに走っていない」を
  区別できない。実体を先に置けば、区別は「台帳に行が無い」という観測可能な事実になる。
- 台帳を1ファイルにする理由は D16-2 と同じ。分けると、その章が別経路で通過したときに
  古い行が残り続け、どちらが正本かが新しい未決になる。

### [D20-5] 教材軸の「改訂待ち〔乖離分類(b)〕」と「外部起因対応中〔乖離分類(c)〕」を1つに統合する

13:61-64 の教材軸は分類(b)と(c)をそれぞれ別の状態名として持っている。統合して
**「改訂待ち〔drift 台帳にその章の未処置 ITEM が1件以上ある〕」**の1状態にする。

理由:

- 分類の正本は台帳の ITEM 行（10:263-266）である。PROGRESS が同じ分類を再掲すると、
  ITEM の分類を直すたびに PROGRESS も直す必要が生じ、13:65-66 が禁じた
  「台帳更新を別作業にしない（別作業にした瞬間に乖離が始まる）」がそのまま起きる。
  片方だけ更新された状態は、どちらが正しいか外から判定できない。
- 10:241 が「分類(a)(b)は引用方式では発生しない」と宣言している以上、
  「改訂待ち〔乖離分類(b)〕」は**発生しないと宣言された状態の名前**になっている。
  分類名を状態名から外せば、宣言の当否と PROGRESS の書式が切り離される。
- 統合しても失われる情報は無い。章行から台帳を引けば分類が読める。

13:62-64 の「複数章・全体に係る場合は PROGRESS 冒頭に全体ブロック行を置く」は残す
（G6RUN-FAIL が複数章に及ぶのは分類(c)固有の性質であり、書式の話であって分類の再掲ではない）。

## 6. 見つけた矛盾（決め直さず報告のみ）

1. **10:241「分類(a)(b)は引用方式では発生しない」と D1-5 の組み合わせに穴がある。**
   D1-5 は `listings/<章ID>/` を「タグ時点の正本から機械生成される派生物」と定めた。
   すると正本（`app/` + `supabase/`）は後続章の実装で変わり続けるのに、
   `listings/<章ID>/` はタグ時点で固定される。教材は listings から引用するので `embedmd -d` は
   緑のままだが、**教材が教えた形と、公開リポジトリに置かれる完成コードは乖離していく**。
   これは 10:276-277 が定義する分類(b)「どの章も教えていない変更が過去章の記述を無効化している」
   そのものである。本決定は 10:241 を決め直さず、D20-2 で RUN を「宣言を検証し続ける仕掛け」として
   置き直した。宣言と D1-5 のどちらを直すかは受注側の判断が要る。

2. **10:15-17 の表題と列見出しが「前作の」で始まっているのに、13:86-88 は同じ表への追記を要求している。**
   17行目以降を足した時点で「前作の手戻り16件 → 対策の対応表」「前作で起きたこと（証拠）」は
   事実と食い違う。shared_edits で一般化を提案したが、10 §1 は局長承認の対象（10:378）なので、
   承認前に書式が変わることの扱いは統合役の判断に委ねる。

3. **10:378 の完了条件「16件対応表・大原則（4つ）・ゲート設計（G0〜G6）・開発ログ仕様に局長承認」と、
   13:86-88 の追記運用が緊張する。** 承認済みの表に受注側が行を足せるのかが書かれていない。
   D22-1 で「行の追加は受注側、対策が凍結物の改訂を伴う場合のみ上流承認」と線を引いたが、
   これは 10 §1 の承認の粒度についての解釈であり、局長が「表全体の承認」を意図している場合は
   食い違う。承認時に確認が要る。

4. **「実行」の語が 10:261 と 16 A5-1 で別の意味を持つ。**
   10:261 は「実行責任は伴走フェーズのオーケストレーター」、16:57-58 は
   「G6実走は執筆に関与していない、文脈ゼロの実行体が行う」。同じ「実行」でも、
   前者は発行責任、後者は実走主体である。D20-1 で分離したが、語そのものは 10 に残る。

5. **10:272-273 と 14:128 が Phase 3 完了条件を二重に持っている。** 現在は同文だが、
   14:4-6 が「工程の順序・開始条件の正本は本書」と定めているので、片方だけ直された日に
   どちらが正しいかが決まらない。10 側を 14 への参照に置き換えるかは本決定の範囲外。
