追記5 の結論（`道具検証の記録.md:688-690`）:
「同じ場所を3回塞いで3回とも抜けられたら、塞ぎ方ではなく設計を疑う。
『入力の中から合図を探す』形は、その入力が任意の文字列を含みうる限り必ず抜けられる。
合図は入力の外に置く。」

追記8 の結論（`:763-764`）:
「抜け道を『使いにくくする』のと『閉じる』のは別。
いま誰も使っていない出口なら、狭めるより閉じる方が確実で、しかも安い。」

追記8 は「免除している章は0件だから閉じた」（`:750-752`）という前提つきの措置であり、

G3 の例外は G5 と違って**誤検知が現に起こる**（13:101-103 が誤検知の運用を別に定めている）ので、
本決定は追記5 の結論（合図を外へ）を全面採用し、追記8 の結論は「承認を挟む形」の設計として引き取る。

## 1. 決定

### [D16-1] `<!-- quality-exception: 理由 -->` を廃止する。ゲート例外の合図は本文の中に一切置かない

13:98 の「該当箇所の直前に `<!-- quality-exception: 理由 -->` を書いて通す」を削除する。
教材本文（`curriculum/<章ID>.md`。D1-2）に書かれた文字列は、
どこに書かれていてもゲートの判定材料にしない。

理由: 同じ方式が捨て試作で3ラウンド連続で迂回された（`道具検証の記録.md:666-670` の表。
Round 15 コード例の中／理由を空にする、Round 16 `~~~` の囲み／空白3つ字下げした囲み、
Round 17 閉じ記号の後ろに文字がある囲み／空白4つ字下げのコード／引用ブロックの中）。
`:672-675` が原因を「解析の精度ではなく、免除の合図を章の本文の中に置いたことそのもの」と
特定している。本作の教材はコードを載せる文書であり（A9 でテストコードも載る。16:91-99）、
本文が任意の文字列を含みうる以上、この方式は必ず抜けられる。

廃止した記法が本文に残っていないかを検査する仕組みは**作らない**。
本文の中から文字列を探す検査は、教材がその記法を例として載せた瞬間に誤検知し、
その誤検知のためにまた例外が要る、という循環になる。
本文の文字列がゲートに一切影響しないことは免除簿の側（D16-2）が保証する。
代わりに G3 の検知テストに1本入れる: **旧記法を本文の地の文に書いても FAIL のままであること**
（`道具検証の記録.md:680-686` の表が同じ形の回帰検査を持っている）。

### [D16-2] 免除簿は `gate-exceptions.tsv`（リポジトリ直下）1本。読み取りは `scripts/curriculum-qa/gate_exceptions.py` に集約する

置き場の理由:

- `curriculum/` 配下に置けない。そこは文体ゲートの deny 対象であり（`.claude/hooks/material-writing-gate.sh:50,:57-61`）、
  かつ「合図を本文の外へ出す」を無効化する（教材本文の隣に置けば、本文を書く動作の中で書けてしまう）。
- `material/` 配下に置けない。そこは設計文書の置き場であって（D1-1 / `task-app資産棚卸し.md` §2）、
  免除簿は伴走中に毎章の PR で増減する運用データである。
- `dev-logs/`（D1-7）と同じく、リポジトリ直下に専用の場所を1つ持たせる。

1ファイルにする理由: `道具検証の記録.md:766-772`（追記9）が
「判定を章ごとから**簿を丸ごと**へ変えた」と結論している。章ごとに引く形だと、
その章が別経路で通過したときに対応する古い行が簿に残り続け、
「残ったまま誰も気づかず、その章から指示が消えた日に古い行が効き始める」。
章ごとにファイルを分けると同じ残留が起きるので、簿は1本にして全行を毎回検証する。

読み取りを1本に集約する理由は D1-6 の `chapter_table.py` と同じ。
パーサが複数あると「どちらの解釈が正しいか」が新しい未決になる。

### [D16-3] 免除簿の1行は6列の TSV。列は 章ID / 検査ID / ルールID / 上限件数 / 理由 / 申請PR

```
<章ID>	<検査ID>	<ルールID>	<上限件数>	<理由>	<申請PR番号>
```

- `#` で始まる行と空行はコメント。
- **行番号・文字位置は列に持たせない。** 本文を1行足すたびにズレ、
  ズレた先で黙って別の箇所を免除する（`道具検証の記録.md:696-701` の追記6 と同型の偽の緑）。
- **粒度は「その章の、その検査の、そのルール」**。これは免除としては粗いが、
  本文の位置に依存しない識別子はこれ以上細かくできない。
  粗さは「上限件数」列で抑える。
- **上限件数**（正の整数）は、その行が抑止してよい指摘の最大数。
  実際の抑止件数がこれを超えたら FAIL。1行で章全体の同一ルール違反を無制限に消すことを防ぐ。
- **理由**が空の行は FAIL（`道具検証の記録.md:726-728` の追記7 —
  「名前だけで外せると、理由を誰も書かないまま章がゲートから消える」。
  理由は人が読む決まりではなく、判定するコードが実際に見る場所に置く）。
- **承認者の列は置かない。** 理由は D16-4。

### [D16-4] 承認の記録は免除簿に書かせない。CI が GitHub の PR レビュー承認を直接見る

免除簿に「承認者: 局長」と書けるなら、書くのは行を足した本人である。
承認の合図を、承認されるべき入力（＝リポジトリの中身）の中に置くことになり、
D16-1 で否定したのと同じ形に戻る。

よって承認の判定材料もリポジトリの外に置く。CI（GitHub Actions。16:103 で確定）が
その PR のレビュー一覧を GitHub API で取り、次を要求する:

- その PR で **追加または変更された免除行が1行以上ある**とき、
  **PR 作成者以外のアカウントによる approve が1件以上**付いていること。無ければ FAIL。
- 既存行に触れていない PR には要求しない（毎 PR で再承認を求めない）。
- 「PR 作成者以外」の判定は CI 側で `reviewer != PR author` を自分で比較する。
  GitHub が自己 approve を拒否するかどうかの挙動に依存させない
  （依存させると、その挙動が変わった日に静かにセルフ承認が通る）。

これで 13:99-100 の「承認者の記録が必要／セルフ承認は禁止」が、
はじめて exit code で判定できる形になる（10:202「全部 exit code で合否」）。

### [D16-5] 件数上限（1章最大3件）は据え置き、数える機構を定義する

上限3件は 13:98 で既に決まっているので決め直さない。数え方を決める:

`gate_exceptions.py` が簿の全行を章IDでグループ化し、**章IDごとの行数が3を超えたら FAIL**。
検査IDごとではなく章ごとの合計で数える（13:98 が「1章につき最大3件」と書いているため）。

### [D16-6] 検査は「簿を丸ごと」。未使用の行は FAIL

`gate_exceptions.py` と G3 本体が満たす条件（いずれか1つでも破れば非ゼロ終了）:

1. 簿のパースに失敗した／指定した簿が読めない → ERROR で止める（追記7 の
   `道具検証の記録.md:730-731`「免除簿が読めないのは材料の問題なので 1 で止める」）。
2. 列数が6でない行、上限件数が正の整数でない行、理由が空の行がある。
3. 章IDが章分割表（`material/17_章分割表.md`。D1-6）に存在しない／tombstone 済み。
4. 検査ID・ルールIDが、その時点の G3 が実際に出しうる語彙に無い。
5. 章IDごとの行数が3を超える（D16-5）。
6. **実際の抑止件数が0の行がある**（残留行）。追記9 の `:768-770` が
   「その章に対応する古い行が簿に残り続ける」を残す設計の欠陥として挙げている。
   D1-8(3) の共通規約「対象はあっても実際に検査した件数が0なら FAIL」の同型。
7. 実際の抑止件数が、その行の上限件数を超える。
8. 免除行があるのに、その PR に D16-4 の承認が無い。

加えて、走らせるたびに**免除した章ID・検査ID・ルールID・抑止件数を必ず標準出力へ出す**
（`道具検証の記録.md:637,:686`「免除した章名を必ず出力する」。
機械が「何が正しい免除か」を決められない部分は、人が見て気づける形にとどめる）。

**簿が空（全部コメント）なのは正常であり FAIL にしない。** ここは
D1-8(3) の「走査対象0件は FAIL」の対象外で、免除簿は検査対象ではなく設定だからである。
実装上の注意も追記9 が実測で残している（`:774-777`）: 簿が全部コメント行だと
`grep -v` は非ゼロを返し、`set -euo pipefail` の下ではその場で落ちる。
`|| true` を付け、**異常経路だけでなく正常経路も走らせて確かめる**。

### [D16-7] 開発ログ存在は例外の適用対象から外す

13:92 の適用対象列挙から「開発ログ存在」を削る。

理由:

- 10:329-332 が「記録がない章は、対話のハマり場面を創作することになり
  内容の嘘（AI臭さの根源）に戻るため、開発ログの存在を G3 のチェック項目に含める」と、
  この検査の目的を「嘘を作らせないこと」と定めている。ここを例外で通すと、
  その章はハマり場面を創作して書くしかなくなり、検査を置いた目的がそのまま消える。
- 例外制度が要る理由は「誤検知」と「どうしても従えない正当な理由」の2つだが、
  この検査は D1-7 により `test -f dev-logs/<章ID>.md` の1行になる。
  ファイルが在るか無いかしか見ないので、誤検知が起きる余地が構造的に無い。
- 「その場では書けなかった」は正当な理由にならない。10:353-354 が
  「記録は実装のその場で書く（後からまとめて書くと『最初に疑ったこと』が
  美化されて嘘になる）」と決めており、後から書いた開発ログを通すために例外を使うのは
  その決定を迂回することになる。
- 開発ログが本当に書けない事態（章の実装が無い等）は、13:42 の
  「実装変更が無い章は N/A 証跡で代替」の経路で扱う話であり、G3 の例外ではない。

### [D16-8] 方針同期チェック（check_policy_sync.py）を例外の適用対象に加える

13:92 の列挙は「構造・文体・混入検査・開発ログ存在」の4つだが、
10:198-202 は G3 の項目に**方針同期チェック**を含めている（Codex R9 M2 で必須実行に昇格）。
13 §7 の列挙はこれを取りこぼしている（§4 に矛盾として記録）。

方針同期チェックは 13:76-78 のとおり「不採用スタック名の混入」を文字列で検査する。
教材本文が「Prisma は使わない」と説明する文脈でも当たるので、誤検知が現実に起こる。
誤検知が起こる検査には例外の経路が要る。よって適用対象に加える。

**D16-7 と D16-8 の結果、例外の適用対象は「構造・文体・混入検査・方針同期」の4つ**になる。
テスト・RLS 検証・実機確認・ビルド・累積証拠ゲート・G5・G6 に適用できないのは 13:93-96 のまま
（Codex R8 M3 対応）。
