### この実測から言えること

1. **監査本文と実測がズレている。** 監査 L341-345 は `check_step_time` / `check_why` /
   `check_step_ref` が「表示は ❌ だが exit=0」と記録しているが、ディレクトリ渡しでは
   3本とも **exit=2** を返した。ディレクトリ渡しに限れば、命名のズレは黙って通らない。
2. **0件緑が出るのはファイル直接渡しの経路で、しかも `dayNN` 命名でも出る。**
   `check_step_time` は B でも C でも `✅ 所要時間の合計 OK（0 ファイル）` exit=0 を返した。
   原因は命名ではない。`day_number()` が返す番号が `NO_TABLE_DAYS` に入っていると
   その file を黙って `continue` する構造（check_step_time.py:30, :88-89）で、
   章ID命名では `day_number()` が常に `None` を返すため**全ファイルが同じ経路で落ちる**。
3. したがって **`dayNN` 命名へ戻しても 0件緑は直らない。** 命名を前作へ合わせる理由が
   1つ消えた。直すべきは「対象0件・検査0件なら FAIL」という共通規約であり、これは
   命名と独立に要る（下の D1-8-3）。
4. `check_comprehension.py:163-172` の `curriculum_order_key()` は `day(\d+)_` に
   合致しないファイルを全部 `(0, name)` に落とす。章ID命名ではアルファベット順に
   並ぶため、「既出語かどうか」の判定順序が壊れる。**exit は 0 のまま**なので
   自己申告されない。命名を決めるなら、この関数は章分割表を読む形へ替える必要がある。
5. `check_quality.sh` は章ID命名を明示的に拒否する（exit=1）。これは黙って通らないので
   危険度は低い。棚卸し §4 で既に「配線し直す」に分類済み。

### 章IDが git タグとして成立するかの実測

`chapter/<章ID>` は git タグになる（10:152）。空の repo で確かめた。

```
git tag chapter/expo-first-screen          → 成功
git tag chapter/expo-first-screen（2回目） → fatal: tag ... already exists / rc=128
git tag chapter/Expo_First                 → 成功してしまう
git tag chapter/はじめの一歩               → 成功してしまう
```

廃止済み ID の再利用は **git 側が拒否する**（rc=128）。一方、大文字・アンダースコア・
日本語は git が受け付けてしまうので、止めるなら規約と機械検査の側に置くしかない。

## 1. 決定

### D1-1. 教材本文のディレクトリは `curriculum/` に確定する

暫定名をそのまま正式名にする。別名にしない。

理由:
- 既に4本のフックと棚卸し表が `curriculum/` 前提で書かれている
  （`.claude/hooks/material-writing-gate.sh:50, :57-61, :78`、
  `material/decisions/task-app資産棚卸し.md` §2 の表、10:103）。
  改名すると「4本のフックと本表を同じPRで直す」（棚卸し §2）作業が発生し、
  得られるものが無い。
- `material/` は使えない。本作の `material/` は設計文書（00〜16・PROGRESS・
  承認パッケージ）であり、前作の `material/30days-curriculum/` とは意味が違う
  （棚卸し §2）。ここを教材本文にすると文体ゲートが設計文書の編集を全部止める
  （棚卸し §2 の検知テスト #3 がその回帰検査にあたる）。
- 本作は「30日」形式ではない（15 §1 のパート A0〜E）ので、`30days-curriculum` は使えない。

**同じPRで `curriculum/README.md` を置き、ディレクトリを実在させる。**
現状フックは `[[ -d "$ROOT/curriculum" ]] || exit 0` で、ディレクトリが無い間は
不活性のまま外から区別できない（棚卸し §2 検知テスト #1 がこの挙動を仕様として固定している）。
ディレクトリを先に作れば「無い＝異常」に変わり、D1-8 の配線検査が意味を持つ。

### D1-2. 章ファイルは `curriculum/<章ID>.md`。連番を名前に入れない

- 章1本 = `curriculum/<章ID>.md` 1ファイル。ディレクトリ直下に平置きする。
- パートごとのサブディレクトリを作らない。
- 章以外の本文（目次・付録・パート扉など）は `curriculum/extra/` の下に置き、
  章ID規約の対象外とし、章分割表にも載せない。

理由:
- **連番を入れると並び替えのたびに全ファイルが動く。** 10:113-115 は章IDを
  「途中挿入・順序変更でも不変」と決めており、10:122-126 は伴走中の章の境界・順序の
  微調整を ADR 1本＋局長の1行承認で認めている。つまり並び替えは**起きる前提**である。
  ファイル名に順序を持たせると、並び替えのたびに `git mv` と本文中の相互参照の
  書き換えが要る。参照先の実在は `check_crossref.py` が見ているので、書き換え漏れは
  検査で落ちるが、落ちる回数だけ手戻りになる。
- **同じ文字列が5つの実体になるので、1回の grep で全部出る形にする。**
  `chapter/<章ID>` タグ（10:152）・`listings/<章ID>/`（10:218）・`snapshots/<章ID>/`
  （`prototype-chapter/tools/make-snapshot.sh:24`）に、本決定で
  `curriculum/<章ID>.md` と `dev-logs/<章ID>.md` が加わる。ファイル名に連番や
  タイトルを混ぜると、この5つが機械的に対応しなくなる。
- パートのサブディレクトリを作らない理由も同じで、章のパート所属は変わりうる
  （15 §1 は「リアルタイムの独立パートをやめ、必要な章に溶かす」と既に1度動かしている）。
  所属は章分割表の列で持つ。
- 直下の `.md` 集合が章分割表の章ID集合と一致することを機械検査できる形になる（D1-8-2）。

順序を知りたいときの唯一の情報源は章分割表（D1-6）である。ディレクトリを
`ls` して順序が分かる状態は捨てる。

### D1-3. 章IDの採番規則

| 項目 | 規則 |
|---|---|
| 文字種 | ASCII 英小文字・数字・ハイフンのみ。正規表現 `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` |
| 言語 | 英語 |
| 長さ | 3〜32 文字 |
| 連番 | **禁止**。末尾セグメントが純粋な数字（`-01` `-2` 等）のものを機械的に弾く |
| 一意性 | 章分割表の全行（tombstone 済みを含む）で一意 |
| tombstone 済み ID の再利用 | **禁止** |

理由:
- **英小文字 ASCII に限る**のは、同じ文字列が git タグ・ディレクトリ名・配布ZIPの
  エントリ名になるため。実測のとおり git は `chapter/Expo_First` も
  `chapter/はじめの一歩` も受け付けてしまう。制作環境は macOS
  （`prototype-chapter/dev-log.md:5` に `macOS arm64` の記録）で、既定のファイルシステムは
  大文字小文字を同一視する設定で作られるため、`Auth-Login` と `auth-login` は
  同じディレクトリになる。非ASCIIはZIPのエントリ名で環境依存になる。
  加えて利用者の他プロジェクトの規約が小文字ケバブケースである。
- **長さの上限 32** の根拠は実在の3件（`expo-first-screen` 17字 /
  `node-npm-setup` 14字 / `live-reload` 11字。`prototype-chapter/listings/` 配下）で、
  最長の倍に余裕を見た値。下限3は1〜2文字の略号が読めないため。
  これは実測に基づく数字ではなく運用の線引きなので、越える章が出たら上げてよい（D1-9 参照）。
- **連番禁止**は D1-2 と同じ理由。名前に順序を密輸入させない。
- **tombstone 済み ID の再利用禁止**は、10:118 が「旧タグは履歴として残す」と
  決めていることと直結する。実測のとおり `git tag` は同名タグの2回目を rc=128 で拒否する。
  つまり再利用を許すと 10:118 の運用が物理的に成立しない。あわせて、過去に配った
  `snapshots/<章ID>/` と別物が同じ名前になるため、A7 の「先の章のコードを含まないことを
  機械検査する」の照合先が曖昧になる。

命名の内容についての指針（規則ではない）: その章で**完成する状態**を指す名前にする。
`auth-login`（10:113 の例）、`expo-first-screen`、`live-reload` はいずれもこの形。
「何を学ぶか」ではなく「何ができた状態になるか」で付けると、章の分割・統合のときに
名前と中身のズレが出にくい。

### D1-4. 章IDの改名手続き（10 に存在しないので新設する）

**原則として章IDは改名しない。** 名前を変えたくなるのは中身が別の章になったときなので、
その場合は G1 のライフサイクル（10:116-121 の 分割 / 統合 / 廃止）で扱う。

例外として、**未着手章に限り**単純改名を認める。未着手の定義は 10:119-121 と同じ線引きにする:

> 実装PR未マージ **かつ** `chapter/<章ID>` タグ未付与 **かつ** 教材ドラフト未着手

手順（1PRで全部やる。分割してはいけない）:

1. ADR を1本書く（13 §2 の ADR。理由と旧ID・新IDを含める）
2. 章分割表の該当行の章IDを書き換え、`supersedes` 列に「旧ID → 新ID（rename）」を記録する
3. `curriculum/<旧>.md` → `curriculum/<新>.md`、`listings/<旧>/` → `listings/<新>/`、
   `dev-logs/<旧>.md` → `dev-logs/<新>.md` を同PRで `git mv` する
4. 旧IDがリポジトリ全体に残っていないことを確認する（章分割表の supersedes 列を除いて
   grep 0件。D1-8-2 の配線検査に含める）

着手済みの章は改名禁止。理由は 10:119-121 が分割・統合を未着手章に限った理由と同じで、
タグ・ゲート履歴・進捗の移管が定義できないため。着手済みの手直しは通常の改訂PR路線で行う。

### D1-5. `listings/<章ID>/` と B2「単一 Expo アプリ」の関係

B2（16:136）は「1リポジトリ・単一 Expo アプリ（`app/` = Expo Router の画面、
`supabase/` = マイグレーションと RLS ポリシー）」と決めている。10:218 は
「引用元は章ごとの実プロジェクト `listings/<章ID>/`」と決めている。両者の関係を
述べた記述はリポジトリに無い。次のように決める。

**正本は単一アプリ（`app/` + `supabase/`）。`listings/<章ID>/` はその章末状態から
機械生成される派生物であり、手で編集しない。**

```
app/ + supabase/            ← 正本。実装PRはここだけを触る
   │  章Nの実装PRをマージ → タグ chapter/<章ID>
   ↓  タグ時点の内容から生成（手編集禁止）
listings/<章ID>/            ← 教材が embedmd で引用する（G5）
   ↓  make-snapshot.sh
snapshots/<章ID>/           ← 読者へ配る章末スナップショット（A7）
```

- `listings/` は **git 追跡する**。理由: G5 はPR時点の検査であり、レビュアが引用元の
  差分を見られる必要がある。加えて、教材PRの差分に引用元の差分が並ぶ状態は
  前作#3（実装変更が教材に1.5ヶ月未反映）を人の目に晒す経路になる。
- 実装が後から変わった場合は、10 が既に持っている改訂タグ `chapter/<章ID>-rK` を打ち、
  そのタグから `listings/<章ID>/` を作り直し、`embedmd -w` で教材を追従させ、G5 を回す。
- `listings/<章ID>/` の内容が `chapter/<章ID>`（または最新の `-rK`）タグ時点の正本と
  一致することを機械検査する（新規。D1-8 で起票）。派生物を追跡する以上、
  ズレの検出が無いと「手で直された listings」が生まれる。

**`supabase/` の章ごとの分け方**: 分けない。各 `listings/<章ID>/` は
`supabase/` をその章末時点の状態で**丸ごと**持つ。

- マイグレーションは追記式なので、章Nの `supabase/migrations/` は章N+1 の前方一致になる。
  差分を取れば「その章で何を足したか」が出る。分割の設計が要らない。
- 1つの章が追加するマイグレーションは1ファイル以上とし、**ファイル名に章IDを含める**
  （`<timestamp>_<章ID>_<内容>.sql`）。どの章がどのポリシーを入れたかを grep で辿れる。
- RLS ポリシーを `listings/` と `snapshots/` から落とさない。B2 が
  「`supabase/` 配下のマイグレーション・RLS ポリシー・トリガー・Storage ポリシーは
  実行されるサーバー側のコードであり、本構成の認可の境界そのもの」と書いており、
  「レビュー・テスト・配布の対象から SQL を落とさない」と明記している（16:136）。
  `make-snapshot.sh:37-40` の EXCLUDES は再取得できるものと AI 向け指示ファイルだけを
  除いており、`supabase/` は入っていない。現状のままでよい。
- 10 §4 の実装PRマージ条件「DB スキーマまたは RLS ポリシーに触れた →
  他人の行を触ろうとして拒否されることを確かめた記録も必須」（10:158-161）は、
  章ごとの `listings/` ではなく正本に対して適用する。派生物に対して二重に要求しない。

**未決で残すもの**: 全章分の `listings/` を追跡したときのリポジトリ容量と生成時間。
測り方は D1-9 に書いた。閾値を超えるなら「追跡」から「CI で生成」へ切り替える判断になるが、
その数字が無いうちに決めない。

### D1-6. 章分割表の正本は `material/18_章分割表.md`

- 場所が `material/` なのは、これが設計文書だからである（G1 で局長承認して凍結する
  対象。10:122）。教材本文ではないので文体ゲートの対象にならないのが正しい。
- **番号は 18**（**2026-08-09 訂正。当初は 17 で予約していた**）。
  2026-08-08 の文体正本の作業が `material/17_文体正本の実測.md` を先に main へ入れたため、
  17 が二重に予約された状態になった。**まだ実在していない側（章分割表）を動かす**方が
  安く済むので、こちらを 18 へずらした。ファイルの改名は発生していない（参照の書き換えのみ）。
  13 §4 の対象文書番号は現在「00〜15」で既に PROGRESS とズレており（監査 D0 の表に既出）、
  そこを直すときに 18 まで含める。
- **機械可読の別ファイル（YAML 等）を作らない。** 二重管理になり、どちらが正本かの
  問題が増える。読み取りは `scripts/curriculum-qa/chapter_table.py` 1本に集約し、
  他の検査はこれを import する。パース失敗と 0 行はどちらも非ゼロ終了にする（fail closed）。
- **★ 2026-08-06 追記: 組版の `vivliostyle.config.js` は D1-5 と同型の派生物である。**
  **この D1-6 は書き換えない。** Vivliostyle は複数ファイルを直接引数に取れず
  （実測: `too many arguments`）、`entry` の省略も exit 1 なので、1冊にするには
  `entry` 配列に章の順序を書くことになる。素直に手書きすると
  「`並び順` 列だけが順序の情報源」が破れるが、**D1-6 が禁じているのは
  「章分割表の第二の正本を作ること」であって、正本から生成される派生物ではない。**
  `listings/<章ID>/` を「タグ時点の正本から機械生成される派生物・手編集禁止・git 追跡」と
  定めた D1-5 の枠がそのまま使える。
  よって `vivliostyle.config.js` は **`18_章分割表.md` から `chapter_table.py` 経由で
  機械生成される派生物とし、手編集を禁止する。**
  config は素の JS なので外部データから `entry` を生成できることは実測済み
  （`decisions/D23_Vivliostyle採用の影響.md` §1-1）。
  生成器と「生成物が章分割表と一致すること」の機械検査が新規に要る（16 B56）。
  **18 がまだ存在しない**ので実装は 18 の作成後になる。

### D1-7. 開発ログは `dev-logs/<章ID>.md`。1章1ファイル

- `curriculum/` の中に置かない。理由: `curriculum/` 配下は文体ゲートが
  スキル読み込みなしの書き込みを deny する。一方 10:353-354 は開発ログを
  「実装の**その場で**書く（後からまとめて書くと『最初に疑ったこと』が美化されて嘘になる）」
  と要求している。書く前にスキル読み込みを挟ませると、この要求と正面から衝突する。
  さらに開発ログはエラーの全文コピー（10:338）を含むので、12 の文体規則を当てる対象ではない。
- `material/` の中にも置かない。設計文書ではないため。
- 1章1ファイルにする理由: G3 の5検査目「開発ログの存在確認」（10:201）が
  `test -f dev-logs/<章ID>.md` の1行で書ける。現状の `prototype-chapter/dev-log.md` は
  2章分（`expo-first-screen` と `live-reload`）を1ファイルにまとめており、
  章と1対1でないため存在確認を機械化できない。
- 見出しは 10:335 のテンプレートどおり `## 章N 開発ログ` ではなく
  `# 開発ログ — 章 \`<章ID>\`` とする（`prototype-chapter/dev-log.md:1` が既にこの形）。
  章番号は動くが章IDは動かないため。10 §5 のテンプレートの1行目を直す（shared_edits）。

### D1-8. fail open を閉じる案（実装はしない。案と起票まで）

現状: `.claude/hooks/material-writing-gate.sh:50` の
`[[ -d "$ROOT/curriculum" ]] || exit 0` は、ディレクトリ名がズレると黙って不活性になり、
正常時と外から区別できない。3点の組み合わせで塞ぐ。

**8-1. パス定数を1箇所にする。**
`.claude/hooks/curriculum-path`（中身は `curriculum` の1行）を唯一の定義とし、
フック4本はこれを読む。フックの中に文字列 `curriculum` を直接書かない。
定数が1つなら、ズレは「定数と現物の不一致」という1種類の事象に縮む。

**8-2. 配線検査 `scripts/check-gate-wiring.sh` を新設し、CI 必須にする。**
次のいずれかで非ゼロ終了する:

- (a) 定数の指すディレクトリが存在しない
- (b) そのディレクトリ直下の `.md` の集合が、章分割表の（tombstone を除く）章ID集合と一致しない
- (c) `listings/` `snapshots/` `dev-logs/` に、章分割表に無いIDのエントリがある／表にあるのに無い
- (d) フック・検査スクリプト・`gates.yml` に、定数を経由しないハードコードされた
  `curriculum/` がある
- (e) tombstone 済み章IDが、章分割表の supersedes 列以外の場所に残っている（D1-4 手順4）

これで「名前がズレたら黙って不活性」が「CI が赤」に変わる。10:198-202 が
「全部 exit code で合否（AI主観の合格判定は禁止）」と定めている土俵に、
ゲートの配線そのものを乗せる。

**8-3. 検査スクリプトの共通規約「対象0件・検査0件は FAIL」。**
本書 §0 の実測のとおり、`check_step_time` は対象ファイルを1本受け取りながら
`✅ 所要時間の合計 OK（0 ファイル）` exit=0 を返した。これは命名と独立の欠陥で、
`dayNN` へ戻しても直らない。規約として次を課す:

- 走査対象が0件なら非ゼロ終了
- 対象はあるが**実際に検査した件数が0**なら非ゼロ終了（`✅ …（0 ファイル）`
  `（0 個）` の類を緑にしない）
- 「この章は対象外」を認める場合は、その理由を章分割表の列か明示の除外リストから読み、
  除外した件数を出力に出す

これは B31（前作28本の分類）の作業に含める。`check_step_time.py` の `NO_TABLE_DAYS`
のような「番号で暗黙に免除する」実装は、章ID命名では全ファイルを免除するので作り直す。

**8-4. 命名に依存している検査の書き換え方針。**
`day(\d{2})` で順序を得ている検査（`check_step_time` `check_step_ref`
`check_procedure_order` `check_crossref` `check_comprehension` `curriculum_blocks`
`check_scaffold_curriculum_alignment` `gen_procedure_map`）は、
`chapter_table.py` から並び順を得る形へ替える。glob を `day[0-9][0-9]_*.md` から
`*.md` へ替えるだけでは、§0 の 4 で示した `check_comprehension` の順序破壊
（exit 0 のまま静かに壊れる）が残る。

### D1-9. 上限32文字の運用

D1-3 の 32 文字は実測ではなく線引きなので、越える章が出たら章分割表の凍結前に上げてよい。
上げるときは配線検査（8-2）の閾値も同じPRで直す。既存IDの改名は伴わない。
