# 保存・復帰APIと権限の具体案

状態: 2026-10-05に版3（v7＋API補足＋B回復案）が選択された。未実装・未実測。不存在keyの本人明示終了の扱いだけはB回復案で置き換えた（同ディレクトリの adoption-receipt.md）。候補v7 WREC-01の不足を埋める比較案であり、既存API名/SQL/schemaではない。原03/05→06→08の確定順序と、ユーザーの設計先行指示を保持する。関数名・物理テーブル名をここで既存契約として確定しない。

## 学習者がすること

入力画面を開くだけでは予約しない。本人が保存を選んだ時に入力を固定し、その操作を登録する。登録が確認できた元のforeground要求だけ保存へ進む。一度でも登録不明・中断へ遷移した要求は、後着した登録成功応答だけでは保存へ進まない。本人の明示続行で同key/input/owner/typeとlock内stateを再確認する。返答が不明になったら、同じ操作の結果を確認する。入力が残っていれば本人が同じ内容で続行でき、入力がなくてもserverで既存reservedを確認できれば、本人は当該操作を終了する選択ができる。登録不明のまま入力を失いserverでは不存在でも、操作のkeyと採用契約版のcontextが手元に残っていれば、本人が終了を明示した操作は閉じる（cancel-before-registration）（B回復案。最小identity保持/旧writer失効/quota上限が条件。同ディレクトリの adoption-receipt.md）。入力なしの登録再試行はしない。不在readだけでは閉じず、未保存確定ともしない。keyやcontextまで失った場合の回復は未設計で、その場合は新保存の停止を維持する。版3の採用は現案を実装可能にしない。次の新しい保存は、前の操作の終了と確認がそろってから許可する。通信復帰・再起動で自動送信しない。

## 共通入力と信頼境界

- projectは接続先の採用project identity、ownerは通常Authで検証した本人。clientに任意ownerを指定させて権限を付与しない。confirmation/recovery用途を通常保存へ混ぜず、確認前の全書込制限を保持する。
- 操作のidentityはproject/owner/type/key。typeはpost_saveまたはprofile_save。keyは新submit時に一度作り、返答不明の再要求では変更しない。keyは複数端末・再install・記録喪失をまたぐ十分な一意性を持つopaque値とし、再利用しない。serverは採用した長さ/形式を検証する。具体生成形式は原採否へ残す。衝突疑いは既存操作として安全停止し、新操作成功とはしない。対象schema/入力契約版を記録する。
- 登録時に本文/画像参照/プロフィール対象/revision等の比較入力を固定する。serverが正規化する範囲と比較bytes規則を版で特定し、serverは検証済み入力から比較identityを計算する。clientのdigest申告だけを信頼しない。秘密credential/tokenは含めない。
- 同keyの再送で比較入力が違えば入力不一致として保存しない。既存操作のstateを変更/閉鎖せず、元操作の結果確認へ戻す。key衝突と確定拒否によるclosed_unsavedを混同しない。
- 権限不足、Auth失効、通信不明は非terminal。API応答のエラーなし、1行更新、現在値一致だけをtrusted terminalにしない。

## 6つの論理操作

以下は論理操作であり、実装済みRPC/エンドポイント名ではない。採用後に引数/schema/grantと原画面を同じPRで具体化する。

| 操作 | client入力 | serverの結果と画面 |
| --- | --- | --- |
| 新操作の登録 | type/key/入力契約版/固定入力と画像・対象revision | ownerの未確認操作をserverで判定し、新key admissionとreserved登録を同取引で確定。同じkeyが既存なら比較identityを検証し既存stateを返す。別の未確認操作があれば登録しない。通信不明は同key登録結果確認へ。一度不明/中断へ入った後着応答では自動保存せず、本人の明示続行が必要 |
| 当該操作の確認 | type/key | 本人の当該stateとtrusted terminal参照を返す。不存在はclosureでない。legacy/契約版不明も未保存確定ではない |
| 同操作の保存 | type/key/元比較identity、固定入力が必要な採用方式では同じ固定入力（第一候補では再送payloadをmutationに使わない） | lock下でstateを再読取。terminalは再実行せず既存結果。reservedだけ入力一致と全保存権限/制約を確認しDB mutationとsuccess receiptを同取引でcommit |
| 当該操作を終了 | type/key/本人の明示終了選択 | 入力保持は不要。既存reservedならclosed_unsaved(reason=user_cancelled)をcommit。success/closedは既存terminal。既知採用WREC keyが不存在なら、本人の明示終了でcancel-before-registrationのclosed_unsaved(reason=user_cancelled)を閉鎖専用recordとserver生成immutable receiptで同取引commitする（B回復案。最小identity保持/旧writer失効/quota上限が条件。同ディレクトリの adoption-receipt.md）。legacy/契約版不明/key不明へは新closureを作らない |
| 終了結果の確認済み記録 | type/key/観測済みsuccess/closedのserver生成immutable receipt identity | 結果を実際に表示できた後の本人の明示「確認しました」操作だけ確認済みにする。受信/描画前のackや一括ackは送らない。successとclosed双方が対象。reservedは対象外。terminal identity不一致なら記録しない。再送は同じ確認記録を返す |
| 本人の未確認履歴取得 | 許可されたページcursor/取得契約版 | 本人のreservedと未確認terminalを発見できる履歴を返す。ページをまたぐ変更検出/再取得条件を示し、空ページだけで網羅性を宣言しない。既知terminalの表示は履歴失敗で隠さない |

確定保存拒否は、mutationをcommitしないことと当該reserved→closed_unsaved(reason=rejected)のcommit確認がそろった場合だけterminalとする。statementエラーで取引全体がabortしたとき、closureが残ったとは扱わない。閉鎖記録を改めて同lockで試みる場合も先にstateを読み、既にsuccessならその結果を優先する。closure返答不明はpending継続。画像bytesはDB取引外で、upload成功/存在/回収の結果を別に持つ。

## 固定payloadと画像bindingの第一候補

第一候補はserverが登録時に検証したcanonical payloadを保存し、mutationはそのpayloadだけを読む方式。canonicalization版・入力revision・比較identityをreservedへ束縛し、clientの再送値で上書きしない。同key登録再送は元入力との一致検査だけに用いる。代案はserverが比較identityを保持し、保存時のexact再送payloadをserverで正規化・一致検査して使う方式。この代案は入力喪失で続行不能になること、server保持量との比較を明記し、両方式を混ぜない。server保持候補でも、登録不明/不存在/入力喪失の入力を回復可能とはしない。key/contextが残る場合の出口は本人の明示終了による閉鎖だけで（B回復案）、失った入力は復元しない。

画像はowner/project/operation/image identity、内容hash、実bytes数、検証済みMIME、採用保存領域のimmutable object identityに束縛する。clientの任意URL/可変pathだけを参照として採用しない。immutable versionを提供できない方式なら、採用server経路で固定された専用objectへ移し、上書き・別owner差替え・通常client直接削除を防ぐ権限と回収規律が必要。その方式のAPI・費用・保持・原FR3受入は未採用。

画像bytes準備/内容検証/存在確認はDB取引前に行い、operation-boundの保持権が確立したobjectだけをDB mutationへ渡す。回収workerもowner→operationの同lockを取り、reservedまたは参照中のsuccess画像を回収しない。DB取引内では束縛されたidentity/保持権を再読取する。外部Storageのbytes観測をDB atomicityに含めない。外部障害や採用権限外の管理削除は別観測で、DB successを取り消さず「保存済み、画像を表示できない」結果へ。bytes準備/保持権が信頼確認できない間は画像保存を開始せずpending/確認へ。Storage保持を設計・実測できない方式では、この画像経路を実装可能と判定しない。

### 画像を含むsubmitのphase順序

第一候補の順序は次の一つに固定する。画像なしは画像準備だけ不要で、予約と保存の順序は同じ。

1. 本人submitで入力/画像bytes/revisionを固定し、静的validationを通してopaque keyを生成。画像資源準備を始める前に本人の当該contextを保持する。入力画面を開いた時点では実行しない。
2. owner/project/keyに結び付く専用の一時objectを準備する。準備経路が実bytes/内容identityを検証し、上書き不可のobject identityを返す。これはStorage資源準備であり、WREC reservedを作る操作ではない。
3. 登録transactionはowner lock下で、画像準備recordの本人/内容/存在確認証拠/有効性と未確認集合を検査し、canonical payload・画像束縛/保持権・reservedを同commitで記録する。保持権はDB内の準備recordを束縛して確定し、transaction内で外部uploadをしない。
4. 登録成立を信頼確認した元foregroundだけ、bytes準備と保持権を再確認して同key保存へ。一度登録不明/中断へ入ったら本人明示続行が必要。
5. 画像準備だけで登録されなかったobjectは、server側の回収判定でowner lock→準備recordの順に排他し、登録・保持権・利用中なしを確認して回収対象化する。回収対象化後の遅延登録はそのobjectを束縛できない。回収状態の変更を登録と同じ排他へ統一する。
6. 登録返答不明ではclientがobjectを削除しない。serverで当該reserved/terminal/準備recordを照合する。確認前の単なるTTLやclient不存在readで回収しない。回収/登録順序、bytes障害、課金/孤児化の実測が成立しない場合、この方式は未採用のまま。

画像資源準備recordはWREC stateを増やさず、operationの予約成立を意味しない。準備record自身の物理schema/権限・cleanup制御は原05/06へ追加設計対象として返す。保存/回収の遅延要求が同じ画像を再利用/上書きできないことを実測する。

## closed_unsaved(reason=rejected)の有限分類候補

この候補で閉じてよいのは、通常本人の同reservedと固定入力を確認し、採用済み契約によってDB内で確定した次の3分類だけ。

登録前に構造/型/文字数/枚数/本文・引用・返信の静的組合せ/canonicalization版を検証し、静的不成立ならreservedを作らない。この予約前拒否をclosed receiptとして返さない。既存同keyがあれば先に本人identityとstateを確認し、不正な再送で元操作を閉じない。登録後に変わり得る次の3分類だけをmutation時のrejected候補にする。

1. 対象revision不一致による確定競合。
2. 表示ID等の採用UNIQUE条件の確定競合。
3. 対象/参照親の確定削除・不在により、その固定操作が許可されないことの確認。

各分類でもmutationなし＋closure commit＋immutable receiptを確認する。分類は採用版で固定し、DB例外を一律分類しない。Auth/用途/owner不一致、権限やRLS設定の不整合、lock timeout、connection loss、transaction abort、Storage存在不明、未知exceptionは非terminal。ownerや入力不一致の要求で元reservedを閉じない。有限分類へ対応づける根拠がなければpendingを維持する。

success/closed receipt identityはserverが当該terminal commitに作る不変の識別で、project/owner/type/key/state/reason/対象結果を束縛する。別操作のreceiptや現在値だけでackできない。端末が結果を受信→表示→本人の確認選択→ack commitと進み、各境界のcrashで未確認を失わない。表示内容には当該操作の結果と、現在値/画像の別読取が未成立ならその状態を含める。単に通信が成功したという表示では確認済みにしない。

## 排他方式の第一比較案

owner/project単位のledger lock→type/keyのoperation lockの順に統一する。新登録・同key登録再試行・保存・終了・確認済み記録・保持/消去の全writerがこの順序を守る。operation lockを先に保持してowner lockを後から取得する経路を作らない。これは未実測の第一比較案で、owner単位の待機時間・ロック競合・学習分量を測って採否する。

新登録はclient履歴の読み取り結果を許可証にせず、owner lock下の同じDB取引でserverの未確認集合と新key登録を判定する。post_saveとprofile_saveは同じowner admissionを共有する。reservedになった自身の同key続行は、新key admissionを再適用せず当該stateを確認する。これにより自身のreservedで続行が止まる条件を避ける。

saveと終了が競合したら同順序でlockを取得した側がstateを確定し、後続はterminalを再読取する。DB mutationとsuccess receiptは同commit。Storage uploadや外部通信をDB lock保持中に行わない。DB完了後の画面表示・現在値取得は別で、現在値を読めなくてもtrusted successを取り消さない。

全通常writerにこの入口を適用する。直接DMLを維持するなら同じ規律をDBで強制できる証拠が必要。できなければ通常権限の直接mutationを閉じ、限定された採用操作だけを公開する。どちらも未採用。通常clientにowner変更/terminal改変/receipt作成/全列更新を許可しない。privilegedな観測・移行経路の権限と監査は通常保存と区別し、secret/service_roleをclientへ渡さない。

## 履歴・保持・migration

履歴はclient記録を失った通常本人が、reservedと未確認terminalを再発見できる方式にする。server側の世代とページの一貫性契約を採用時に決め、途中で変更があれば網羅性を確定せず再取得する。新保存の許可自体は常にserver取引内で判定する。履歴を読めない間も単なる章の閲覧や既知terminal結果確認は止めない。

確認済み記録の返答が不明なら同terminal identityで照合/再送する。clientだけで確認済みにしたり、未知操作を一括確認済みにしない。reservedと未確認terminalを期限切れだけで消さない。本文等を消去する場合も、terminal keyを再利用/再openできない最小identityを残す採用方式が必要。保持期限・容量・消去権限・退会との関係は未決。legacy操作はv7予約が存在したと偽装せず、移行対象/旧終了条件/通常本人の復帰を個別に決める。
