3. **該当箇所**: `material/03_基本設計書.md:17`, `material/04_詳細設計書.md:27`, `material/06_API設計書.md:24-30` / **指摘**: モバイルクライアントが Supabase Data API を直接呼ぶ構成なのに、クライアントへ埋め込むキーの種類が設計契約から完全に抜けている。「秘密情報」は Web 公開設計にだけ現れ、Expo 側では publishable key を使い、secret/service_role key は絶対に置かないという最重要境界がない。初心者が Dashboard に並ぶキーを取り違えると、RLS を全迂回して全データを読み書きできる。旧 NestJS ではサーバー内に閉じ込められた秘密が、ピボット後は教材本文で明示しないと守れない。 / **重大度**: C / **根拠**: Supabase 公式では publishable key はモバイルへ埋め込み可、secret key と legacy `service_role` は RLS を迂回するためクライアントへ露出禁止である。https://supabase.com/docs/guides/getting-started/api-keys

4. **該当箇所**: `material/05_DB設計書.md:102-112,196` / **指摘**: 「UPDATE は既読フラグのみ本人可」は RLS だけでは実現できない。`recipient_id = auth.uid()` の UPDATE ポリシーは行を選別するだけで、`actor_id`、`type`、`post_id`、`created_at` まで更新可能にする。直接DBアクセスへ変えたことで、旧API層のDTO・更新項目制限はもう存在しない。`authenticated` からテーブル全体の UPDATE を revoke して `read_at` だけ grant する、既読化RPCだけを公開する、または既読を別テーブルへ分離する必要がある。 / **重大度**: C / **根拠**: Supabase 公式は「RLS は列を制限しない。所有者向け UPDATE ポリシーだけでは全列を更新できる」と明記している。https://supabase.com/docs/guides/database/postgres/column-level-security

5. **該当箇所**: `material/05_DB設計書.md:68,146-147,189-193` / **指摘**: `posts` はスレッド構造を守るため論理削除すると決定しているのに、RLS表は所有者に `DELETE` を許している。改造クライアントは `deleted_at` を立てずに物理削除でき、まさに設計理由として避けた参照切れ・cascade・履歴消失を起こせる。旧 NestJS の削除ハンドラが暗黙に守っていた制約は消えた。`posts` の DELETE を全面拒否し、`deleted_at` 更新だけを許すRPCまたは列権限・トリガーが必要である。 / **重大度**: C / **根拠**: 同一文書内で「物理削除だと `reply_to_post_id` が指す先を失う」としながら、INSERT / UPDATE / DELETE を一括して許可している。RLS は許可された DELETE を論理削除へ変換しない。

6. **該当箇所**: `material/01_要件定義書.md:17-18`, `material/05_DB設計書.md:35-41,48-50`, `material/06_API設計書.md:27` / **指摘**: `auth.users` 作成トリガーは現状の `users` 行を生成できない。登録要件はメール＋パスワードだけなのに、公開プロフィールは `username`、`display_name`、`updated_at` が NOT NULL かつ既定値なしである。トリガーが何を挿入するか、`signUp` の `raw_user_meta_data` に何を必須で渡すか、username競合時にどうするかがない。このまま素直に実装するとトリガー失敗が Auth の signup 自体を失敗させる。 / **重大度**: C / **根拠**: Supabase 公式も `auth.users` トリガー失敗は signup をブロックすると警告し、`security definer set search_path = ''` と、metadataから挿入する列を明示した例を示している。https://supabase.com/docs/guides/auth/managing-user-data

7. **該当箇所**: `material/01_要件定義書.md:17,57`, `material/05_DB設計書.md:52-56`, `material/04_詳細設計書.md:16-29` / **指摘**: 「セッションとトークン更新は Supabase の責務」は半分だけ正しい。トークン発行は Supabase の責務だが、React Native 側には永続ストレージ、URL polyfill、`persistSession`、`autoRefreshToken`、`detectSessionInUrl: false`、排他lock、AppStateに応じた refresh の開始・停止が必要である。詳細設計の目次にはこのクライアントライフサイクルが一項目もなく、ブラウザ用クライアントと同じ初期化で済むという誤解を作っている。 / **重大度**: M / **根拠**: Supabase の React Native 公式クイックスタートは AsyncStorage、`react-native-url-polyfill`、`processLock`、AppState listener を明示的に要求している。https://supabase.com/docs/guides/auth/quickstarts/react-native

8. **該当箇所**: `material/05_DB設計書.md:62,67,77,86-88,96-98,106-112,118,134-136`, `material/06_API設計書.md:13-15,24-25` / **指摘**: 「DB定義の大半は無傷」という書き換え判断により、旧 Prisma／NestJS 側が埋めていた生成値の責任が宙に浮いている。直接 insert する `posts`、`post_media`、`notifications`、`hashtags` の UUID に default がなく、likes/follows/bookmarks/notifications の `created_at` にも default がない。クライアントが全値を生成する契約もないため、教材どおりの単純な Supabase insert は NOT NULL 違反または必須PK不足になる。DBで `gen_random_uuid()` / `now()` を持たせるか、全 insert payload に生成責任を明記すべきである。 / **重大度**: M / **根拠**: Supabase SDK はスキーマにない既定値を補わない。旧ORM・サービス層を削除した以上、生成責任はDB defaultかクライアント契約へ明示的に移す必要がある。

9. **該当箇所**: `material/01_要件定義書.md:57`, `material/04_詳細設計書.md:16-20`, `material/05_DB設計書.md:201-205` / **指摘**: 画像の MIME・拡張子・サイズ検証が画面入力バリデーションへ押し込まれ、Storage 側は「自分のフォルダ」ポリシーしか持っていない。直接アップロード構成では改造クライアントがUI検証を迂回できるため、任意形式・過大ファイルを保存できる。旧 NestJS のアップロード検証が消えた代わりに、bucket の `allowed_mime_types` / `file_size_limit` と `storage.objects` のポリシーをサーバー側受入条件として決める必要がある。 / **重大度**: M / **根拠**: Supabase Storage は bucket 単位の MIME type と file size 制限を提供しており、クライアント検証の代替ではなくサーバー側制約として設定できる。https://supabase.com/docs/guides/storage/uploads/file-limits
