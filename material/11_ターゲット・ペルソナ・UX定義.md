ステータス: ドラフト（局長レビュー待ち）

**単体でも始められる**（task-app修了を必須にしない）。

## 1. 商品としての位置づけ

| 項目 | 決定 |

| 用途 | 販売商品 兼 社内インターン育成教材（両立） |

## 2. ペルソナ（2本立て）

### ペルソナA: 社内インターン「はるかさん」（22歳・情報系でない大学生）

- プログラミング経験: ほぼゼロ（Progateを少し触った程度）
- 動機: エンジニア就職を目指してインターン参加。スマホアプリを作った実績が欲しい
- 環境: 会社支給または自前のMac。質問できる先輩（メンター）が周囲にいる
- つまずきポイント想定: 環境構築、エラーメッセージの読み方、非同期処理の概念
- 修了時のゴール: 「自分のスマホに自作SNSが入っている」状態。面接で実物を見せられる

### ペルソナB: 購入者「ケンジさん」（28歳・非IT職の独学者）

- プログラミング経験: 入門書1冊を写経した程度。Webチュートリアルで挫折経験あり
- 動機: 副業・転職を見据えてポートフォリオになる実物を作りたい
- 環境: 自宅のPC（Mac想定。Windows対応範囲は`08_テスト計画書.md`で扱う）。**質問できる相手がいない**
- つまずきポイント想定: 詰まったときに聞ける人がおらず、エラー1つで数日止まる
- 修了時のゴール: ストア公開はしないまでも、実機で動くSNSと「全プラットフォームを1言語で作った」という説明力

**設計上の含意**: ペルソナBが独りで完走できる教材は、ペルソナAには確実に完走できる。
よって教材の自己完結性・エラー先回り解説は**ペルソナB基準**で作る。

## 3. 学習者の前提と序盤設計

- 前提知識: **不要**（単体で始められる）。ただし PC の基本操作はできること
- TypeScript基礎パート: 本教材用に**新規執筆**する。ただし文体・進め方は局長制作済みの
  対話形式TS基礎教材（変数と定数〜クラス、磯貝×阿部形式、Google Drive上の原稿）を
  **スタイルの正本**とする（局長訂正 2026-07-24: 原稿の取り込みではなく
  「ああいう感じで一緒に進めている感を出したい」がゴール。詳細は
  `12_文体・AI臭さ排除方針.md`）
- task-app修了者は序盤パートをスキップできる導線（各章冒頭に「この章でできるようになること」
  を明記し、できる人は飛ばせる構成）

## 4. 教材から得られるユーザー体験（UX）

### 体験の核: 「先生と一緒に作っている」感覚

前作の反省（誇大・情緒的なAI文体で読者を煽る→局長苦情）を踏まえ、本作の体験は
**磯貝先生と隣で画面を見ながら進めている感覚**に全振りする。詳細は
`12_文体・AI臭さ排除方針.md`。

### 体験マイルストーン（学習者が「進んでる」と実感する節目）

| 節目 | 体験 |
|---|---|
| 序盤（TS基礎修了） | Playgroundでコードが動く。「読める・書ける」の実感 |
| Web版初回起動 | 自分のブラウザにSNSの画面が出る |
| 初投稿成功 | 自分が作ったフォームから投稿がDBに入りタイムラインに出る |
| リアルタイム通知 | 2台のブラウザ窓の間で、いいねが即座に相手に届く（パートC） |
| **スマホに入る瞬間（本教材のハイライト）** | 同じコードが自分のiPhone/Androidで動く。ここが「TypeScript Everywhere」の体験的証明（パートD — 15のC→D順と一致。Codex R4 m1対応） |
| 修了 | 3プラットフォームで動く自作SNS + 人に説明できる技術理解 |

### 挫折防止の設計原則

1. **エラーは先生と一緒に踏む**: 開発ログ（10 §5）に記録された本物の詰まりを生徒の
   エラー体験として対話で再現し、先生が読み方から解決までを実演する。本物の詰まりが
   無い章でエラーを創作しない（12 §1.3 — Codex R1 M10対応）
2. **各章が動く状態で終わる**: 章の途中で「動かない状態のまま次章へ」を禁止
3. **つまずき先回り**: 各章末に「よくあるエラーと対処」を必ず置く（前作の
   トラブルシューティングappendix方式を章単位に分散配置）

### 退屈・迷子防止の設計原則（局長指示 2026-07-24: 「つまんね」「これが何につながるか
わからない」「初心者が興味ないセキュリティガチガチ」を作らない）

4. **全章「地図」つき**: 各章の冒頭に、完成品SNSの画面図の中で「今日作るのはここ」を
   塗って示す。学習者が今の作業と完成品のつながりを見失う瞬間をゼロにする
5. **毎章、目に見える変化**: どの章も「章の前後で画面・動作に見える違いが1つ以上ある」
   ことを章設計の原則にする。例外（Codex R1 M5対応）: DB移行・通知基盤・ビルド設定など
   見える画面変化を作れない基盤章は、ターミナル出力・ログ・ツール画面での確認を
   代替の「見える変化」として扱ってよい（連続2章まで）。「本来の開発フローの順序」
   （10の大原則1）と衝突したときは開発フロー優先
6. **重いトピックは「必要になった瞬間」に最小限**: セキュリティ・設定・環境の話は
   独立章にせず、それが無いと目の前の機能が動かない・危ないという文脈が生まれた
   瞬間に、その解決に必要な分だけ扱う。網羅的な解説は付録に隔離し本編に混ぜない
7. **長さより密度**: 教材全体が長くなること自体は許容（局長判断）。禁止なのは
   「退屈な章」「つながりの見えない章」。章の数を削るより、章の質ゲートで守る
   （`10_教材制作フロー.md` G4の外部レビュー観点に「この章は完成品への
   つながりが見えるか・退屈でないか」を必須項目として追加する）

## 5. スコープ外（このドキュメントでは扱わない）

- 価格設定・販売チャネル（BOOTH/Udemy等）: 実装フェーズ後の販売準備工程で別途
- 教材の配布形式（ZIP/Webサイト）の決定は**Phase 1（章分割凍結と同時）へ前倒し**
  （Codex R1 M14対応 — 配布形式はスターター取得手順・教材内リンク・G6実走環境を左右するため、
  教材完成後に決めると全体手戻りになる）。価格・販売チャネルのみPhase 4で判断
